# Sprint 002 critique

Read both drafts, intent, lifecycle research, adapter/session code, and the actual fixture at `/private/tmp/gimbal-317-sprint/{main.go,run.py,claude-tap.py}`. No probes run. The supplied baseline—valid waiting returned around 10 seconds into a 20-second command, with call two correctly suppressed—demonstrates the original defect, not successful continuation.

1. **Claude: embedding T verbatim does not preserve reference semantics.** A valid standalone schema `{"$defs":{"X":{"type":"string"}},"$ref":"#/$defs/X"}` resolves against its document root. Placing it under `properties.value` leaves that reference pointing to the envelope root, where `$defs.X` does not exist. Recursive `$ref:"#"` likewise changes meaning. Unresolved item 4 is therefore a concrete correctness blocker, not merely uncertainty about native validator support. Specify reference-preserving composition and require a referenced/recursive T regression; the flat acceptance types cannot demonstrate this.

2. **Claude: missing terminal value can become successful empty text.** The envelope requires only `state`. Reading rule 4 assumes absent `value` becomes `null` and fails `ValidateJSON`. Actual `Text.ValidateJSON` uses `json.Unmarshal` into a string, which accepts `null`; Generate's subsequent decoding also succeeds with the zero value. Thus `{"state":"completed"}` can reproduce empty success. Require value presence independently of T validation, and define malformed-envelope handling. Resolve Text support before implementation: leaving it optional leaves the original prose-turn defect uncovered; enabling native schemas also requires reconciling the documented Text contract in `session.go`.

3. **Both: result ownership remains unresolved.** Claude's assertion that one host prompt makes every process result belong to that call contradicts the recorded resumed-process orphan notification. Skipping missing structured output handles that observed shape only. A stale notification followed by a structured completed declaration would still satisfy the proposed reader before the current assignment answers. Gemini names the race without specifying its rule. Require a concrete association contract and a regression sequence containing a stale notification/result before the current answer. Do not claim native origin/index alone proves ownership; the research explicitly denies that guarantee. This does not require service survival or exactly-once recovery.

4. **Gemini: the recommended prompt-only contract cannot cover arbitrary T.** A caller schema with `additionalProperties:false` and no state field cannot emit `state:completed` while remaining valid. The existing Recall fixture is such a type. Testing a specially state-bearing first type cannot validate Option B generally. Settle the adapter-owned completion representation, retaining native validation of the caller's final value, before declaring implementation ready.

5. **Acceptance still needs semantic waiting and host-input evidence.** The actual runner already checks ordering, a completion notification, receipt equality, tool usage, and changed launch schemas. However, it recognizes waiting by finding `WAITING_317` anywhere in the first result: even a completed object containing that text passes this check. Assert the actual nonterminal declaration. The tap captures stdout only, so a hidden host reprompt between waiting and completion is not excluded by the tool assertions. Capture submitted input and verify no additional prompt caused continuation. Use native result session IDs as well as launch arguments. Claude's proposed Session-event-only evidence is insufficient: the current projector drops task notifications. Gemini's six-second example also cannot guarantee waiting before completion; preserve explicit fixture failure when waiting was not witnessed.

6. **Failure and cleanup requirements need executable boundaries.** Gemini's blanket background-failure abort exceeds the adapter contract: a failed command may be a legitimate result reported through T. Distinguish provider/cancellation failure from workflow-owned rejection of this required command's failure. Conversely, the actual runner has no failure-path cleanup for descendants/observer, and only checks the first native PID on success; its outer timeout kills the direct subprocess without establishing descendant cleanup. Require bounded cleanup on timeout/assertion failure. Also finish/drain observer capture before reading logs, so a trailing missing event is not confused with failed behavior. These are temporary fixture requirements, not product retention or lifecycle features.
