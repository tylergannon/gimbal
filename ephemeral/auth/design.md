# Optional OAuth login and durable users

## TL;DR

Gimbal owns its login endpoints, session lifecycle, and request
gate. Two runtime-selected plugins supply provider identity and durable users
and sessions. `User` is an interface implemented by customer code. Ship a
GitHub provider and a small file-backed user store first. Authentication is off
unless explicitly selected at startup; selecting auth makes failures deny access.
An identity is admitted only if it already has a local user in the selected store.

All admitted users operate the same instance and its projects. This is access
control for trusted operators, not isolation between tenants or a sandbox for
agent execution.

## User and storage contracts

The proposed public types belong to a small standard-library-only `auth`
package. Registration stays in the root gimbal Registry, as existing native
plugins already export `Register(*gimbal.Registry) error`.

```go
type User interface {
    ID() string
    Name() string
}

type Identity struct {
    Issuer  string
    Subject string
    Name    string
}

type Session struct {
    Hash      string
    UserID    string
    ExpiresAt time.Time
}

type Users interface {
    CreateUser(context.Context, Identity) (User, error)
    UserForIdentity(ctx context.Context, issuer, subject string) (User, error)
    User(context.Context, string) (User, error)
    DeleteUser(context.Context, string) error
    CreateSession(context.Context, Session) error
    Session(context.Context, string) (Session, error)
    DeleteSession(context.Context, string) error
}
```

`User.ID()` is an immutable, nonempty local ID; `Name()` is display text and
never an authorization key. Customer implementations may hold additional data.
Gimbal neither serializes the interface nor persists its concrete Go type: a
session stores its ID, and `Users.User` reconstructs it on subsequent requests.
The store owns serialization and schema changes for its own implementation.

`CreateUser` is a trusted operator operation, never called by the login callback.
It atomically creates a durable user for an identity or returns the existing
user for that exact issuer/subject pair. Concurrent calls and retries return
the same local ID. Identity keys are separate fields, not an ambiguous
concatenation. Different identities remain different users; there is no
automatic linking by name or email. Existing names may remain unchanged.

`UserForIdentity` looks up the existing local user for a verified identity.
Absence means not admitted. `User` looks up that same local user by ID on
subsequent requests and must return a matching nonempty ID. Both return
auth.ErrNotFound for absence. `DeleteUser` durably removes the user and its
identity mapping and is idempotent. Recreating that identity creates a new ID;
old sessions cannot acquire access to the new user. Requests and active streams
must retrieve the user again, so deleting the user revokes existing access.
There is one user registry, in the plugin, and no separate allowlist in config.

Session hashes are SHA-256 of 32-byte cryptographically random bearer tokens
generated by Gimbal. Only the token goes in the cookie; only its hash goes to
the store. The hash is lowercase hex. Session creation must verify the user
exists, reject an existing hash, and durably complete before returning success.
Reads return immutable copies.
User IDs are never reused.

`auth.ErrNotFound` classifies absent users and sessions. All other errors are
operational failures. `DeleteSession` is durable and idempotent, including an
already absent session. Successful user creation, session creation, and deletion
must survive an ordinary process restart and a crash after success was returned.
The plugin owns concurrency control and persistence; Gimbal adds no storage
framework. Methods are safe for concurrent requests and honor their contexts.

The needed operations are user creation, identity lookup, ID lookup, user
removal, session issuance, session lookup, and session revocation. Password
operations do not apply to provider-owned credentials.
There is no speculative profile-editing interface, account linking, user directory UI,
role hierarchy, organization model, or per-project permission system.

## Provider contract

The provider returns a verified external identity, not a local `User`. The user
store owns local users, independently of the selected provider.

```go
type Provider interface {
    AuthorizationURL(state, codeChallenge, nonce string) (string, error)
    Exchange(ctx context.Context, code, codeVerifier, nonce string) (Identity, error)
}
```

Credentials and one exact callback URL are constructor configuration. The
application supplies unpredictable state and nonce and an S256 PKCE challenge.
`Exchange` uses the same configured callback URL and code verifier and returns
an identity only after provider verification. State validation happens in
Gimbal before Exchange. The provider binds all returned identities to its
configured issuer; unverified fields from browser input are never identities.

The first provider is GitHub.com. It uses the token endpoint and authenticated
`/user` endpoint, returning issuer `https://github.com` and the decimal numeric
user ID as subject. Login/name is display data. Request no extra OAuth scopes;
discard the access token after fetching identity. Gimbal does not use it for
repositories, agent credentials, or provider-token refresh.

A future Google plugin fits the same seam: it validates the ID token including
signature, audience, issuer, expiry, and the supplied nonce; it normalizes the
issuer to `https://accounts.google.com` and uses sub. GitHub ignores nonce because
its flow is not OIDC. Google is compatibility reasoning, not first-slice work.

## Login and request handling

Gimbal defines these routes. Plugins receive no ResponseWriter, request handler,
route registration, or access to the rest of the HTTP application.

1. GET `/auth/login` shows a sign-in page in the existing SvelteKit application.
   Its button calls an application-owned skgo `beginLogin` command. The command
   runs skgo's normal origin check, generates state/verifier/nonce, and sets a
   five-minute HttpOnly flow cookie containing those values and expiry. Encrypt
   and authenticate the cookie with an AEAD and a random per-process key. Keep
   the small payload bounded and use a fresh AEAD nonce for each issuance. A
   restart invalidates unfinished logins because the key changes. There is no
   server-side pending-flow map to exhaust. The command returns the provider
   authorization URL for normal full-document navigation to the external
   provider, without hand-written fetch or History API calls. SvelteKit goto
   accepts application navigation, so it is not used for the external URL.
   There is one selected
   provider and one configured callback URL for the instance.
2. GET `/auth/callback` is an application server route because the provider
   navigates to it. Validate/decrypt the flow cookie, check its expiry and the
   returned state, and clear that cookie on completion. A missing cookie,
   mismatched state, invalid code or provider denial creates no user/session.
   Exact-code replay is refused by the provider's one-use authorization-code
   exchange; do not cache a successful identity result for reuse. Concurrent
   exchanges of the same code must yield at most one successful login. The
   stateless cookie alone does not claim a server-enforced one-use flow: a new
   provider-issued code can start another login within its five-minute lifetime.
   Existing sessions are independently revocable through durable storage.
3. Exchange the code for a verified Identity. Call UserForIdentity with its
   exact issuer/subject. An identity without a local user receives 403 and no
   session is created. There is no automatic user creation or public signup.
4. Generate a fresh token and durably CreateSession with the local user ID
   and an absolute eight-hour expiry. Never adopt a token supplied
   by the browser. Replacing an existing session also revokes the previous
   session before the replacement cookie is issued. Set the session cookie
   only after the required durable operations succeed, then redirect to `/`.
5. On each protected request, hash the cookie token, read the session, check its
   expiry, and retrieve User by local ID. Reject absent,
   expired, malformed or invalid users/sessions. Never serialize the customer's
   concrete User or put an OAuth token into a cookie. Attach User to request
   context; expose only an explicit ID/name DTO if the page needs it.
6. The application-owned skgo `logout` command uses the same authentication
   and skgo origin checks, durably deletes that session, then expires the browser
   cookie. A deletion failure
   returns 503 without reporting successful logout or clearing the cookie, so
   the caller can retry. Logout does not cancel workflows already running.

Cookies are host-only, Path=/, HttpOnly, Secure, SameSite=Lax; auth responses are
Cache-Control: no-store. HTTPS and an explicit trusted public origin are required
when auth is enabled, including behind a reverse proxy. The selected auth origin
is the sole origin passed to both auth and every skgo configuration; there is no
second origin for remotes. Cookie names use the `__Host-` prefix. A proxy
terminates HTTPS while Gimbal retains its loopback or
UDS listener. Do not infer origin/callback URLs from arbitrary forwarded headers.
After login the browser goes to `/`; no return-path parameter or redirect policy
is needed. The callback's code/state query parameters are OAuth protocol inputs,
not Gimbal page state or resource identity.

Protect the entire web stack: pages, SSR loads, remote queries/commands/forms,
file routes, run snapshots, streams, and artifacts. The only unauthenticated
exceptions are GET `/auth/login` and its generated route-data request, the
exact generated POST remote for beginLogin, GET `/auth/callback`, and
manifest-listed static build assets. Logout is protected.
Never expose other functions from a shared remote module by prefix. The login
page and route-data request dispatch before projectRequest, so their layout
load has no Owner or project-choice context and reads no project data. The
anonymous layout does not start RecorderBridge or other project subscriptions.
Classify built static resources from the build manifest, without deriving a
per-page chunk graph. Never exempt a blanket `/_app/` prefix that also contains
remote endpoints, and never project files or artifacts. Unauthenticated direct
document navigation to a page receives an HTTP redirect to `/auth/login`.
Unauthenticated SvelteKit route-data requests receive HTTP 200 with Kit's data
redirect envelope (`type: redirect`, `status: 303`, `location: /auth/login`),
not a bare 401 or an HTTP redirect to HTML. API and remote requests receive
401, including a session whose local user was deleted. Storage errors
return 503 without exposing data. Errors do not switch authentication off.

The UI owners of remote operations handle rejected authentication with
`isHttpError(error, 401)` from SvelteKit and navigate to `/auth/login` using
`goto`. Apply that same handling in the query error boundary; a command's
rejected promise needs its own catch because render boundaries do not catch
event-handler failures. Keep other errors in their normal UI. Do not replace
global fetch, build a custom remote client, or automatically replay a mutation
after login. Only a refused operation triggers this handling; auth checking
does not revoke permission retroactively from work already accepted.

Keep skgo's existing Origin checks for remotes, including beginLogin and logout.
Apply the same expected-origin check to any cookie-authenticated unsafe server
routes that do not go through skgo's remote check. Authenticated SSR internal fetches
must retain the originating request's identity/session, with no global bypass
header or process-wide authenticated flag. Every long-lived response, including
observation SSE and skgo LiveQuery such as watchRecording, rechecks session
expiry, revocation and user existence at least every 30 seconds and closes on
failure. This bounds access after logout; already accepted workflow execution
continues. Unauthenticated requests never start application work.

## Selection and durability

The concrete selection surface is `gimbal --auth-file /absolute/auth.json` on the
root command, which is the existing command that serves the web application.
This new flag is an explicit opt-in, not a search for optional configuration.
An explicitly supplied blank, missing, unreadable, malformed, or incomplete
file fails startup; it never means auth off. Relative paths are rejected. No
per-HOME auth configuration or implicit discovery is introduced.

`web.WithAuthFile(path)` carries the same selection into `web.NewInstance`.
NewInstance resolves and validates it once, before starting control or web
listeners, and receives an error for unavailable plugins, credentials or
storage. Native plugins are loaded/registered by the caller before NewInstance,
as the root command's serve function already does. The flag is added to the
root command's serverFlags, which is not shared by other commands. The current
run-prompt path uses WithNoWeb and exposes no web listener. Custom hosts and
example programs that serve a web listener can select the same WithAuthFile
Option. Every NewInstance
caller without this Option explicitly retains the open local behavior. This
does not secure another independently started instance merely because its
project or HOME happens to match; the operator must select auth for the instance
the public proxy targets. Command help must make this startup choice explicit.

The required file contains provider and users selections and one HTTPS public
origin. With auth on, that origin configures the whole application and callback;
if GIMBAL_WEB_ORIGIN is also supplied and differs, startup fails. With auth off,
the current listener/override origin behavior stays unchanged. No automatic
fallback to the loopback origin is allowed with auth on, including UDS mode.

No first-login administrator or public signup is added. An empty user store
denies everybody. Operators provision/remove identities through local user
operations, without restarting the web instance. The two trusted local commands
are `gimbal user add --instance-dir /absolute/instance --issuer https://github.com
--subject 123456 --name Tyler` and `gimbal user remove --instance-dir /absolute/instance
USER_ID`. These commands call
CreateUser/DeleteUser through the running instance's Unix control socket. The
server performs the storage operations using its already-open Users handle;
control clients neither load native plugins nor open a second writer. They
resolve and verify the live instance through its existing discovery protocol
and refuse an auth-off instance. The CLI returns the stable local ID.
Customer hosts may call the same Users methods from their trusted operator code.
GitHub provisioning help shows `gh api users/LOGIN --jq .id` to obtain the
numeric subject; the user-facing login is not used as the stored identity key.

Required auth-file shape:

```json
{
    "provider": {
      "name": "github",
      "configuration": {
        "clientID": "...",
        "clientSecretEnv": "GIMBAL_GITHUB_CLIENT_SECRET"
      }
    },
    "users": {
      "name": "files",
      "configuration": { "directory": "/absolute/instance/auth" }
    },
    "origin": "https://gimbal.example.com"
}
```

Gimbal derives the single callback URL from the configured origin and its
fixed callback route and passes it to the provider constructor. Configuration
stores a secret reference, not its value. Auth secrets, tokens, pending-flow
cookies, and callback query strings are never written to run logs or prompts.

Add ProviderDefinition and UsersDefinition registrations to the existing
Registry: Name, ValidateConfiguration, and Connect(ctx, raw configuration).
Provider construction also receives the application-owned callback URL. Connect
returns the corresponding interface; it neither binds a listener nor registers
HTTP routes. Resource-owning implementations may implement io.Closer, following
the existing backend pattern. Stop accepting requests, terminate streams, join
in-flight handlers, then close those handles on shutdown. The two selections
are independent; a customer can replace storage without rewriting GitHub login.

The first Users plugin persists users, identity mapping, and session hashes in
an instance-owned directory with mode 0700 and files 0600. One JSON state file
with serialized mutations and atomic durable replacement is enough. Hold an
exclusive directory lock for the connection lifetime; a second owner fails
startup. Flush the replacement file and directory before reporting a mutation
successful. Missing state is initialized only in a new directory; malformed or
inconsistent existing state fails startup. The file implementation targets one
instance, not shared network storage. Expired sessions can be pruned on mutations.
Customer implementations may use a database while preserving the same contract.

Users and sessions survive restart, but User values are reloaded. Restart does
not need GitHub to recognize an existing session. Loss of provider connectivity
prevents new login; loss of the selected store denies protected access. Changing
provider does not merge accounts; changing stores requires explicitly carrying
their durable data or users log in again. No implicit data migration is added.

## Integration and acceptance

Move projectRequest composition into the shared `web.NewHandler` assembly and
pass it that request-boundary function explicitly. The complete order is:
authentication gate -> projectRequest -> observation/skgo application. The
public auth routes and static login assets are dispatched by the gate before
projectRequest; all protected paths, including unknown project IDs, meet the
gate first. The production runtime and integration tests provide the same
project boundary and auth inputs. Tests that use bare NewHandler remain useful
unit tests, but do not prove the instance-wide ordering. Preserve normal SSR
fetch dispatch and carry the original request session through it, never an
auth bypass. Resolve plugins before NewInstance starts either listener.
The root command's serve function must start its optional --task-listen listener only after
NewInstance has resolved auth successfully; today it starts that listener first.

The local CLI uses a separate Unix control socket. Authentication of remote
browser users does not isolate the server's OS account or trusted local callers.
The existing control transport remains a local operator capability, and must
never be published by the web proxy. The optional task listener exposes
`/tasks/` and `/workflows/` on another HTTP server and executes trusted commands.
It stays on a private transport/network and is never published through the
web proxy; this design does not claim OAuth protects that listener. Any live
deployment proof must identify all listeners and confirm that boundary.
When auth and --task-listen are both selected, command help and the startup
message explicitly identify the task listener as outside web authentication.

The UI needs sign-in, sign-out, and the current user's name. No user management
page or password screen is introduced. Existing operator/supervisor attribution
retains its current contract, including Source "person"; user attribution is a
separate future request.

Implementation is accepted only after observing: auth-off behavior; startup
failure for an explicit missing auth file, conflicting origin, or unavailable
selected plugins/store; anonymous refusal of pages (including unknown project
paths), remotes, streams and file downloads; an admitted real GitHub login; refusal of
an unprovisioned account; local user provisioning/removal; consistent user ID
under concurrent creation and restart; session survival across restart;
expiry and replay refusal; durable logout with
bounded stream closure; rejection of cross-origin mutations; isolation of two
browser cookies; document navigation, client-side route navigation and remote
actions returning to sign-in after expiry, cross-tab logout or user deletion;
and customer User rehydration through a replacement Users
implementation. Repeatable cases belong in package tests. Run records and
screenshots are not committed. Design consensus does not substitute for these
implementation observations.
