# Optional OAuth login and durable users

## TL;DR

Gimbal owns its login endpoints, admission check, session lifecycle, and request
gate. Two runtime-selected plugins supply provider identity and durable users
and sessions. `User` is an interface implemented by customer code. Ship a
GitHub provider and a small file-backed user store first. Authentication is off
when no auth configuration exists; selecting auth makes failures deny access.

All admitted users operate the same instance and its projects. This is access
control for trusted operators, not isolation between tenants or a sandbox for
agent execution.

## User and storage contracts

The proposed public types belong to a small standard-library-only `auth`
package. Registration stays in the root gimbal Registry, as existing native
plugins already export `Register(*gimbal.Registry) error`.

```go
type User interface {
    ID() string
    Name() string
}

type IdentityKey struct {
    Issuer  string
    Subject string
}

type Identity struct {
    IdentityKey
    Name string
}

type Session struct {
    Hash      string
    UserID    string
    Identity  IdentityKey
    ExpiresAt time.Time
}

type Users interface {
    CreateUser(context.Context, Identity) (User, error)
    User(context.Context, string) (User, error)
    CreateSession(context.Context, Session) error
    Session(context.Context, string) (Session, error)
    DeleteSession(context.Context, string) error
}
```

`User.ID()` is an immutable, nonempty local ID; `Name()` is display text and
never an authorization key. Customer implementations may hold additional data.
Gimbal neither serializes the interface nor persists its concrete Go type: a
session stores its ID, and `Users.User` reconstructs it on subsequent requests.
The store owns serialization and schema changes for its own implementation.

`CreateUser` atomically creates a durable user for an identity or returns the
existing user for that exact issuer/subject pair. Concurrent callbacks and
retries return the same local ID. Identity keys are separate fields, not an
ambiguous concatenation. Different identities remain different users; there is
no automatic linking by name or email. Existing names may remain unchanged.

Session hashes are SHA-256 of 32-byte cryptographically random bearer tokens
generated by Gimbal. Only the token goes in the cookie; only its hash goes to
the store. The hash is lowercase hex. Session creation must verify the user
exists and the session's identity belongs to that user, reject an existing hash,
and durably complete before returning success. Reads return immutable copies.
User IDs are never reused.

`auth.ErrNotFound` classifies absent users and sessions. All other errors are
operational failures. `DeleteSession` is durable and idempotent, including an
already absent session. Successful user creation, session creation, and deletion
must survive an ordinary process restart and a crash after success was returned.
The plugin owns concurrency control and persistence; Gimbal adds no storage
framework. Methods are safe for concurrent requests and honor their contexts.

The needed operations are creation, lookup, session issuance, lookup, and
revocation. Password operations do not apply to provider-owned credentials.
There is no speculative CRUD interface, account linking, user directory UI,
role hierarchy, organization model, or per-project permission system.

## Provider contract

The provider returns a verified external identity, not a local `User`. The user
store owns local users, independently of the selected provider.

```go
type Authorization struct {
    State, CodeChallenge, Nonce string
}

type Callback struct {
    Code, CodeVerifier, Nonce string
}

type Provider interface {
    AuthorizationURL(Authorization) (string, error)
    Exchange(context.Context, Callback) (Identity, error)
}
```

Credentials and one exact callback URL are constructor configuration. The
application supplies unpredictable state and nonce and an S256 PKCE challenge.
`Exchange` uses the same configured callback URL and code verifier and returns
an identity only after provider verification. State validation happens in
Gimbal before Exchange. The provider binds all returned identities to its
configured issuer; unverified fields from browser input are never identities.

The first provider is GitHub.com. It uses the token endpoint and authenticated
`/user` endpoint, returning issuer `https://github.com` and the decimal numeric
user ID as subject. Login/name is display data. Request no extra OAuth scopes;
discard the access token after fetching identity. Gimbal does not use it for
repositories, agent credentials, or provider-token refresh.

A future Google plugin fits the same seam: it validates the ID token including
signature, audience, issuer, expiry, and the supplied nonce; it normalizes the
issuer to `https://accounts.google.com` and uses sub. GitHub ignores nonce because
its flow is not OIDC. Google is compatibility reasoning, not first-slice work.

## Login and request handling

Gimbal defines these routes. Plugins receive no ResponseWriter, request handler,
route registration, or access to the rest of the HTTP application.

1. GET `/auth/login` shows a minimal sign-in page. POST `/auth/login` verifies
   the configured browser origin and starts provider authorization. Gimbal
   records a five-minute, one-use pending flow bound to a random HttpOnly cookie
   in the initiating browser. It retains state, verifier, nonce, selected
   provider, and a validated same-origin return path. Pending flows may be in
   memory; a restart invalidates them and the user restarts login. Expired flows
   are removed and a new attempt replaces the browser's prior attempt.
2. GET `/auth/callback` validates the pending flow cookie, state, provider and
   expiry and consumes the flow exactly once before any token exchange. OAuth
   denial or invalid fields end the attempt without creating a user/session.
3. Exchange the code for a verified Identity. Check its exact issuer/subject
   against the configured allowed-user list. Unlisted identities receive 403
   and no user or session is created. Then call CreateUser.
4. Generate a fresh token and durably CreateSession with the local user ID,
   identity key, and an absolute eight-hour expiry. Never adopt a token supplied
   by the browser. Replacing an existing session also revokes the previous
   session before the replacement cookie is issued. Set the session cookie
   only after the required durable operations succeed, then redirect to the
   validated return path (default `/`).
5. On each protected request, hash the cookie token, read the session, check its
   expiry and identity admission, and retrieve User by local ID. Reject absent,
   expired, malformed or invalid users/sessions. Never serialize the customer's
   concrete User or put an OAuth token into a cookie. Attach User to request
   context; expose only an explicit ID/name DTO if the page needs it.
6. POST `/auth/logout` uses the same authentication and origin checks, durably
   deletes that session, then expires the browser cookie. A deletion failure
   returns 503 without reporting successful logout or clearing the cookie, so
   the caller can retry. Logout does not cancel workflows already running.

Cookies are host-only, Path=/, HttpOnly, Secure, SameSite=Lax; auth responses are
Cache-Control: no-store. HTTPS and an explicit trusted public origin are required
when auth is enabled, including behind a reverse proxy. Cookie names use the
`__Host-` prefix. A proxy terminates HTTPS while Gimbal retains its loopback or
UDS listener. Do not infer origin/callback URLs from arbitrary forwarded headers.
Return paths must be local paths, with no scheme, host, or protocol-relative URL.

Protect the entire web stack: pages, SSR loads, remote queries/commands/forms,
file routes, run snapshots, streams, and artifacts. The only unauthenticated
exceptions are the login page, login initiation, and callback. Use a self-contained
login page so it needs no exceptions for application assets. Unauthenticated
page navigation redirects to login; API and remote requests return 401; a valid
session for an identity outside the admission list receives 403. Storage errors
return 503 without exposing data. Errors do not switch authentication off.

Check the expected Origin on all cookie-authenticated unsafe requests, including
login and logout; keep skgo's existing checks. Authenticated SSR internal fetches
must retain the originating request's identity/session, with no global bypass
header or process-wide authenticated flag. Active observation streams recheck
session expiry, revocation and admission at least every 30 seconds and close on
failure. This bounds access after logout; already accepted workflow execution
continues. Unauthenticated requests never start application work.

## Selection and durability

No auth configuration means authentication is off and no auth store is opened.
An auth configuration requires explicit provider and users selections and the
trusted public origin. Missing plugins, invalid selections, missing credentials,
or unavailable storage fail startup before listeners accept work. An empty
allowed-user list denies everybody. There is no first-login administrator or
public signup. The operator edits the identity list and restarts the instance
to change admission; existing sessions are rechecked against the new list.

Conceptual configuration (field casing may follow the existing config format):

```json
{
  "auth": {
    "provider": {
      "name": "github",
      "configuration": {
        "clientID": "...",
        "clientSecretEnv": "GIMBAL_GITHUB_CLIENT_SECRET"
      }
    },
    "users": {
      "name": "files",
      "configuration": { "directory": "/absolute/instance/auth" }
    },
    "origin": "https://gimbal.example.com",
    "allowedUsers": [
      { "issuer": "https://github.com", "subject": "123456" }
    ]
  }
}
```

Gimbal derives the single callback URL from the configured origin and its
fixed callback route and passes it to the provider constructor. Configuration
stores a secret reference, not its value. Auth secrets, tokens, pending-flow
cookies, and callback query strings are never written to run logs or prompts.

Add ProviderDefinition and UsersDefinition registrations to the existing
Registry: Name, ValidateConfiguration, and Connect(ctx, raw configuration).
Provider construction also receives the application-owned callback URL. Connect
returns the corresponding interface; it neither binds a listener nor registers
HTTP routes. Resource-owning implementations may implement io.Closer, following
the existing backend pattern. Stop accepting requests, terminate streams, join
in-flight handlers, then close those handles on shutdown. The two selections
are independent; a customer can replace storage without rewriting GitHub login.

The first Users plugin persists users, identity mapping, and session hashes in
an instance-owned directory with mode 0700 and files 0600. One JSON state file
with serialized mutations and atomic durable replacement is enough. Hold an
exclusive directory lock for the connection lifetime; a second owner fails
startup. Flush the replacement file and directory before reporting a mutation
successful. Missing state is initialized only in a new directory; malformed or
inconsistent existing state fails startup. The file implementation targets one
instance, not shared network storage. Expired sessions can be pruned on mutations.
Customer implementations may use a database while preserving the same contract.

Users and sessions survive restart, but User values are reloaded. Restart does
not need GitHub to recognize an existing session. Loss of provider connectivity
prevents new login; loss of the selected store denies protected access. Changing
provider does not merge accounts; changing stores requires explicitly carrying
their durable data or users log in again. No implicit data migration is added.

## Integration and acceptance

The web gate belongs in the shared `web.NewHandler` composition, outside
`observation.Routes`, and before the project request handler can disclose
project data. Preserve the normal SSR fetch route and carry request identity
through it. Resolve plugins before `web.NewInstance` starts either listener.
The auth configuration is passed explicitly into handler construction, so the
binary and tests exercise the same assembly.

The local CLI uses a separate Unix control socket. Authentication of remote
browser users does not isolate the server's OS account from itself. Restrict
the control socket to 0600 even for its short-path fallback, and keep discovery
and auth state private to the operator. The optional task listener exposes
`/tasks/` and `/workflows/` on another HTTP server and executes trusted commands.
It stays on a private transport/network and is never published through the
web proxy; this design does not claim OAuth protects that listener. Any live
deployment proof must identify all listeners and confirm that boundary.

Browser actions use the authenticated local user ID for the existing By/source
attribution instead of the literal "person". No full audit subsystem is added.
The UI needs sign-in, sign-out, and the current user's name. No user management
page or password screen is introduced.

Implementation is accepted only after observing: auth-off behavior; startup
failure for unavailable selected plugins/store; anonymous refusal of pages,
remotes, streams and file downloads; an admitted real GitHub login; refusal of
an unlisted account; consistent user ID under concurrent creation and restart;
session survival across restart; expiry and replay refusal; durable logout with
bounded stream closure; rejection of cross-origin mutations; isolation of two
browser cookies; and customer User rehydration through a replacement Users
implementation. Repeatable cases belong in package tests. Run records and
screenshots are not committed. Design consensus does not substitute for these
implementation observations.
