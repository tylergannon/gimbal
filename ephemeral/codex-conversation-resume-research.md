The design path is clear, with one installed-runtime validation gap: **0.155.0-alpha.9.2 must demonstrate unsubscribe→resource unload→same-ID continuation in isolation.** Persist Codex’s native `thread.id`, explicitly unsubscribe on graceful dashboard shutdown, and resume that same ID after restart. Correct the earlier “simply disconnect” recommendation: socket closure alone has no proven cleanup here, and unsubscribe permits delayed unload rather than immediate release.

The smallest proposal is to add the native thread ID and provider lifecycle outcome to the existing conversation JSON. Save the ID as soon as native creation succeeds. Keep durable identity separate from `Live`: a saved ID does not establish a current binding or guaranteed resumability. On restart, retain readable history and `Live=false`; on the first send, construct the adapter, call `thread/resume` with the saved ID, rebuild local session/routing state, and only then run the turn. Never silently create a new thread or seed one from the visible transcript.

The harness needs narrowly scoped capabilities to resume an existing native session and detach a durable conversation. Graceful manager shutdown should explicitly send `thread/unsubscribe`, remove local bindings, and close Gimble’s own connection after its subscriptions are released. **A hard kill cannot execute this shutdown path; cleanup after bare socket loss remains unverified.** Keep archive-based `Close` for workflow sessions outside this decision. Cleanup must neither start a stopped daemon nor stop/restart the shared daemon. Missing IDs or definitively unavailable/archived history mean continuation is unavailable; uncertain detach/resume results remain unverified. A saved ID permits a later resume attempt but does not establish resource cleanup. The proposal accepts delayed cleanup, not an immediate release guarantee. [Official API](https://developers.openai.com/codex/app-server/) · [Local design evidence][design]

1. **Current Gimble boundary.** Conversation JSON already preserves metadata, visible messages, worktree/branch, and workflow records. Reload normalizes interrupted state and forces `Live=false`. The manager’s `activeConversation.session`, adapter pointer, and Codex routing maps are process-local. First send creates the native session lazily; after restart, the manager rejects sends because no active binding exists. Same-process socket reconnection can resume locally known IDs, but cannot recover an ID lost with the process. The harness exposes creation, turns, steering, fork, and close, with no persisted-ID resume or detach capability. The manager restart test proves four visible messages and worktree survival without constructing an adapter; it does not prove native continuation. Cleanup tests establish idempotence, local-state removal on failure, and no daemon start during cleanup. [Manager][manager] [Harness][harness] [Tests][tests]

2. **Identity and native history.** The continuation key is `thread.id`, passed as `threadId` to `thread/resume`. `thread.sessionId` describes the session-tree root and can be shared by forks; it must not replace the thread ID. Stored history and loaded runtime state are separate: `thread/read` inspects persisted history without loading/subscribing, while `thread/loaded/list` reports memory residency. The captured installed binary is **0.155.0-alpha.9.2**; its generated schemas expose read, resume, archive, unarchive, and unsubscribe. Exact-version protocol source prefers `thread_id`; alternative history/path selectors can override it and are unnecessary here. Interface availability proves neither cleanup timing nor successful restoration. [Versioned protocol source](https://github.com/openai/codex/tree/rust-v0.155.0-alpha.9.2/codex-rs/app-server-protocol) · [Local identity and installed evidence][identity]

3. **Lifecycle semantics and the old defect.** Current official documentation, captured September 19, says unsubscribe removes only this connection’s subscription. After the last subscriber leaves, unloading occurs after **30 minutes without subscribers or activity**. An `unsubscribed` response is therefore not cleanup proof. Archive moves stored history into archived storage; unarchive restores its storage location. Neither operation is required for ordinary durable continuation. Gimble’s current `Close` explicitly archives, and its `callThread` guard rejects archived resume/fork; that restriction must not be generalized into a timeless provider guarantee. [Official lifecycle][official] [Adapter][adapter]

   Upstream `main` source observed September 19 computes the unload deadline from both subscriber absence and inactivity, then shuts down/removes runtime state; a shutdown timeout leaves the thread loaded. This is a dated, unpinned source observation, not verification of the installed alpha. An [upstream disconnect report](https://github.com/openai/codex/issues/14137) also describes orphaned loaded threads. No source here proves every MCP child exits in the installed version. [Upstream lifecycle source](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/request_processors/thread_lifecycle.rs) · [Local observation][primary]

   The recorded **0.153.4** defect was specific: API or CLI unarchive produced an `active`, loaded ghost with no rollout that could not be archived/deleted until daemon restart. Current schema availability does not establish a fix. Treat that as historical evidence, leave present unarchive behavior unresolved, and avoid automatic archive→unarchive recovery. Its fix status need not block the proposed non-archiving path. [Historical evidence][history]

4. **Minimum implementation consequence.** The manager must persist native identity and distinguish saved history from a live binding; the harness must permit existing-ID resume and non-archiving detach; Codex must populate its normal session/routing maps from the resume response. Require the returned ID to match the saved ID. Preserve honest errors for archived/missing history rather than manufacturing continuity. Successful detach records subscription removal, not provider resource teardown. Other subscribers or activity can legitimately keep a thread loaded, so dashboard shutdown cannot promise global unload. These are bounded changes to human-facing conversations, not workflow recovery or a new lifecycle framework. [Design evidence][design]

5. **One material open question and deciding test.** Does installed 0.155.0-alpha.9.2 actually support unsubscribe→unload→same-ID resume, including release of target-owned MCP resources? Run one future isolated test using a temporary project, worktree, Codex home, and private app-server endpoint; verify endpoint isolation before any mutation. Use `gpt-5.6-luna`, one target thread, and a separately subscribed control thread. Do not connect to the shared daemon. [Test basis][test]

   Have the target read a random token from a temporary file and respond only `READY`. Ensure the token is absent from Gimble’s persisted visible transcript, then delete the file. Record its native ID and target-owned MCP process/descriptor baseline. Shut down Gimble through explicit unsubscribe and close its connection. Before restarting Gimble, wait at most 35 minutes for the documented idle window: require the target absent from `thread/loaded/list`, its unarchived history still readable, and its measured MCP resources released. A subscribed control must remain loaded and callable, with the private daemon identity unchanged. Use read-only polling that does not resume/subscribe the target; do not depend on receiving notifications over the closed connection.

   Restart only Gimble, resume the saved ID, and request the token without supplying it or enabling alternate retrieval. Pass requires exact recovery, the same returned ID, and no replacement thread. Together, these checks distinguish native model context from transcript replay and prove cleanup before reload. A timeout, resource leak, changed ID, or failed context recovery leaves the candidate unverified and blocks claiming restart continuation; diagnose only in isolation. No live lifecycle test was run for this recommendation, and no shared session may be mutated, archived, unarchived, interrupted, stopped, or restarted during research.
