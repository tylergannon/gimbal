# [P1] Claude completion scope can deadlock planner and validator turns

https://github.com/tylergannon/gimbal/issues/390
State: OPEN

## Problem

An ordinary Claude planning turn can finish its requested response but declare the adapter-private state `waiting` because the larger implementation outcome is unfinished. Gimbal then waits indefinitely instead of dispatching the coder. Later planner and validator turns are exposed to the same ambiguity. This blocks unattended workflows.

## Observed on 2026-09-25

A real hosted `implement` run for #386 used Sonnet 5 for planning/validation and GPT-6 Luna for coding. Installed Gimbal reported revision `7460360e`; both prior Claude fixes below are included.

- At 14:10 Costa Rica time, Sonnet produced the complete backlog and selected task, wrapped in `state: waiting`, with message: `Backlog planned: core Pi adapter first, then steer/cancel/fork; outcome not yet delivered.`
- No coder started. The native process stayed alive, and the workflow remained running for about 50 minutes.
- A generic finish-planning steer was delivered but produced the same waiting response.
- A second steer explained that the outer state describes completion of the current planning response, not achievement of the implementation outcome. Sonnet returned `state: completed`; its `value` was exactly equal to the preceding waiting payload.
- Gimbal closed the planner turn and started Luna at 15:00. No restart or runtime edit was needed for this one-turn recovery. This does not repair future Claude turns.

## Fault and previous fixes

`claude/claude.go` completionSchema tells the model: `Use waiting while required work is pending, then completed only when the whole assignment is done.` `waitTurn` continues reading on waiting and only returns the caller value on completed. In this run the planner understood whole assignment as the workflow outcome, although its assigned work was just selecting a task. The steer response establishes that the process was responsive and a valid task result existed; there is no evidence this stall was a lost-result race.

- #317 was closed by merged PR #322 (`6755d0b4`, September 20). That fix correctly kept a Generate call alive through real background-task completion and verified a schema-changing same-session follow-up. Its completion envelope is active here.
- #351 was filed afterward for Haiku structured-output workflow stalls and remains open without a linked repair. It is related, but do not claim identical cause or close it without reproducing its own failure.
- #371 / PR #372 (`aa144700`, September 23) fixed tool-event correlation failures, not this waiting behavior.

A validator must be able to finish its assessment with substantial gaps without waiting for someone else to fix them.
