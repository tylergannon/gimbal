Finish workflow launch, Runs and live agent focus inside the workspace

## Outcome

A person can launch a workflow in the current project, understand the run and its agents, and steer the active work without leaving the workspace. Current activity, trouble and requests for human input remain legible. Deliver this as one independent workflow-observation slice.

This replaces the workflow/run work bundled into the unaccepted draft #572. Start from current main and selectively reuse the useful presentation changes. Neither the combined draft nor the file, session or machine-screen issues is a prerequisite.

## Scope

Provide the project-bound workflow launcher, retained guide/structure tab and compact Runs list with Live, Needs you, Ended and All filters, revealed search, factual summaries, elapsed time, cost and session count.

Present an agent's turn as chat with collapsed tools and factual details on demand: run, scope, provider/host, checkout, turn, usage, context, structured output and prior steers. Arrow/Return steers an active turn. Whole-run cancellation belongs on the run row/header and requires confirmation; agent focus has no stop or cancel action.

Preserve existing maps, attention, recorded history and observation reconnection. Session setup, machine provisioning, recording presentation and Promises contents are outside this issue. #562 records related remaining native observation gaps; use relevant evidence to address overlap without opening a general validation project.

## Architectural guidance and defects in the reference

- Reuse the existing workflow registry, launch path and run inventory. The launcher owns its form and errors; the workspace owns retained tab identity. Launching or reading a guide does not require another runtime or separate inventory.
- The reference has a confirmed live-rendering regression: projection data mutates while retaining object identity, so agent focus can keep showing an old transcript even as the working line advances. Carry observation changes through message and tool rendering, including updates within existing messages.
- The simplified chat renderer drops provider retry causes and message-level errors that the previous full activity view exposed. Preserve access to those diagnostics, shell/compaction records and other recorded facts while simplifying their presentation.
- Retained views own their portaled UI. The new row cancellation confirmation remains visible after its Runs container is hidden; active-view ownership must cover the launcher, row menus and cancellation dialog.
- Steering must preserve the running session's identity even when the observer is reading an older turn. Unsupported routes and ended/between-turn states need an explanation rather than a misleading active composer.

## Completeness criteria

- [ ] A real inexpensive-model workflow launches in the selected project, opens its run in a retained tab, and appears in the same inventory used for chat-launched runs. The guide and structure remain inspectable without losing the run or launch draft.
- [ ] Runs exposes the four filters and revealed search, truthful summaries and attention, distinct completed/failed/canceled outcomes, elapsed time, session count and cost. A nonzero charge never appears as free. Maps and run details remain available.
- [ ] While agent focus remains open, new messages, text deltas and tool progress/results visibly arrive without reopening or switching the view. Reading earlier activity remains possible without live updates repeatedly moving the reader away.
- [ ] Provider retries and their named causes, message errors and existing activity records remain accessible. A controlled retry/backoff case shows its cause while the turn is still active; completed turns retain their prompt/context, output and usage.
- [ ] Arrow and Return deliver a steer to the running session and show whether it landed or was dropped, including while an earlier turn is selected. The composer explains unavailable steering for unsupported routes, between turns and ended runs. Agent focus exposes no stop/cancel control.
- [ ] Run-row/header cancellation confirms the whole-run consequence, cancels only the chosen run and lets the authoritative run record determine the outcome. Switching away through native tab/menu navigation removes that view's launcher, row menu and cancellation dialog; returning does not revive a stale confirmation.
- [ ] A waiting human question remains attached to the correct run across tab changes and can be answered there. Observation disconnect/reconnect retains run identity and reports the observation gap without inventing execution failure or starting replacement work. The changed views remain usable at default and minimum native window sizes.

Completion evidence must name the final Gimbal revision and demonstrate the live transitions above in the native app. Include incremental-event and inactive-view regression coverage; the earlier 177 passing frontend tests missed both. A populated screenshot or a successful steer alone does not establish live transcript correctness. This issue can be accepted independently of the other split issues.
