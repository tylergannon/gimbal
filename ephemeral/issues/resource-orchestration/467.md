Provide consumer-relative named-service bindings through runtime orchestration

https://github.com/tylergannon/gimbal/issues/467

## Goal

Depends on explicit runtime construction in #466 and the messaging foundation repairs #462, #463, #464, #465. This is the concrete consumer that should settle the smallest useful orchestration interface.

An unchanged workflow can use a named service from a different network environment because the runtime's orchestration dependency makes it usable by the actual consumer and delivers the needed binding there.

The PR #461 service specimen deliberately used local placement and a shared-workdir address file. Returning a URL or environment map to workflow Go alone does not establish access for an agent or command executing elsewhere. HTTP can route agents and processes to different producers, so one task-route label does not necessarily identify the consumer. Source: [service specimen](https://github.com/tylergannon/gimbal/blob/5d0466cd744173011f8f266417068af0cce55e48/internal/workflows/servicecheck/servicecheck.go), [execution carriers](https://github.com/tylergannon/gimbal/blob/5d0466cd744173011f8f266417068af0cce55e48/backend/backend.go), [HTTP routing](https://github.com/tylergannon/gimbal/blob/5d0466cd744173011f8f266417068af0cce55e48/plugins/messaging-http/main.go).

## Desired state

The runtime identifies the named service, owning scope, and logical consumer. The implementation determines location, connectivity, and the declared readiness condition. The resulting address and/or non-secret bindings reach the actual supported executor in the form it needs. Workflow code does not learn hosts, containers, queues, or concrete resource implementations.

Process launch, service readiness, and consumer access have distinct meanings. Acquisition and release have explicit ownership; relinquishing one scope's use must not indiscriminately stop shared infrastructure or another scope's work. State the availability/loss behavior supported by this first service contract without inventing broader guarantees. UI exposure is limited to truthful resource-use observations, not implementation handles.

## Proof

- Run one real workflow with service and consumer in distinct network environments. The actual consumer obtains a response using the supplied binding; merely returning or displaying an address is insufficient.
- Change external placement/configuration while retaining workflow source and demonstrate consumer-relative access again. Do not depend on a shared-workdir file to convey the address.
- Observe scoped release and confirm unrelated/shared use is preserved. Failure to establish the declared readiness or access does not appear as successful acquisition.

Derive the smallest interface and binding carrier from this consumer. No secret-claim syntax, steering, general infrastructure configuration language, or replacement of Go workflow control flow is requested.
