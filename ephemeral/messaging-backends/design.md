# Runtime-loaded messaging backends: bounded implementation design

Earlier proposals and the rejected plugin worktree are not implementation requirements or source to transplant.

## Desired state

A normally launched Gimbal workflow sends its action requests and receives authoritative action results through a selected, runtime-loaded messaging plugin. Three real implementations work: filesystem requests/events; River requests with Postgres events; HTTP requests with SSE fan-in from multiple producer endpoints. The ordinary Go workflow and native provider adapters are identical for all three. No orchestration, placement, discovery, Docker lifecycle, or steering contract is added.

Use the existing native `Register(*gimbal.Registry) error` plugin loader and `--task-route` selection. Register a separate narrow messaging definition; do not make a messaging plugin implement today's broad `backend.Execution` interface. Its registered definition supplies the caller connection and a worker entry function. The existing wide backend remains for its existing features; no compatibility adapter implements it using messages. The new path must be wired into normal runtime entrypoints, not a demonstration-only runner.

## Contract

The caller/producer connection has only publishing a request, listening for selected events since a starting point, and publishing an event. Connection cancellation releases subscriptions and owned connection resources, not work. A plugin worker entry accepts a handler for received requests; request acquisition/acknowledgment and concrete serving mechanics belong to each transport. It is not a machine or workflow scheduler interface.

A request has its own ULID, creation time, run/scope/logical-action attribution, independent persistent session identity when relevant, and a typed action payload. Reuse the existing session/turn/process/scope DTO meanings rather than inventing a universal resource model. A turn includes prompt, JSON schema, and session identity. Output crosses as bytes plus executor-owned outcome/usage, preserving malformed bytes and invalid-output classification. Core request payloads contain no network or machine routing fields. Backend configuration uses hardwired local paths, queue names, and URLs.

An event has identity, request and owner attribution, optional session identity, kind, and payload. The minimal facts are request accepted/started, native agent activity, service established, and authoritative completion (including command exit code/stdout/stderr or turn bytes/usage/error). Completion is produced from the native executor result, not inferred from diagnostic activity. Completing a turn never closes its session. Core requests needed for existing scope ownership include session creation/close, turn, process/service, interrupt, and scope cleanup; no steering implementation. Session fork can be reported unsupported in the new messaging path unless a selected existing workflow actually requires it.

Listening includes retained matching events emitted from the request's creation through live delivery, even if the request finishes before listening starts. A selection can target a request or a run; an empty selection may observe the configured backend. ULID lexicographic order alone is not the catch-up proof: same-millisecond events and late producer arrivals must not be skipped. Event IDs make duplicates recognizable. A listener's disconnect or slowness cannot consume events for other listeners or close an executor/session/service. Required output is carried with completion; no separate Result polling or artifact-acknowledgment handshake is introduced in the messaging path.

Supported lifetime is this explicitly running local worker deployment with retained stores left intact. Filesystem/HTTP events remain until the configured directory is removed, Postgres events until the deployment database is removed. Restarting an executor does not resume native sessions. Automatic ambiguous execution retry is excluded: keep a request's identity, avoid duplicate execution during the supported worker lifetime, and surface errors/uncertainty. River's delivery/retry settings must not replay a native turn blindly after a worker crash. These are declared limits, not an invitation to implement a reliability framework. Native adapters retain their existing cancellation and recovery behavior.

## Application integration

1. Extend the registry with messaging definitions and let its existing task-route resolution return a connection containing the narrow messaging transport. Existing plugin loading, CLI route files, runner identity, and normal `gimbal run` startup remain the application entrypoint. The workflow-route resolution does not accept a messaging-only definition as an orchestration backend.
2. Add request-and-await helpers under `internal/effects`, with explicit request handles carrying ID/time into the waiter. Do not conceal a mutable task-to-request lookup table behind old `Call`/`Wait` APIs. Branch existing action forwarding at `internal/taskdaemon/client.go` for sessions/turns, and at `remote_execution.go`/`service.go` for commands/services. `internal/invocation` selects the forwarding adapter when a messaging connection exists. `Generate[T]` and native adapters are unchanged.
3. Add the narrow request consumer to the existing task daemon. Reuse its native session/process ownership and cleanup. Publish native activity and completion at the places where the daemon already receives them; do not poll the old HTTP backend or build a second native executor. Service establishment permits `Service()` to return while its lifetime waiter continues until cleanup/completion. Command completion includes captured bytes before returning. Shared localhost filesystem paths suffice for workflow inputs; no workspace distribution layer.
4. The normal runtime already turns these action results/activity callbacks into run/session records and the existing console projections. Feed those paths directly from the received facts so the same existing UI meanings remain. Keep local workflow lifecycle records (scopes, checks, run completion) as they are. A wider plugin listener can independently see the action facts; this slice does not refactor the UI reducers or claim that every lifecycle record now lives on the bus.
5. Expose a normal CLI worker mode to load the same plugin and call its worker entry with the daemon's request handler. Reuse plugin-dir loading and route configuration rather than introducing a daemon manager. Scope cleanup and ordinary context interruption travel through the same selected messaging transport. Current runner cleanup routing must recognize a messaging connection where it currently checks only `.Execution`; no new recovery supervisor.

## Three delivery implementations

- **Filesystem:** atomic request publication into a configured directory; one explicitly started worker consumes/claims requests there. Retained immutable event records in the paired event directory provide catch-up and live polling. Requests are not consumed by event observers. No file-watcher dependency or generic queue framework is needed.
- **River/Postgres:** a real River client inserts action jobs into a configured queue; a River worker invokes the same daemon request handler. Tags may label run/request identity but never route work. A small plugin-owned Postgres event table retains facts; listeners catch up then continue reading it. Native work executes on the host; one dedicated local Postgres Docker container is sufficient. Keep the container ID in a private local file and remove that exact container after validation. No container data enters the interface.
- **HTTP/SSE:** HTTP publishes requests to explicitly configured producer endpoints. Each producer retains its own events (filesystem storage can be reused) and serves catch-up plus live SSE. The caller connection fans in independent SSE streams from at least two actual producers. Configure one agent producer and one command/service producer, with cleanup broadcast internally to the configured producers. Endpoint mapping belongs solely to this plugin; sessions remain on their configured producer. A producer disconnect must not prevent the other stream from progressing; reconnect resumes retained facts without a gap. Do not replace fan-in with one central polling endpoint and call it SSE.

## Proof that establishes done

Primary common specimen is existing `internal/workflows/servicecheck/servicecheck.go`, unchanged. Launch the actual built application, load each separately built `.so`, select each task route, and run `service-check` with Codex `gpt-5.6-luna` (or Claude Haiku if needed, disclosed consistently). Observe all three full runs: real agent writes `GIMBAL_SERVICE_OK`, real command retrieves it over the real scoped HTTP service, scope exit stops that service, and the final parent command verifies it is unreachable. Capture exact revision, plugin identity, invocation, run ID, model, exit/outcome and concrete observations in chat/PR; private logs stay outside Git. A transport's unit tests or direct envelope round-trip cannot substitute for these runs.

A second uncommitted ordinary Go workflow may demonstrate two sequential turns against the same session plus parallel commands and a join, unchanged across all three transports. This is a scratch live run, not a committed proof program. It establishes independent session/request IDs and nontrivial causal progression beyond the service-check specimen. Have a separate run/request listener observe matching action facts independently; for HTTP, show events originating from both producer URLs in the same run. Observe the normal application run record reaches completion; inspect the normal console for status/activity if making any UI claim.

Focused package tests cover: completion before subscribe, same-millisecond retained events, independent listeners and reconnect, output/error/invalid-result preservation, turn completion without session close, service return before its process exits and cleanup afterward, duplicate request identity in the supported lifetime, and HTTP multi-producer fan-in. Tests sit beside the package being checked, without a generic proof framework. Include real Postgres/River integration tests when configured, and run them during validation.

Run the repository's applicable build/vet/test checks. Build actual matching-toolchain plugins and host; a missing plugin must prevent selecting that transport, proving runtime loading is real. Claude independently inspects the implementation and the live observations and decides whether this definition of done was actually demonstrated. Only material findings against this scope trigger repairs.
