# Diffusion Router integration research for Gimble

Research date: 2026-09-25. Scope: Pi, Codex, OpenCode, and Claude Code; Gemini deliberately excluded. This is a design and compatibility assessment, not an implementation or a claim that a full Router-backed coding turn works today. The portal guide archive, authenticated model ID snapshot, and harness-specific investigations are linked below.

> **Current-code update (2026-09-25):** The provider and protocol probes below remain useful, but their Gimble implementation inventory was taken from commit `39462ce`. This branch is now rebased onto `origin/main` at `81dc3c8`, which has an active root Go application and an implemented OpenCode adapter. Read [CURRENT-CODE.md](CURRENT-CODE.md) before using these notes for implementation. The old references to a missing OpenCode adapter and a five-method contract including `Interrupt`/`Compact` are historical, not current requirements.

## Recommendation

**Build explicit, durable harness profiles, then prototype Pi first for Router open-weight coding turns.** Pi's language-independent RPC controls map closely to Gimble's Go harness contract and its portal configuration parsed on the current release. Continue the requested OpenCode adapter research and keep Codex app-server as the Codex transport; its per-thread `modelProvider` selection removes the configuration-level one-provider constraint. Pi is a plausible replacement for using Codex *with Router*, but that decision needs real Router tool-loop and structured-output results. Treat Claude Code on open-weight models as experimental because Anthropic does not support non-Claude models through gateways, even though Diffusion offers a beta recipe. Do not select a single universal harness for all 22 catalog IDs: the catalog contains model names associated with embedding, reranking, vision, and image tasks as well as text models, but supplies no coding capability attestations.

The first Pi and OpenCode Router baseline can be `deepseek-4.1-flash`, which both portal guides name; OpenCode needs a corrected config. The first Codex baseline should be `glm-5.3-flash`: the [portal's Codex guide](portal/coding/codex.md) reports one successful short Responses reply on CLI 0.155.0-alpha.16.3. That is **not** a coding workflow proof. The guide also reports DeepSeek currently rejecting Codex `input_text` upstream. These are candidate test targets, not quality rankings.

### Pi is the strongest new live-control candidate

Pi is an extensible terminal coding agent with built-in file and shell tools. Its current package is [`@earendil-works/pi-coding-agent`](https://pi.dev/docs/latest/quickstart); the older `@mariozechner` package is deprecated. Pi offers a language-independent `pi --mode rpc` subprocess: JSONL commands for prompt, steer, follow-up, abort, compact, model selection, and session inspection, with streamed message/tool/usage events. For Gimble's Go code, that is a direct adapter surface without embedding a TypeScript SDK. [Pi RPC](https://pi.dev/docs/latest/rpc), [RPC commands](https://pi.dev/docs/latest/rpc-commands).

The [portal's Pi guide](portal/coding/pi.md) uses `<PI_CODING_AGENT_DIR>/models.json` with `api=openai-completions`, `baseUrl=https://router.diffusion.io/v1`, `apiKey=$DIFFUSION_API_KEY`, and a `deepseek-4.1-flash` model entry. Current [Pi model documentation](https://pi.dev/docs/latest/models#configure-a-compatible-endpoint) confirms that shape and environment interpolation. A disposable Pi **0.87.1** probe loaded the exact shape (with a localhost URL and fake key), sent `POST /v1/chat/completions` with Bearer auth and SSE, emitted the expected RPC events, and resumed a persisted conversation in a second process. This is stronger local adapter evidence than a model listing, but it did **not** call Router or prove real tool use. Pi also sends `max_completion_tokens`, `store`, and `stream_options` by default; Router tolerance for those fields is an open gate. [Detailed Pi probe](pi-findings.md).

Prototype one supervised RPC child **per active Gimble session**, with `PI_CODING_AGENT_DIR` and `--session-dir` scoped to a managed profile. `--session-id` supports native session creation and cross-process resume. Map `RunTurn` to `prompt` acceptance plus events through `agent_settled` (not merely `agent_end`); `Steer` to queued `steer`; `Interrupt` to `clear_queue` then `abort`; and `Compact` to `compact`. This fits the preserved contract more directly than an OpenCode `run` subprocess. Pi's steering is delivered between model calls after pending tool calls, so it is not an immediate interruption. [Pi RPC lifecycle](https://pi.dev/docs/latest/rpc#run-lifecycle), [commands](https://pi.dev/docs/latest/rpc-commands).

Pi has **no documented core `outputSchema` parameter** for RPC prompts. Gimble can require JSON, validate with its existing result validator, and do bounded repair retries, but first-pass strictness will differ from Codex app-server's native schema support. The portal's minimal Pi model entry also silently defaults to `reasoning=false`, text-only input, 128K context, 16,384 output tokens, and zero cost in the tested build; these values are Pi defaults, not verified Router model facts. Fill them from reliable model data or measured behavior before relying on compaction, cost, or effort choices. Pi tools inherit the child process's OS permissions; configure that boundary deliberately. [Pi findings](pi-findings.md), [Pi security](https://pi.dev/docs/latest/security).

### The Codex process/profile question

The preserved [`harness/codex/adapter.go`](../../../legacy/harness/codex/adapter.go) explicitly starts `codex app-server --stdio` for a new thread and uses a **fresh process for later turns**, resuming the durable thread. It does not currently use one global app-server. It sends `model` but no `modelProvider` on `thread/start`, and it sends neither provider nor model on `thread/resume`. The neutral [`HarnessAdapter`](../../../legacy/harness/contract.go) has no profile identity. Thus the missing capability is provider selection and persistence, regardless of the chosen process topology.

The locally generated Codex **0.147** app-server schema exposes `modelProvider` on `thread/start`, `thread/resume`, and `thread/fork`. `turn/start` can set `model` and effort but cannot switch provider. [Official OpenAI documentation](https://learn.chatgpt.com/docs/app-server) explains how to generate the schema for the exact installed CLI version; Gimble should regenerate it for the version it deploys. A local 0.147 probe with disposable config confirmed that **one app-server accepted threads for two registered custom providers** and that a turn sent a Responses request to the selected mock endpoint. This proves the routing seam; simultaneous real Router turns and complete model output remain untested. Register the [portal's custom provider](portal/coding/codex.md) with `base_url=https://router.diffusion.io/v1`, `wire_api=responses`, `env_key=DIFFUSION_API_KEY`, `supports_websockets=false`, then set the provider explicitly per thread. [Codex custom-provider documentation](https://learn.chatgpt.com/docs/config-file/config-advanced#custom-model-providers) supports that configuration.

**Keep app-server first.** It already gives Gimble native thread/turn events, steer, interrupt, compaction, and schema handling. A persistent process can reduce startup cost after concurrency and lifecycle testing; the current per-turn process gives crash isolation and matches existing code. Start another process or `CODEX_HOME` when credentials, effective configuration, or trust boundaries require isolation, not merely because two threads use different registered models. A global CLI `--profile` and the portal's Desktop default-setting instructions address those launch surfaces; they are not required to select a provider for each app-server thread. The [official Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode) makes `codex exec --json` with `exec resume` a viable batch fallback, but it has no documented equivalent of active app-server `turn/steer`; benchmark it only if app-server compatibility or operating cost warrants the trade.

### OpenCode remains a distinct new adapter

The portal's [OpenCode guide](portal/coding/opencode.md) combines v1 `provider` with v2 `providers` in one JSON object. Installed OpenCode **1.2.27 rejects** that exact object with `Unrecognized key: "providers"`. The corrected v1 shape in [OpenCode findings](opencode-findings.md) puts `npm`, `options`, and `models` together under singular `provider.diffusion`; `opencode models diffusion` then lists `diffusion/deepseek-4.1-flash` with a dummy key. Current [OpenCode provider docs](https://opencode.ai/docs/providers/) explain the v1 OpenAI-compatible provider. The separate [v2 migration guide](https://opencode.ai/v2/docs/migrate-v1) changes these keys again; Gimble must detect or pin the installed major version and emit one schema only.

The fastest useful turn path is `opencode run --format json --model diffusion/<model-id> --dir <workdir>`, then `--session <id>` on continuation. A local mock proved newline-delimited events, a stable session ID across two invocations, and `/v1/chat/completions` requests. Gimble must add `harness/opencode`, capture the native session ID when the first CLI turn starts, supervise cancellation and process exit, map events without losing unknown types, and validate results. The current neutral contract creates a session **before** a turn, so either return a local pending ID and bind it to OpenCode's native ID, or use the [OpenCode server API](https://opencode.ai/docs/server/) to create native sessions eagerly. CLI `run` does not document an output-schema flag; exact JSON output may require Gimble validation/retry or the server/SDK structured-output route.

An `opencode serve` process and HTTP/SSE adapter can later reduce repeated plugin/MCP startup and supply explicit session creation, prompt, event, abort, and summarize operations. Scope a server pool by configuration and credential profile because its environment is fixed at process start. `OPENCODE_CONFIG_CONTENT` can inject the provider per CLI child without changing global files, but OpenCode merges other user/project settings; it is not complete isolation. Decide whether those settings should remain visible to a Gimbal run, and test an isolated XDG home if they should not. [OpenCode CLI](https://opencode.ai/docs/cli/), [server API](https://opencode.ai/docs/server/), [configuration](https://opencode.ai/docs/config/).

### Claude Code is a qualified experiment

The preserved Claude adapter already launches the CLI through a Go SDK **per turn**. Its missing pieces are a Router endpoint/token/config profile passed to that subprocess, a profile bound to the persisted session ID, and explicit routing for non-`claude-` model IDs. The [portal's beta recipe](portal/coding/claude-code.md) uses `ANTHROPIC_BASE_URL=https://router.diffusion.io`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_MODEL=deepseek-4.1-flash`, a Haiku fallback, and gateway model discovery. The SDK environment option overlays the parent environment, so Gimble must filter inherited provider variables before launching another profile. A direct `claude -p` JSON stream is an alternative only if the SDK cannot deliver the needed isolation or controls.

[Anthropic's gateway overview](https://code.claude.com/docs/en/llm-gateway) expressly says non-Claude models through gateways are unsupported. That does not erase Diffusion's beta guide, but it means a passing smoke prompt can never establish upstream support. The [Claude gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol) also includes streaming, tool use, beta fields, and model-discovery expectations that must be tested with the exact Router/model combination. Prioritize Pi, Codex, and OpenCode for open-weight qualification and expose Claude/Router only after explicit, version-pinned proof and an experimental label.

## Gimble changes common to all four

1. Replace model-prefix-only selection with a resolved target that records **harness**, **transport provider**, **native model ID**, **profile ID**, and optional model-specific settings. `glm-5.3-flash` is a Router model ID, not enough information to choose Pi versus Codex versus OpenCode or a credential. The preserved [`modelalias`](../../../legacy/internal/modelalias/modelalias.go) recognizes only `claude-`, `gemini-`, and OpenAI model prefixes and rejects Router IDs; [`program.NewRuntime`](../../../legacy/program/runtime.go) constructs neither Pi nor OpenCode adapter.
2. Give each created session an immutable profile binding. Persist the profile ID and native session ID with the workspace and harness. On follow-up/resume, reject a mismatched profile rather than silently sending prior context to a different provider or credential. Keep credential **references** in metadata and actual keys out of logs and tracked config. A model change within one provider may be possible; a provider change needs a new session or a tested fork/resume flow.
3. Resolve process environment per profile. Pi needs an isolated agent directory, session directory, Router key and model metadata. Codex needs a registered provider and key reachable by its app-server child. OpenCode needs version-correct provider config and key in its child/server. Claude needs its gateway variables with incompatible inherited variables removed. A shell export may not reach a desktop-launched Gimble process. Record the target CLI version, effective non-secret config, profile ID, and actual response route for each proof run.
4. Make features conditional by harness/model. The current contract's `Steer`, `Interrupt`, `Compact`, `OutputSchema`, and `ReasoningEffort` should not be promised merely because a model ID appears in the catalog. Pi exposes live RPC controls but lacks native schema output; Codex has native RPCs and schema handling; OpenCode CLI may need server mode for some controls; Claude compatibility is model sensitive. Omit unsupported effort/variant values rather than forcing the preserved default `high` onto every open-weight model.
5. Keep the existing Gimble event/operation log model, but record actual harness, provider, model ID, session ID, profile ID, and capability result so later research can distinguish a selected model from a successful tool cycle. Mask keys and authorization headers.

A plausible neutral shape is `SessionTarget{Harness, Provider, ModelID, ProfileID, CredentialRef}` resolved before `CreateSession`; `RunTurn` then carries the session ID and turn-level options. This is a design sketch, not a proposed final Go API. It avoids changing endpoints or credentials on an active session.

## How to prove readiness

Use a disposable project and a specifically scoped Router key. For **each** candidate harness/model/version profile, record the following gates, the raw sanitized event trace, and the Router usage entry showing the actual model:

| Gate | Required observation |
| --- | --- |
| Configuration | The native CLI loads the intended provider/profile and identifies the requested model; an invalid key fails without fallback. |
| One turn | Text response from the real Router, with a completed stream and final usage. |
| Coding loop | Agent reads a file, edits it, runs a shell command, and returns a result; tool-call IDs/arguments/results remain paired. |
| Durability | Second prompt resumes the same native session after its original child process exits; workspace and provider are unchanged. |
| Controls | Stream events, cancel/interrupt, mid-turn steer where promised, compaction, and exact JSON schema output each pass or are explicitly unavailable. |
| Isolation | First-party and Router sessions run concurrently with no cross-routing, key leakage, or history mix-up. |
| Limits and cost | Long-context behavior, model metadata fallback, rate-limit handling, startup latency, and auxiliary model calls are measured. |

Order the work: **(1)** pin/test harness versions, correct the OpenCode config, and verify Pi's model metadata; **(2)** implement profile identity and routing; **(3)** prototype Pi RPC against one Router model and exact schema output; **(4)** qualify Codex app-server and OpenCode CLI against Router on one model each, then compare quality and latency on the same coding tasks; **(5)** choose persistent process policy from concurrency and startup data; **(6)** run Claude compatibility as a separate experiment. The first production claim should be scoped to the exact harness, CLI version, Router model, and passed capability gates.
