# Claude Code with Diffusion Router: harness research

Research date: 2026-09-25. Scope: Claude Code's current gateway and programmatic interfaces, Diffusion Router's portal guide, and Gimble's existing Claude adapter. This note has **not** verified a live Diffusion Router endpoint or run a paid model request. The portal guide supplies setup claims; runtime compatibility remains to be tested.

## Decision in brief

**Treat open-weight models in Claude Code as an experimental compatibility path, not a supported product path.** Anthropic's current gateway overview says any gateway exposing a supported API format works, but explicitly says it *does not support routing Claude Code to non-Claude models through any gateway*. Its compatibility guide says `ANTHROPIC_BASE_URL` makes Claude Code treat a gateway as the Claude API and send current Claude-specific request fields, including adaptive reasoning, effort and context management even for unrecognized model IDs. An Anthropic-compatible router may translate enough of this to make some open-weight models run, but a successful one-line completion does not prove tool use, continuation, compaction or structured output. [Gateway overview](https://code.claude.com/docs/en/llm-gateway) [Gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol)

This does not prevent using Diffusion Router for **Claude models** through Claude Code, provided the router serves a compatible Anthropic Messages endpoint. Open-weight models may be a better fit for a harness that officially accepts OpenAI-compatible providers; that is a cross-harness architecture decision.

## Diffusion Router portal guide (reviewed 2026-09-20)

The downloaded `portal/coding/claude-code.json` explicitly labels Claude Code **beta** and gives a concrete path for a non-Claude model. It sets `ANTHROPIC_BASE_URL=https://router.diffusion.io`, `ANTHROPIC_AUTH_TOKEN` to the Diffusion key, `ANTHROPIC_MODEL=deepseek-4.1-flash`, `ANTHROPIC_DEFAULT_HAIKU_MODEL=deepseek-4.1-flash`, and `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`. It says bearer auth avoids subscription-login precedence and that non-Claude IDs need explicit selection because Claude Code's native picker filters them. It claims the Messages surface is used end to end, and asks users to verify with a prompt. Its troubleshooting specifically calls for checking `/v1/messages?beta=true` and `/v1/models?limit=1000` on HTTP 400; it warns **not to invent `behavesAs` mappings or context-window overrides** in response to nonblocking unknown-model/Advisor warnings. These are router-authored claims and instructions, not proof that every Claude Code feature works with the listed model.

This reconciles the apparent contradiction: the router **offers** a beta compatibility integration, while Anthropic **does not support** non-Claude models in Claude Code behind any gateway. Gimble can investigate and conditionally expose it, but cannot treat router setup documentation as an Anthropic support promise.

[CLI reference](https://code.claude.com/docs/en/cli-reference) [Headless guide](https://code.claude.com/docs/en/headless) [Environment variables](https://code.claude.com/docs/en/env-vars) |

The official CLI guide documents `claude -p ... --output-format stream-json --verbose --include-partial-messages` for real-time tokens, final `result` metadata, and `--resume` with an ID for multiple concurrent conversations. `--forward-subagent-text` exposes subagent text and thinking in the stream. These are possible alternatives if the pinned Go SDK cannot be extended cleanly; they are **not required to solve process isolation** because that SDK already launches a CLI subprocess per turn. [Headless guide](https://code.claude.com/docs/en/headless) [CLI reference](https://code.claude.com/docs/en/cli-reference)

The machine's Claude CLI was `2.1.246` on the research date. Current online docs mention features gated at later versions, including some model/context and permission controls, so CLI upgrade and version-pinned integration tests are necessary before relying on those settings. No model call was made.

## Gimble's current code

- `ephemeral/legacy/harness/claude/adapter.go:51-53,115-165` launches a native Claude session for **each turn**, serialized only per session. `CreateSession` mints a UUID; a fresh turn uses `--session-id`, following turns use resume. `native.go:21-56` sets cwd, model, effort, schema, and native session flags through the pinned `github.com/roasbeef/claude-agent-sdk-go` SDK. Thus Claude already has per-turn processes, unlike the Codex app-server concern.
- `adapter.go:306-324` currently injects only `GIMBLE_RUN_DIR` and `GIMBLE_SERVICE_PORT`. It has no router endpoint, credential, config directory or profile in `nativeConfig` or durable `sessionState`. `native.go:29-31` does call SDK `WithEnv`, so adding a per-turn provider environment is a small adapter seam. The pinned SDK's local `transport.go:399-413` starts with `os.Environ()` and overlays `WithEnv`; it also has a ConfigDir option. That makes parent-process inherited credentials a real isolation hazard. In particular, `WithEnv` is an overlay, not a clean environment constructor: an Anthropic-profile turn could inherit router variables (or the reverse) unless Gimble launches with a filtered base environment or verifies safe unset semantics.
- `ephemeral/legacy/internal/modelalias/modelalias.go:62-66,183-194` routes based on native model prefix: only `claude-` maps to the Claude harness; arbitrary Diffusion Router model IDs fail provider resolution. Provider, harness, and model ID need separate metadata rather than prefix inference if router models are first-class.
- `adapter.go:92-108,326-337` stores only UUID/workdir/fresh state, while Claude history is on disk in the selected config dir. A resumed router session needs an immutable provider/profile association and config dir; swapping profiles under the same session ID could resume against the wrong transcript, endpoint, or key. This is an architectural inference from the code and `CLAUDE_CONFIG_DIR` documentation, not an observed failure.

## Minimum useful prototype

1. Start with the portal's exact beta setup and confirm the advertised `https://router.diffusion.io` Anthropic Messages route, bearer token, `deepseek-4.1-flash`, `/v1/models?limit=1000`, model limits, streamed tool blocks and `--json-schema`-style structured outputs. Do not put actual keys in artifacts. Do not fabricate `behavesAs` mappings or context overrides; apply a window setting only if the router's catalog or live failure proves a specific mismatch.
2. Add a private per-run provider profile object containing endpoint, credential reference, model ID, optional config dir, context/window and feature flags. Route the selected model to a harness explicitly. Bind a session to its profile; reject profile changes on resume. Pass endpoint/auth/config only to that Claude subprocess. Avoid writing secrets to `settings.json`, run logs or event JSON.
3. Run a bounded live matrix with a sandbox project: (a) one text result, (b) read + write + shell tool cycle, (c) streamed assistant/tool/result events, (d) JSON schema result, (e) second turn via resume after process exit, (f) simultaneous sessions on router and first-party profiles, (g) cancel/interrupt, (h) compaction near the router limit. Check router-side model and usage records so a request cannot silently fall back to Anthropic.
4. Decide whether Claude Code earns a supported Gimbal route for those specific router models based on this matrix. If it fails, retain Claude for Claude models and use another harness for the open-weight models. Because Anthropic disclaims non-Claude routing, even a passing matrix should be marked version-sensitive and rerun on CLI upgrades.

## Source boundaries

Anthropic documents the Claude Code CLI/Agent SDK and gateway protocol, but not Diffusion Router's compatibility or any open-weight model's suitability. The linked pages are primary sources for Claude behavior. `ephemeral/projects/gimble/diffusion-router-research/portal/coding/claude-code.json` is the downloaded router portal source for the beta setup; its claims still need live proof. Local code paths are repository evidence; the Go SDK package is a third-party dependency pinned by this repository, not Anthropic's maintained Go SDK.
