# Pi harness and Diffusion Router: integration findings

Research date: 2026-09-25. Scope: the proposed Pi adapter for Gimbal's preserved Go `HarnessAdapter` contract. The current npm release tested was **`@earendil-works/pi-coding-agent` 0.87.1** in a disposable `/tmp` directory. The old `@mariozechner/pi-coding-agent` package is deprecated at 0.73.1; current [Pi installation docs](https://pi.dev/docs/latest/quickstart) use the new scope. No real Diffusion key, user Pi configuration, or Router inference was used. The local probe used a fake key and a localhost Chat Completions server. [Current package](https://www.npmjs.com/package/@earendil-works/pi-coding-agent), [old package](https://www.npmjs.com/package/@mariozechner/pi-coding-agent).

## Recommendation

**Prototype Pi as a new harness adapter, using one supervised `pi --mode rpc` child per active session.** It is a strong fit for Gimbal's provider-neutral contract and an attractive first route for Router open-weight models. Pi gives a native language-independent JSONL RPC protocol for prompt, live steer, abort, manual compact, model changes, durable resume, and ordered message/tool/usage events. Its `models.json` accepts the Portal's OpenAI-compatible provider shape. A separate child process with `PI_CODING_AGENT_DIR` and `--session-dir` gives Gimbal a distinct Router profile without changing the user's personal Codex or Pi setup. [Pi RPC](https://pi.dev/docs/latest/rpc), [RPC commands](https://pi.dev/docs/latest/rpc-commands), [configuration](https://pi.dev/docs/latest/configuration).

**Do not replace Codex or OpenCode yet.** The Portal labels Pi support beta. Current Pi's core RPC prompt has no documented `outputSchema` or forced structured-result option, so Gimbal would have to prompt for JSON and use its own exact schema validator with bounded repair retries. Router's actual Chat Completions streaming, tool-call roundtrip, request-field tolerance, and model metadata remain unverified. Pi's control surface is stronger for Gimbal than the initial OpenCode `run` CLI route, while Codex app-server already has native schema output and can select a provider per thread (see sibling findings). This is a staged adapter recommendation, not a claim of higher model quality or proven Router compatibility. [Portal Pi guide](portal/coding/pi.json), [RPC prompt fields](https://pi.dev/docs/latest/rpc-commands#prompt), [Gimbal contract](../../../legacy/harness/contract.go).

## What Pi is

Pi is an extensible terminal coding agent with built-in `read`, `bash`, `edit`, and `write` tools (additional `grep`, `find`, and `ls` tools are available). It has interactive, one-shot print, JSON event stream, RPC subprocess, and in-process TypeScript SDK modes. Gimbal is Go, so RPC is the natural integration; the SDK would require a separate Node/Bun bridge and would give up the simple subprocess boundary. Pi explicitly recommends RPC for other-language hosts and process isolation. [Overview](https://pi.dev/docs/latest/how-pi-works), [CLI](https://pi.dev/docs/latest/cli), [RPC](https://pi.dev/docs/latest/rpc), [SDK](https://pi.dev/docs/latest/sdk).

The preserved implementation lives under `ephemeral/legacy/`, not an active root Go module. Its `HarnessAdapter` requires `CreateSession`, `RunTurn`, `Steer`, `Interrupt`, and `Compact`; `RunTurn` must return a JSON string for plain text or an object validated exactly against caller JSON Schema. The current runtime only instantiates Codex, Claude, and agy, so Pi requires both an adapter and an explicit model/harness routing path. [Contract](../../../legacy/harness/contract.go), [result validator](../../../legacy/harness/result.go), [runtime](../../../legacy/program/runtime.go).

## Portal configuration and model metadata

The [archived Portal guide](portal/coding/pi.json) says to merge this block into `~/.pi/agent/models.json` (or, for Gimbal isolation, `<PI_CODING_AGENT_DIR>/models.json`):

```json
{
  "providers": {
    "diffusion": {
      "baseUrl": "https://router.diffusion.io/v1",
      "api": "openai-completions",
      "apiKey": "$DIFFUSION_API_KEY",
      "models": [{ "id": "deepseek-4.1-flash" }]
    }
  }
}
```

The current [Pi model guide](https://pi.dev/docs/latest/models#configure-a-compatible-endpoint) confirms `models.json`, `openai-completions`, and `$NAME`/`${NAME}` environment interpolation. `PI_CODING_AGENT_DIR` redirects the agent configuration directory. Keep the literal `$DIFFUSION_API_KEY` reference in the file and inject the actual key only into the child environment; do not pass credentials through a CLI flag or persist them in research material. [Pi configuration](https://pi.dev/docs/latest/configuration), [Pi environment variables](https://pi.dev/docs/latest/environment-variables).

**The minimal model entry is accepted, but its inferred metadata is not a Router specification.** With the exact shape above, a dummy key, and a localhost base URL substituted for the Router URL, Pi 0.87.1 listed `diffusion/deepseek-4.1-flash` and reported `contextWindow=128000`, `maxTokens=16384`, `reasoning=false`, `input=["text"]`, and all costs zero. Those are Pi defaults. The Portal's `crush` guide independently lists 128000 for this model, but that does not verify its output limit, reasoning modes, modalities, or pricing. For each Router model, provide verified context/output limits, reasoning support and accepted thinking levels, image support, and usage cost as needed. The Portal's fresh catalog lists `deepseek-4.1-flash`, `glm-5.3`, and `glm-5.3-flash`, but a catalog ID alone says nothing about agent tool behavior. [Portal catalog snapshot](portal/catalog-2026-09-25.json), [Portal Crush guide](portal/coding/crush.json), [Pi models](https://pi.dev/docs/latest/models).

The guide recommends `pi -p --provider diffusion --model deepseek-4.1-flash ...` as its smoke test. That demonstrates a one-shot answer only. Gimbal should use RPC for live controls and test a complete tool-use turn, restart/resume, compaction, and concurrency against real Router credentials before promoting the adapter. [Portal Pi guide](portal/coding/pi.json), [Pi CLI integration](https://pi.dev/docs/latest/cli-integration).

### Request-shape risk observed locally

The local fake server received `POST /v1/chat/completions` with `Authorization: Bearer mock-only`, `model: deepseek-4.1-flash`, and `stream: true`. Pi also sent `max_completion_tokens`, `store`, and `stream_options` by default. The Portal's Chat Completions example has only `model` and `messages`, so it does not establish that Router accepts these extra fields. A permissive local server did; the real Router was not called. Verify those exact request fields, streaming usage, and tool-call messages against Router. If a field fails, use a verified Pi OpenAI compatibility override or a small provider extension; do not guess compatibility flags. [Portal Chat Completions guide](portal/apis/openai-chat-completions.json), [Pi custom providers](https://pi.dev/docs/latest/custom-provider).

## Adapter mapping to Gimbal's contract

| Gimbal method | Pi 0.87.1 mechanism | Implementation detail / gap |
| --- | --- | --- |
| `CreateSession(model, workdir)` | Mint a Gimbal session ID, launch `pi --mode rpc --session-id <id> --session-dir <managed-dir> --provider diffusion --model <id>` with process cwd=`workdir`; call `get_state` to verify selected model, ID, and session file. | `--session-id` creates the project session if missing and reopens the exact ID later. Scope the Pi agent dir and session dir per desired configuration/credential identity. Preserve ID-to-workdir/provider binding in adapter metadata. [CLI](https://pi.dev/docs/latest/cli#sessions), [RPC `get_state`](https://pi.dev/docs/latest/rpc-commands#get_state). |
| `RunTurn(ctx, input, onEvent)` | Send `prompt` with an `id` and combined ordered text parts; accept response, consume events until `agent_settled`, extract authoritative completed assistant text. | A successful prompt response means accepted, not completed. `agent_end` is insufficient because automatic retry/compaction/queued work may follow; `agent_settled` is the correct idle boundary in current 0.87.1. Subscribe/read before prompting and continuously drain stdout. Handle model errors in `message_end`, process exit, and stderr separately. [RPC lifecycle](https://pi.dev/docs/latest/rpc#run-lifecycle), [event stream](https://pi.dev/docs/latest/json). |
| `Steer(sessionID, parts)` | Send `steer` during an active run. | Pi queues steering after the current assistant response executes its tool calls, before the next model call. It does **not** interrupt the in-flight model request or tool. A command success means queued, not consumed; `queue_update` can show pending state. [RPC steer](https://pi.dev/docs/latest/rpc-commands#steer), [events](https://pi.dev/docs/latest/json). |
| `Interrupt(sessionID)` / context cancel | Send `clear_queue`, then `abort`; if the process fails to settle, terminate the child after a deadline. | Current docs state `abort` waits for idle but can continue queued messages unless cleared first. `abort` command success and `agent_settled` are separate boundaries. This matters for Gimbal's cancellation guarantee. [RPC abort and clear queue](https://pi.dev/docs/latest/rpc-commands#abort). |
| `Compact(sessionID, workdir)` | Send `compact` while the session is idle; await its success response and `compaction_end`. | Compaction invokes a model and may fail or be aborted; only mark complete on success. Pi also has automatic compaction and overflow recovery, so their events should be projected without mistaking them for the end of Gimbal's turn. [RPC compact](https://pi.dev/docs/latest/rpc-commands#compact), [compaction](https://pi.dev/docs/latest/compaction). |
| `ReasoningEffort` | On startup `--thinking <level>` or RPC `set_thinking_level` between turns. | Pi levels include `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, and (current) `max`; availability is model-specific. The minimal Router entry reports `reasoning=false`, so Gimbal's current default `high` must not be passed unconditionally. Query `get_available_thinking_levels` or omit effort until verified. [RPC thinking](https://pi.dev/docs/latest/rpc-commands#set_thinking_level), [model selection](https://pi.dev/docs/latest/models). |
| `OutputSchema` | No native schema parameter in documented core RPC `prompt`/CLI `--print` options. Ask for JSON, parse one object, validate with `harness.ResultValidator`; retry/repair on invalid output within a bounded policy. | This is a material parity gap versus Codex app-server and Claude. Local validation guarantees Gimbal does not **return** invalid objects, but it cannot guarantee the model will produce a valid object on the first call. Investigate a trusted output-tool extension if first-pass strictness is required, but test it with Router tool calls. [RPC prompt fields](https://pi.dev/docs/latest/rpc-commands#prompt), [CLI](https://pi.dev/docs/latest/cli), [Gimbal result validator](../../../legacy/harness/result.go). |

For event projection, use `message_end` for complete user/assistant/tool-result messages; `message_update` for optional live text/thinking deltas; `tool_execution_start`/`end` keyed by `toolCallId`; and assistant `usage`/session stats for cost and token events. Preserve unknown event fields/types because Pi is moving quickly. Distinguish Pi's low-level `turn_start`/`turn_end` (one assistant response plus its tools) from Gimbal's `RunTurn` (entire prompt-to-idle run). [JSON event reference](https://pi.dev/docs/latest/json), [message types](https://pi.dev/docs/latest/message-types).

## Isolation and turn-start choices

| Option | Strength | Cost / limitation |
| --- | --- | --- |
| One `pi --mode rpc` process per live session (recommended prototype) | Full live control, explicit config directory, native persistent session, process crash isolation, no singleton app-server/profile restriction. | One Node process per active session; supervise process and drain streams. Reuse it for several turns or restart by `--session-id` when idle. |
| One `pi --mode json` or `pi -p` process per turn | Simple batch operation and native persisted session via `--session-id`. | No bidirectional RPC control during a turn; cannot faithfully implement live `Steer`; structured output still needs wrapper validation. |
| In-process Pi SDK | Full direct API, avoids subprocess serialization. | Pi SDK is TypeScript/Node/Bun; Gimbal's preserved implementation is Go. Requires a durable bridge/service and its own isolation policy. |

The Pi process itself can select different providers/models per session and `set_model` can switch within a process, but a Gimbal-owned profile should make endpoint, credential source, model catalog, trust/resources, and session storage explicit. `PI_CODING_AGENT_DIR` isolates global Pi settings/auth/models/extensions from the user's personal profile. Project `.pi` resources and `AGENTS.md`/`CLAUDE.md` can still load from the working directory; decide whether that is desired. CLI flags allow disabling extensions, skills, prompt templates, context files, or tools for a controlled job, but those choices affect coding ability and instruction fidelity. Pi tools run with the child process's OS permissions. [Configuration](https://pi.dev/docs/latest/configuration), [CLI resources/tools](https://pi.dev/docs/latest/cli#resources), [security](https://pi.dev/docs/latest/security).

For efficient operation, keep a process alive while turns are active and consider an idle pool or exit/restart policy after measuring startup time and memory. Pi's session file is durable and append-only, with active branches and compaction entries. `get_entries` supports stable entry-ID cursors; this could help Gimbal reconcile events after a process restart. Do not open the same native session concurrently from two Pi processes; enforce Gimbal's one-live-turn-per-session invariant. [Sessions](https://pi.dev/docs/latest/sessions), [session format](https://pi.dev/docs/latest/session-format), [RPC `get_entries`](https://pi.dev/docs/latest/rpc-commands#get_entries).

## Local no-key probe (reproducible evidence)

`npm view` showed the current package as 0.87.1; the package was installed under `/tmp/gimble-pi-current`, and `node .../dist/cli.js --version` returned `0.87.1`. In `/tmp/gimble-pi-probe-agent/models.json`, I used the Portal block with only the base URL changed to `http://127.0.0.1:8765/v1`. `PI_CODING_AGENT_DIR=/tmp/gimble-pi-probe-agent`, `PI_OFFLINE=1`, and `DIFFUSION_API_KEY=mock-only` kept the probe away from the user profile and real Router. `--list-models deepseek-4.1-flash` displayed the model and default metadata above.

A localhost SSE fake replied to two prompts. The first RPC process launched with `--mode rpc --session-id gimble-probe --session-dir /tmp/gimble-pi-probe-sessions --provider diffusion --model deepseek-4.1-flash --no-tools --no-extensions`. It returned `get_state`, `prompt` acceptance, ordered `agent_start`/`turn_start`/`message_*`/`turn_end`/`agent_end`/`agent_settled`, and `get_state` with `messageCount=3`. A **new** Pi process launched with the same session ID and directory, reported the same session file and `messageCount=3`, and sent a second request containing four model messages instead of the first request's two. That proves local config parsing, bearer-key interpolation, Chat Completions request construction, event framing, and cross-process resume. It does **not** prove Router inference, real model tool use, schema-valid output, steering, interruption, compaction, or performance. The probe script is disposable at `/tmp/gimble-pi-probe.py` and not part of Gimbal.

## Next live qualification gates

1. Use a test Diffusion key in a Gimbal-owned Pi profile; query `/v1/models` and record actual model metadata/capabilities. Avoid publishing the key or bearer header.
2. For each candidate open-weight model, run Pi RPC through Router on a coding task that reads, shells, edits, and writes. Check streamed tool-call IDs/arguments, tool results, error handling, and usage. Probe whether Router accepts `store`, `stream_options`, `max_completion_tokens`, and repeated tool messages.
3. On one session, verify follow-up in the same process, resume in a new process, live steer, queued steer then clear+abort, manual/automatic compaction, cancellation, and event reconciliation. Run independent sessions concurrently under one managed config and under different profiles.
4. Compare model output quality and latency on the same tasks across Pi, Codex, and OpenCode. Specifically evaluate Gimbal's exact JSON Schema contract: first-pass validity, repair attempts, and failure reporting. Retain Codex for tasks where native schema enforcement or its agent behavior wins.
5. Pin the Pi package version during adapter implementation and test against its exact RPC/event protocol. The deprecated 0.73.1 release and current 0.87.1 differ materially: current events include `agent_settled`, and current CLI has `--session-id`. Treat online `latest` docs as version-specific, not proof of behavior for an older installed binary.
