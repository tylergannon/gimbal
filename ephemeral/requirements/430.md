A lost Codex app-server connection should not terminate a productive multi-stage implementation run and leave the operator to reconstruct it outside Gimbal. That is what happened here: stage 1 was accepted, stage 2 had useful edits and passing focused checks, then one connection failure ended the whole run before stage-2 validation.

## Observed failure

On **2026-10-07 at 09:35:38 America/Los_Angeles**, hosted `implement` run `01M4BEVDFPKAFQVA53PKN3X3H0.implement` failed at:

```
outcome.2/implementation.1/task.1/coding.1
```

Planning/coding used `gpt-6.1-sol:high`; independent validation used `claude-opus-5-5`. This was a six-outcome SKGo implementation with `--max-tasks-per-outcome 5`.

The saved terminal error starts:

```
outcome 2: gimbal: outcome.2/implementation.1/task.1/coding.1:
codex: app-server connection closed:
failed to get reader: failed to read frame header: EOF
```

Cleanup then appended errors for both owned Codex threads:

```
gimbal: close: ... codex: archive thread <thread-id>:
codex: app-server daemon version: exit status 1:
Error: failed to connect to ~/.codex/app-server-control/app-server-control.sock
Caused by:
    Connection refused (os error 61)
```

The worker was still producing tool activity at 09:35:36, two seconds before termination. The persisted session list contains no stage-2 QA session and no later outcomes. The worktree edits survived, but completing the task required manually handing them to a new agent outside the workflow. Stage 1 had already received a passing independent assessment.

Evidence is retained in the SKGo task worktree under `.gimbal/runs/01M4BEVDFPKAFQVA53PKN3X3H0.implement/` (`run.json`, `turns.json`, `sessions.json`, scope records, and the stage-2 coding JSONL), plus `ephemeral/tmp/request-event-gimbal-server.log`. The excerpts above make the failure visible without requiring access to local files.

**Unknown:** what caused the daemon/control service to disappear. EOF plus connection refusal establish lost transport and unavailable cleanup, not the daemon's underlying crash/restart cause. No failure was injected into the shared daemon during this investigation.

## Why the existing reconnect support does not cover this

The installed binary inspected reports revision `4377acbc7581bc8a20551eb0dde7f7276ba1fc61`, with `vcs.modified=true`. The relevant local source files are unchanged from that revision.

- [connection/resumeThreads](https://github.com/tylergannon/gimbal/blob/4377acbc7581bc8a20551eb0dde7f7276ba1fc61/codex/codex.go#L82-L150) redials a dead connection and resubscribes known threads **when another caller enters that path**.
- [RunTurn](https://github.com/tylergannon/gimbal/blob/4377acbc7581bc8a20551eb0dde7f7276ba1fc61/codex/codex.go#L295-L309) returns a read error from the active turn and clears its active-turn reference. It does not reconnect/reconcile that interrupted turn.
- [The implementation workflow](https://github.com/tylergannon/gimbal/blob/4377acbc7581bc8a20551eb0dde7f7276ba1fc61/internal/workflows/implementation/implementation.go#L105-L147) treats the Generate error as terminal, breaking before validation. The five-task bound does not provide a transport-recovery attempt.
- [Close](https://github.com/tylergannon/gimbal/blob/4377acbc7581bc8a20551eb0dde7f7276ba1fc61/codex/codex.go#L424-L449) deletes local session ownership before attempting remote archive. Failed cleanup therefore also complicates recovery/control; #422 covers that related defect.
- [The live reconnect test](https://github.com/tylergannon/gimbal/blob/4377acbc7581bc8a20551eb0dde7f7276ba1fc61/codex/daemon_live_test.go#L21-L104) closes the socket **between completed turns**, then starts another turn. It does not prove recovery from a disconnect during tool execution or while awaiting completion.

## Required behavior

Recover a temporary connection loss with bounded, observable attempts while preserving the current outcome, task, worktree and native-session identity. Reconcile what the remote worker actually did before continuing: losing the response does not mean the last operation never happened. Do not blindly replay edits, start a duplicate worker, or rerun accepted outcomes.

When the service returns, continue the interrupted task and reach independent validation. If safe automatic continuation is impossible, retain an explicit recoverable state and a supported resume action for that same run, with an actionable explanation. A persistent outage must not retry forever. Explicit cancellation must remain cancellation, with ownership/control retained until remote cessation is verified. Cleanup errors must not obscure the original cause.

## Evidence that would demonstrate the fix

Use an isolated/fake daemon to disconnect **during an active turn after a known tool effect**, then restore service. Demonstrate preserved edits, no duplicate tool effect or concurrent replacement worker, one validation of the completed task, and advancement to the next outcome without replaying the accepted first outcome. Cover a surviving remote turn, a daemon restart with durable thread history, disconnect after remote completion but before local receipt, persistent unavailability, and cancellation during recovery. Keep the existing between-turn reconnect test too.
