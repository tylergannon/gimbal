# Bug 317: decision notes

Investigated 2026-09-20 against Claude Code 2.1.270 and the Go SDK version
pinned by this checkout. Live probes used claude-haiku-4-5-20251001. No
application code was changed. The original incident used Opus 5; its local
native transcript was also inspected.

The follow-up [investigation synthesis](findings.md) incorporates independent
Sol and Terra probes and the literature run. It supersedes the open schema
question below: the tested reinitialization and clearing paths acknowledged
success but left the initial schema in force.

## The contract mismatch

Claude's streaming process can return a successful result while background
shell work remains. If its input and process remain alive, completion can
wake the model and produce another result. The latter carries
`origin.kind = task-notification`. With a JSON schema, both the initial
answer and the completion-triggered answer can contain valid structured
output. Schema conformance does not identify semantic assignment completion.
The model was explicitly instructed to produce a waiting response in the
controlled probes; the original incident establishes that it also chose
that behavior during a real assignment.

Gimble launches a process per RunTurn, accepts the first successful result
in claude/claude.go:waitTurn, and closes the SDK client on return. The SDK
ends stdin and allows five seconds before force-killing. That lifetime
cannot preserve delayed notifications across turns. Resuming a native
conversation restores history, not the previous process's live task state.

On resume, Claude can emit an orphan-task notification and an empty successful
result with zero model turns and task-notification origin. A later result
answers the newly submitted prompt. The SDK already exposes the Origin field;
Gimble ignores it. Its unstructured path accepts the empty result as success;
its structured path rejects the missing structured output. Both paths can
consume the wrong result before the requested answer arrives.

The original native transcript contains the orphan-task notification immediately
before the UI/UX debrief prompt. The controlled SDK reproduction establishes
the intervening raw-result sequence; those raw results were not retained for
the original incident, so the original sequence remains an evidence-backed
explanation rather than a directly captured wire trace.

## Choices

- Correct result attribution in any repair. A task-notification result must
  not satisfy an unrelated new prompt. Filtering by empty text is insufficient:
  notification results can also contain nonempty text and valid structured
  output. Preserve their observation without treating them as that prompt's
  terminal answer. Origin discrimination is directly supported; broader
  prompt/result correlation, including steering and mixed queued inputs,
  still needs explicit tests.
- Disable Claude background tasks in Gimble's subprocesses if retaining the
  current per-turn process model. This is the smallest containment compatible
  with that model. The documented flag is CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1.
  A finite foreground command and resumed follow-up worked with it. The flag
  also removes background subagents and auto-backgrounding; this investigation
  does not establish compatibility with every workflow that starts a service.
  Validate those workflows before adopting it as a default.
- Preserve background support only with a defined completion policy and a
  process lifetime that permits its continuations. Native task lifecycle
  events identify running work, but do not say which background shell is an
  assignment dependency and which is an intentionally persistent service.
  Neither a quiet interval nor waiting for every task is a sufficient policy.
  Keeping a process alive alone also does not decide when Generate returns.
- Explicit TaskOutput(block=true) waiting is a narrower workflow workaround.
  It kept the observed finite task inside one turn and allowed a correct
  follow-up. It relies on the agent following the waiting instruction and
  does not repair the adapter's attribution bug. A structured pending/done
  field could express workflow semantics explicitly, but would still require
  a live process or explicit waiting; adding a schema alone does not fix this.

Updated recommendation after discussing the cost of disabling background work:
repair attribution and prefer a Claude process owned by the Gimble session,
with background tasks enabled. Claude explicitly supports persistent streaming
input, and the live probe already demonstrated multiple results and a later
prompt in the same process. Per-turn teardown is our adapter choice, not a
Claude requirement. Keep the documented background-disable flag as optional
containment, rather than making it the desired design.

Gimble's Codex and OpenCode adapters connect to shared servers. Claude's
supported SDK hosting pattern instead maps each active session to a long-lived
query and its subprocess. No equivalent documented shared local multi-session
server was established by this investigation; one stdio process per session
already supplies the needed lifetime without adding a daemon.

The session should own the SDK client, stream, and continuous event reader;
RunTurn submits a prompt and awaits the associated response, while session
Close owns teardown. Event routing must keep working between calls. Keeping
the process alive is necessary but does not decide when Generate has fulfilled
the assignment: returning a waiting answer can still let a workflow advance
and close the entire scope. Settle awaited work versus persistent-service
semantics separately. Also verify changing and clearing output schemas between
calls: the current adapter supplies --json-schema at process launch, and the
successful persistent probe used one unchanged schema. Do not infer completion
from prose or idle timing.
