# Proposal: daily product validation through Gimble

Build one built-in workflow, provisionally `validate-product`, that accepts a JSON or YAML file describing a product and its features. Gimble itself becomes the first customer. The [organized inventory](feature-inventory.md) covers CLI commands and built-ins, browser observation and control, conversations/providers, workflow primitives, and history/tooling. Its feature IDs should become the checklist; implementation status and validation results remain separate.

Keep the input small: working directory, optional preparation/build script, foreground startup command or existing browser URL/CLI executable, readiness check, output directory, and timeout. Each feature needs an ID, frontend, any setup, a plain-English interaction to perform, and the observable result that means it worked. Accept both file formats as the same data structure. Let agents navigate the product using those descriptions; avoid turning the file into another programming language.

Write the workflow as ordinary Go: prepare the target with `RunCommand`, start owned processes with `Service`, check readiness explicitly, and use `Iterate` to visit the features. A testing agent operates the real product and gathers observations; a separate validation pass judges whether those observations demonstrate the requested behavior. Exit codes, outputs, visible state, and existing assertions support that judgment. Each declared feature receives a pass, fail, or blocked result with evidence. Unavailable credentials, missing tools, or an unfinished feature keep the overall run incomplete. Preserve failures rather than retrying until they disappear.

Start with Playwright CLI as the browser driver. Its documented named sessions, browser actions, tracing, and video commands fit the shell access already available to Gemini. Record the same session the agent operates. For CLI interactions, try an existing loopback terminal such as ttyd and record its real terminal through that browser session; retain command output and exit status for assertions. This is a proposed integration that must be tried, especially for terminal text inspection and cleanup. A trace or terminal event stream alone does not satisfy the video requirement. Finalize recordings before teardown on success, failure, and cancellation, and report missing video explicitly. ([Playwright CLI](https://github.com/microsoft/playwright-cli), [ttyd](https://github.com/tsl0922/ttyd))

First demonstrate one browser feature and one CLI feature, including an intentional failure and cancellation, with playable recordings and no surviving owned processes. Then expand to every inventory family, including real provider sessions, restart behavior, and library capabilities exercised through maintained workflows or package tests. Keep the validating runner separate from the Gimble instance being tested so cancellation and restart checks cannot kill their observer.

Finally, schedule that same command daily with an existing scheduler. Resolve latest `main` once, build it in an isolated checkout, and record the tested commit. Keep videos and results in the run's output directory, outside Git. The daily deliverable is a readable feature-by-feature report linked to recordings, with failures and gaps prominent. The next step is the small recording-and-validation pilot; scheduling follows once the full checklist works.
