# Gimbal distribution map 1

Date: 2026-10-12
Scope: independent end-to-end distribution research; source inspection only. No Apple/GitHub account mutations and no secret access.

## Recommendation

Use a two-part release:

1. GoReleaser OSS for immutable versioned CLI archives and checksums attached to GitHub Releases. Publish Linux amd64 and arm64 archives; publish Darwin amd64 and arm64 CLI archives as well if the CLI is a supported macOS entry point. Use GoReleaser's current `homebrew_casks` integration for a cask that places the signed `Gimbal.app` in `/Applications`; distribute the tap in a dedicated `tylergannon/homebrew-gimbal` repository. Homebrew's cask model natively installs app bundles, while GoReleaser's old `brews` formula publisher is deprecated since v2.10 and GoReleaser says generated formulae are not suitable for Homebrew Core. If a conventional CLI formula is required, maintain a small hand-authored formula in that tap (or generate a tap-specific formula from the release workflow) pointing at the per-OS/architecture CLI archives. The formula is a distinct interface from the cask.
2. Build/package/sign/notarize the Mac application and its embedded Go helper on macOS. A Mac app is a signed bundle with a valid Info.plist and executable(s), not a Go CLI archive renamed `.app`. Prefer a native GitHub-hosted macOS runner for the first automated release; it is an ephemeral macOS machine with Xcode tools. A private repository's standard macOS runner is currently $0.062/min after applicable included minutes; for a public repo standard hosted runners are free and unlimited. A self-hosted Mac adds ownership, patching and secret-hygiene costs and is unnecessary unless local signing proof or hosted-runner constraints require it.

Avoid GoReleaser Pro at the outset: OSS handles ordinary multi-target Go archives and Homebrew Casks. Its prebuilt/multi-machine CGO import path is Pro-only. If Go's CGO/native-host build cannot be built reliably on one macOS runner, separate native builds across runners will be an implementation choice to revisit, not a reason to buy Pro upfront.

## Exact repository constraints found

- `cmd/gimbal` is a Go CLI whose default command starts the web server. The root help describes serving the current repository; CLI subcommands include run, runs, watch, steer, generate, etc. The web UI is embedded by `web/dist.go` (`//go:embed all:build`), so release binaries require the generated/built web tree first. `just build` currently does Go module tidying, web dependency install, generation, formatting/build, manifest check, and `go build -o bin/gimbal ./cmd/gimbal`.
- Current Gimbal release skill says local installation is the distribution target and explicitly says local release needs no signing/scalable distribution. `.github/workflows/` has docs and model-price workflows, but no release pipeline or GoReleaser config exists.
- Go app dependencies include Goja (interpreter) and repository code uses only Go for `cmd/gimbal`; the only `import "C"` found is `native/host/main.go`, a Go C-ABI host built as part of the native app path. This means ordinary CLI archives should remain CGO-free where possible; test each target build before choosing `CGO_ENABLED=0`, because tags/dependencies can alter the build graph. Native-host build cannot be cross-compiled from Linux without Apple toolchain support.
- There is native SwiftUI application source at `native/Sources/Application.swift` and supporting WebKit UI. `native/skgo-native.json` declares bundle ID `com.tylergannon.gimbal`, macOS target 27.0, microphone and speech-recognition usage descriptions, resources, and a Go bridge. `native/host/main.go` exports `SKGoHostStart/Recover/Stop` through cgo; its reverse proxy defaults to `http://127.0.0.1:8080` / `GIMBAL_SERVER_URL`. `NativeHost.swift` starts that bridge and embeds its local URL in WKWebView. Crucially, the bridge proxies to an independent Gimbal server; this source does not launch the `gimbal` CLI/server. A distributed desktop app must either document/install/start a separate server, or bundle the CLI and have the app manage the child process lifecycle. For an end-user `/Applications` app, bundling/owning the matching server is the coherent self-contained path, but it needs process-lifecycle, shutdown, port selection, upgrade, and server-health behavior proved before CI automates it.
- The native sources shown are an app shell but there is no checked-in root `Package.swift`, Xcode project, `.app` layout, `Info.plist` for the app, or entitlements file in the scanned tree. `skgo-native.json` is generator input. Pin/document the actual native build command/tool version and generated artifacts before release automation; the current `just build` only builds the CLI.
- The native app's current macOS minimum is 27.0, which is a real compatibility restriction. Decide whether this is intentional before claiming broad Mac availability. The Go module targets Go 1.27.1. Produce separate Darwin amd64 and arm64 binaries, or a universal binary only if the app's packaging tool can make that reliably. Do not assume GoReleaser's universal binary step resolves CGO/cross-toolchain requirements.
- The only obvious macOS privacy declarations in `skgo-native.json` are `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription`; the app uses WebKit and native recording. No current entitlements file was found. Do not add JIT, library-validation, microphone or sandbox entitlements speculatively. Verify actual Go/Swift executable behavior under hardened runtime first; `goja` is interpreted JS, not an embedded JIT engine.

## Apple signing and notarization requirements

- For direct distribution outside the Mac App Store, use a **Developer ID Application** identity for the app and all nested executable code; use hardened runtime, a secure timestamp and valid XML entitlements. Do not use a Mac App Store distribution identity or ad-hoc signing. Remove `com.apple.security.get-task-allow=true`. App Sandbox is optional for notarization (required for Mac App Store), but should be an explicit product choice because this app needs localhost service access and possibly local project files.
- The app's microphone and speech-recognition consent strings belong in the final generated Info.plist. Check these after native packaging and before signing. If no protected/restricted entitlement is actually needed, an empty/minimal entitlements file is preferable. Assess bundled Go code and native recording runtime with hardened runtime enabled; only add a runtime exception when the signed/notarized app demonstrably needs it.
- Sign nested code from inner executable outward and sign the final `.app` bundle with hardened runtime and `--timestamp`; verify with `codesign --verify --deep --strict --verbose=2`. Submit the actual final deliverable with Xcode `notarytool` (Apple ID/App Store Connect API key credentials), wait for Accepted, staple supported deliverable (usually app or DMG; test `.zip` handling), then verify with `xcrun stapler validate` and `spctl --assess --type execute --verbose=4`. Do not modify the bundle after signing/notarizing. Prefer a signed, notarized, stapled DMG or ZIP containing the app for direct download; Homebrew cask installs the `.app` from the release artifact into `/Applications`.
- Apple Developer Program currently costs **US$99 per membership year** (or local currency where available); notarization itself is part of Developer ID distribution. Account Holder can create Developer ID certificates; Apple Developer docs show role permissions should be checked for the signed-in account. Current blocker is known: the parent reports membership expired and renewal requested, and no local signing identity exists. Once renewed, confirm account role/certificate access and whether the signing identity/private key can be exported for CI.
- Keep signing secrets out of chat and source control. Local proof can use the identity in Keychain. If exporting for hosted CI is authorized: store an encrypted/exported Developer ID Application `.p12` (base64 or secure file) and its import password, Team ID, plus an App Store Connect API key private key with key ID and issuer ID (or use notarytool's Apple-ID/app-specific-password method if API access is unavailable). Put these only in GitHub Actions secrets or a protected release environment. CI imports the p12 into a temporary keychain with a short timeout, signs, notarizes with `notarytool`, staples, validates and destroys the keychain/temp credential files. Use GitHub OIDC for other cloud services where possible; Apple signing/notarization still requires Apple-controlled credentials. Don't print credentials, certificates, or decoded environment variables in logs.

## Local proof before automation

On the user's Mac, first establish one real local release candidate:

1. Confirm `xcode-select -p`, Xcode command line tools, `swift --version`, Go 1.27.1 and existing `skgo` generator/build tooling; inspect generator output and ensure app Info.plist/bundle ID/macOS target/privacy strings are what the release will ship. Run the app's generated build on the local Mac, preserving separate arm64/x86_64 target requirements.
2. Decide/fix the app-to-server contract. If self-contained, bundle the matching Gimbal CLI/helper, start it under an app-owned directory and loopback port, wait for health, open WebKit to the actual origin, and stop/reap it on app termination. Then test Finder launch with no Terminal, clean install to `/Applications`, permissions prompts, app quit/relaunch, server-not-running/recovery, and whether app UI and CLI operate on the same project/run data.
3. Sign the exact packaged `.app` locally with Developer ID Application + hardened runtime + timestamp and minimal entitlements. Inspect `codesign -dv --verbose=4`, `codesign -d --entitlements :-`, then verify strict signature and Gatekeeper assessment. Submit via `xcrun notarytool` using the user's logged-in Apple Developer access, inspect the notary log on failure, staple the app or outer DMG, and validate staple + Gatekeeper after moving/installing the artifact. Test the actual quarantined downloaded artifact on a clean/non-development Mac account if available. This is the requested human/local proof gate before CI secrets/publishing automation.
4. Independently validate raw Linux archives on Linux amd64/arm64: checksum, executable, `gimbal --help`, and run the bundled web server long enough to see the embedded web UI. Verify version metadata, checksums and reproducible archive naming.

## Release automation outline after local proof

1. Build the actual production application and CLI with pinned Go/Xcode/skgo generator inputs. Use GoReleaser OSS for versioned Linux (`linux_amd64`, `linux_arm64`) and Darwin CLI archives as applicable, SHA-256 checksums, and GitHub Release upload. Keep source archive/binary names stable and version tag/commit injected through ldflags.
2. On macOS runner, generate the app's real `.app` bundle, include the app-owned Gimbal server/helper if decided, sign every nested Mach-O and final app with imported Developer ID identity, notarize the final distribution container, staple and verify it. Publish app DMG/ZIP as release asset. Test the cask install path in a clean Homebrew prefix and assert resulting `/Applications/Gimbal.app` exists and launches; test formula `brew install` yields `gimbal` on each supported platform.
3. Generate/update a dedicated Homebrew tap. GoReleaser `homebrew_casks` can publish the cask to another repo, but requires a separate token with contents write access; Actions `GITHUB_TOKEN` cannot write cross-repository. Use a narrowly scoped fine-grained PAT/repository secret or make the tap update a PR for human review. A standard formula should be manually authored/maintained in that tap because GoReleaser's legacy formula publishing is deprecated and its generated formula is not Homebrew Core quality. Verify formula URL/SHA per macOS/Linux architecture. Avoid secrets for Linux-only binary build if release workflow can use narrowly scoped `contents: write` GITHUB_TOKEN.
4. Trigger only on protected version tags after local product proof and source review. Give the GitHub release job minimum `contents: write`; isolate signing/notary secrets in an environment with required reviewers if desired. Publish assets, then update tap only after release assets are visible and checksums stable. Do not let untrusted pull-request workflows access signing secrets. Use a release concurrency guard to avoid two tags signing/publishing concurrently.

## Cost and runner comparison

- Apple Developer Program: $99 USD/year (unless local currency/eligible fee waiver). The user appears to have a logged-in Safari session but membership/team entitlements remain unverified.
- Public GitHub repo: standard GitHub-hosted Linux/macOS runners are free/unlimited according to current docs. Private standard macOS runner: current stated rate $0.062/min (subject to account included minutes and billing changes). A short macOS signing/notary job should be minutes to tens of minutes per release, so low recurring cost. GitHub larger macOS M2 runner is $0.102/min and requires Team or Enterprise; likely unnecessary.
- Self-hosted runner: no GitHub hosted-minute charge, but requires maintaining a dedicated Mac, runner registration/updates, disk cleanup, network exposure controls, and handling an especially sensitive signing key. Avoid unless interactive Apple login or on-hardware validation is required. Account/Apple signing operations are safer to do locally for the initial proof, then export/import a protected CI signing identity only if/when it is acceptable.
- GoReleaser OSS is sufficient for normal builds/releases/casks; no service fee. Homebrew tap is a public GitHub repository with no direct hosting cost. Direct GitHub release artifact download is included.
