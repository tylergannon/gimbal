# Gimbal CLI and macOS app release map (independent pass 3)

Research date: 2026-10-12. Scope: conventional Linux/macOS CLI downloads and Homebrew install, plus a real signed, notarized macOS `Gimbal.app` installed to `/Applications`. No account settings or credentials were inspected or changed. Draft automation was added for review; it has not been published, tagged, or activated.

## Finding

The CLI side has a tested unsigned snapshot build and a drafted native-runner workflow that deliberately builds the SvelteKit output before compiling each Go target. The app is generated by the pinned SKGo builder rather than checked in as an Xcode project: `go tool skgo native build --platform macos` creates the distribution project and Debug app under `native/build/macos/`. The release script builds its Release target, sets the semantic version and CI build number, then signs, notarizes, staples, and packages the app. Local signed/notarized proof remains blocked until a valid Developer ID identity and notary credentials exist.

## What exists now

- The current checkout is `2f77dc8` (`2026-10-12`); the latest upstream GitHub release and tag are still `v0.12.1` (`fcfcc5d`, released 2026-09-23), with 32 commits to `main` since it. The release is titled “Gimble v0.12.1” and the module at the old tag says `github.com/tylergannon/gimble`; current `go.mod` says `github.com/tylergannon/gimbal`. New automation should use the current `gimbal` spelling and a fresh version, not copy the old title or module metadata.
- The CLI entry point is `cmd/gimbal`; release version metadata is injected into `main.version`, `main.commit`, and `main.date`; `Justfile`'s `build` recipe runs `go mod tidy`, installs/builds the frontend, runs Go generation, builds the SvelteKit application, checks `web/build/skgo.manifest.json`, then builds `bin/gimbal`.
- `web/dist.go` embeds `all:build`, while `.gitignore` ignores `web/build/*`; a raw `go build ./cmd/gimbal` from a clean checkout lacks the generated frontend. In contrast, the generated adapter archive `web/build.zip` is committed and the root skill says versioned module install relies on that archive. A release workflow must invoke the authoritative frontend build before GoReleaser, then ensure the tracked archive/tree is ready for Go compilation. The exact build-and-restore interaction should be proven once before codifying it.
- GoReleaser 2.18.3 is installed locally on Darwin arm64. It is not configured in this repo. `cmd/gimbal` imports Go's `plugin` package for daemon/plugin commands. `plugin` needs its supported native platform/toolchain and `CGO_ENABLED=1`; a Linux arm64 compile with `CGO_ENABLED=0` succeeds here, but `plugin` resolves to `plugin_stubs.go` (no CgoFiles), so that binary silently lacks usable dynamic plugin loading. Do not globally set `CGO_ENABLED=0` just to make cross-compilation easy. Build each supported target on a compatible native runner or use a vetted C cross-compiler/toolchain and prove plugin commands still work. The initial draft matrix builds Darwin arm64, Linux amd64, and Linux arm64 on native compatible runners; do not disable CGO, which would silently remove plugin support. Intel macOS requires an explicit compatible builder/target decision.
- Current native implementation is under `native/Sources/` with SwiftUI `@main` in `Application.swift`, Swift native host calls declared by `native/Bridge.h`, and the C ABI Go host in `native/host/main.go`. Pinned `github.com/tylergannon/skgo v0.29.0` builder resolves native SDK, generates Go/Swift projections, builds the separate Go presentation host as an arm64 C archive with CGO enabled, generates an Xcode project from `native/skgo-native.json`, and invokes Xcode. The app is intentionally a presentation shell around the independently run Gimbal server; preserve this boundary. The distribution config sets bundle ID `com.tylergannon.gimbal`, deployment target 27.0, microphone/speech purpose strings, and resources. The generated app is at `native/build/macos/DerivedData/Build/Products/Debug/Gimbal.app`. The generated project sets `ARCHS=arm64`, `ONLY_ACTIVE_ARCH=YES`, and `CODE_SIGNING_ALLOWED=NO` when no development team is supplied; its Info.plist defaults are `CFBundleVersion=1` and `CFBundleShortVersionString=0.1.0`. `native/Transcription/Package.swift` is a separate library/test package. `ProbeInfo.plist` belongs to a test probe, not the distributed app.
- The code does not yet tell us the supported macOS app CPU architectures, executable names, bundle layout, app version/build stamping, login/update behavior, or whether the final target needs any hardened-runtime exception. Keep these as local build questions, not assumptions.

## Recommended first release shape

Use public GitHub Releases as the one artifact origin. Emit a checksum file and per-platform CLI tarballs; start with Darwin arm64 and Linux amd64/arm64 built on matching native runners. Keep names in the verified GoReleaser form: `gimbal_<version>_darwin_arm64.tar.gz`, `gimbal_<version>_linux_amd64.tar.gz`, and `gimbal_<version>_linux_arm64.tar.gz`. Include `gimbal`, `LICENSE`, `README`, and generated Cobra shell completions where their commands support it. A single checksum file covers every archive. The README already distinguishes running a built binary from `go install`; document this release path beside those instructions.

Use a separate `tylergannon/homebrew-gimbal` repository. Publish macOS CLI with a Homebrew binary Cask named `gimbal`, using a small manually-rendered Cask that points at the Darwin arm64 GitHub Release archive. GoReleaser 2.18+ OSS can publish binary Casks, but this split artifact workflow writes both Casks after the final release checksum exists. Casks are a macOS install channel; Linux users get the architecture-labelled GitHub Release tarballs directly. Do not use the deprecated GoReleaser `brews` formula publisher just to put a binary in a tap. The native GUI app is a different product and can have a simple manually-rendered `gimbal-app` Cask after a successful release; GoReleaser's Cask `app: .app`/DMG mode is Pro-only in the current docs. `homebrew/core` acceptance is a different and much stricter project; a personal tap is the normal first channel.

For the GUI, publish `Gimbal-<version>-macos-arm64.zip` containing the stapled `Gimbal.app` and preferably a signed, notarized, stapled `Gimbal-<version>-macos-arm64.dmg` for direct drag-to-`/Applications` installs. Add a separate `gimbal-app` Cask in the tap that fetches the ZIP or DMG and declares `app "Gimbal.app"`, so Homebrew places the app under `/Applications`. Keep the app token distinct from the `gimbal` CLI Cask. Cask URLs support ZIP/DMG and checksums; GoReleaser Casks can publish a binary Cask into a tap, but its `.app`/DMG mode is Pro-only in the currently documented feature. Updating this small app Cask from release metadata is simpler than buying GoReleaser Pro solely for app publishing.

Do not conflate a GitHub Release tag with a release. The previous tags have no CLI archive assets: GitHub currently shows only the source-code archives for `v0.12.1`. The first new tagged release should include architecture-labelled artifacts, checksums, and explicit install instructions.

## Build, local proof, then automate

1. **Use the generated target and control release metadata.** Run `just build`, then `go tool skgo native build --platform macos` from the exact release commit. This requires macOS/Xcode and also uses the pinned SKGo native SDK, Swift packages, Zig, and `xcodegen`. Verify the generated project and its Release target/output. Set `CFBundleShortVersionString` to the tag without `v`, `CFBundleVersion` to a valid increasing build number, and confirm `com.tylergannon.gimbal` and `LSMinimumSystemVersion=27.0` before signing. Do not hand-edit generated app source or sign `transcription-probe` as though it were the app.
2. **Prove the app locally before activating Actions automation.** Build from a clean worktree and the exact release commit, inspect the generated bundle layout, launch it from `/Applications/Gimbal.app`, verify the app window and native host interaction with the independently running Gimbal server, exercise recording only with an explicit microphone permission grant, and confirm bundle/version/minimum-OS metadata. The app's separate Go server is an intentional architecture boundary; preserve it in this packaging flow. Build an unsigned local copy first to establish the linker/resource setup, then perform a real Developer ID signed local build. The account owner reports that Apple Developer membership is renewed but certificate creation is not currently available and there are zero signing identities; therefore local signing/notarization proof is presently blocked on the Apple certificate service and creating/exporting the correct Developer ID identity. There is no useful end-to-end signature proof without a real Developer ID identity and Apple notarization credentials; do not represent self-signed/ad-hoc signing as notarization.
3. **Sign the app.** Create a `Developer ID Application` certificate (exportable as a `.p12`) for direct distribution. Apple excludes development, Mac App Distribution, ad-hoc, and self-signed identities for this flow. Sign embedded executable code from the inside out, then the app bundle with secure timestamp and hardened runtime (`codesign --options runtime --timestamp`). The actual recorder uses AVAudioEngine input and Core Audio capture, so the app's `native/release.entitlements.plist` carries `com.apple.security.device.audio-input=true`; microphone/speech purpose strings in Info.plist remain necessary user-facing permission descriptions. Do not add the CLI's library-validation entitlement to the app. Notarization requires hardened runtime and rejects `com.apple.security.get-task-allow=true`. Use `codesign --verify --deep --strict --verbose=2` and `spctl --assess --type execute --verbose=2` on the built app.
4. **Notarize locally.** Create an App Store Connect API key with the least permission accepted by Apple notarization, and store it as a `notarytool` keychain profile (`xcrun notarytool store-credentials ... --key ... --key-id ... --issuer ...`). Sign first; make a ZIP preserving the `.app` root with `ditto -c -k --keepParent`; submit via `xcrun notarytool submit <zip> --keychain-profile <profile> --wait`; inspect the notary log even on accepted status. Staple to `Gimbal.app` with `xcrun stapler staple Gimbal.app`, verify with `xcrun stapler validate`, repeat `codesign` and `spctl`, then package the stapled app for download. If shipping a DMG, create it after the app is stapled, sign it, submit it for notarization, and staple/validate the DMG too. Apple says ZIPs cannot be stapled directly; staple the app/disk image and then make the final ZIP from the stapled app.
5. **Test the actual download/install.** Download the release ZIP/DMG to a separate fresh user or Mac if available; install it into `/Applications`, confirm Gatekeeper acceptance while offline after stapling, cold-launch, verify the expected app bundle identifier/version, and exercise the native host path. Run the Go CLI separately from its released archive and run the app's product path with the standalone server as documented. This proof catches packaging issues that checking source or codesign alone does not.
6. **Activate release automation after signed proof.** Tag push triggers compatible native builds. As of 2026-09-10 GitHub-hosted `xcode-27` and `xcode-27-xlarge` are public-preview ARM64 macOS 27 runner labels, making `xcode-27` the simplest default for both Darwin CLI and app target. The draft workflow is prepared, but activation/publication should wait until the native app and CLI have passed local Developer ID signing and Apple notary acceptance. Linux CLI targets with Cgo plugins need Linux+C toolchain-compatible runners: use a standard x64 Ubuntu runner for amd64 and native `ubuntu-24.04-arm` for arm64. The normal hosted runners avoid needing `amritanandamayi` merely to get the required operating systems; keep that host as an optional candidate only if hosted-runner cost, continuity, or another requirement warrants it. If self-hosting, first verify labels, OS/architecture, registration, availability, clean-runner policy, and untrusted-job restrictions. Never run an untrusted PR build on a credential-bearing host.
7. **Publish from the tagged commit.** Run GoReleaser OSS on compatible native platform jobs after running the repository's frontend generation/build recipe; retain CGO on all supported release builds. Collect the resulting archives and checksums, attach them plus notarized app ZIP/DMG to the GitHub Release only after every required job succeeds, verify artifact names/checksums/signature/staple and install behavior, then publish. Publish the binary `gimbal` Cask after the macOS CLI archive is public; render the separate `gimbal-app` DMG Cask after the stapled app asset is public. Use exact tag version and release asset SHA-256; do not use `:no_check`.

## GitHub Actions credential inventory and handling

Use a protected GitHub Actions `release` environment with tag-only deployment branch restrictions and a required reviewer if manual release approval is desired. Workflow permissions should default to `contents: read`, then grant the publishing job only `contents: write`; give the tap updater only its tap-repository access. Keep secrets off PR/fork workflows. GitHub warns that transformed secrets may not redact and recommends minimizing token scope, using env/stdin rather than command-line literals, masking derived sensitive values, and auditing logs. Import certificate files into an ephemeral temporary keychain on the release runner; do not install them in the runner's login keychain or print them.

Likely environment secrets (names are proposal, values must never be written into this note):

- `DEVELOPER_ID_CERTIFICATE_P12_BASE64`: base64-encoded Developer ID Application `.p12` with private key.
- `DEVELOPER_ID_CERTIFICATE_PASSWORD`: password used for the exported `.p12`.
- `APPLE_TEAM_ID`: the developer team identifier used to select the Developer ID identity.
- `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_API_KEY_P8_BASE64`: App Store Connect API key ID, issuer ID, and base64 `.p8` private key for `notarytool`.
- `TAP_GITHUB_TOKEN`: narrowly scoped write access to `tylergannon/homebrew-gimbal` if using a PAT. Prefer a GitHub App token scoped to that one repository when practical.

The public repo's release `GITHUB_TOKEN` uses the per-job `contents: write` grant for its own GitHub Release. Decode P12/P8 into a private temp directory, set file permissions, import P12 into a throwaway keychain, register a notarytool profile only for that runner/job, and remove temp files/keychain in an `always()` cleanup step. Feed sensitive command values through environment variables. GitHub secrets cannot exceed 48 KiB; confirm the base64 P12 fits or use a deliberately designed encrypted-file approach. Store tap credential and Apple secrets in the protected environment rather than exposing them to normal build/test events.

## Decisions that must be answered by a real local run / account owner

1. Is the team already enrolled in the Apple Developer Program and is there a valid Developer ID Application certificate/private key that can be exported and used by the intended release runner? The host must not inspect or alter the keychain as part of this research.
2. Is there an App Store Connect API key available for `notarytool`, and can its intended permissions submit notarization requests? If not, create/authorize one outside repository code and provide its identifiers/secret directly through protected Actions secrets.
3. Is `amritanandamayi` an always-available Apple Silicon Mac with the required Xcode and macOS target, and is it already/appropriately registered as a repository or organization self-hosted Actions runner? Do not route secrets to it until the service account, isolation, updates, and untrusted-job restrictions are settled.
4. Confirm whether Intel macOS app support is in scope. The current native JSON says macOS 27 but does not define CPU support. The CLI matrix can include Intel independently of the native app.
5. The chosen personal tap is `tylergannon/homebrew-gimbal`; publish CLI and app as separate Casks, not a Formula.

## Draft automation implementation and newly proven macOS CLI behavior

The reviewable automation draft now lives in `.goreleaser.yaml`, `.github/workflows/release.yml`, and `scripts/release-{cli,macos}.sh`, plus `scripts/ci-signing.sh`, `scripts/sign-notarize-macos-cli.sh`, the CLI entitlement plist, and `scripts/update-homebrew-casks.sh`. The GoReleaser OSS config validates with 2.18.3; a local arm64 `--snapshot --skip=before` build produced `gimbal_0.12.1-SNAPSHOT-2f77dc8_darwin_arm64.tar.gz`, confirming its lowercase OS and `arm64` archive naming. This is build proof only; the snapshot is unsigned, and the workflow has no unsigned release fallback. The actual release wrapper performs `just build`, emits a native target through a temporary config, signs/notarizes the macOS CLI, and calculates its interim checksum; CI combines all checksums after all platform artifacts are collected.

An independent local probe found that macOS hardened runtime blocks `plugin.Open` for the existing separately compiled Go plugin binaries when the Gimbal CLI has library validation enabled. Signing only the CLI host with `com.apple.security.cs.disable-library-validation=true` restores that plugin path. The CLI archive is notarized through a ZIP submission; Apple does not allow stapling to a standalone CLI ZIP or tarball, so initial Gatekeeper validation relies on online ticket lookup. This entitlement is deliberately absent from the native app and plugin artifacts. A quarantined third-party plugin still needs its own notarization or user approval. This is a measured limitation and must be documented with the CLI install path.

The draft workflow uses one protected macOS job for both signed products, native Linux amd64/arm64 jobs with `CGO_ENABLED=1`, and a final GitHub release/tap update. The tap updater writes the `gimbal` CLI Cask and `gimbal-app` DMG Cask into `tylergannon/homebrew-gimbal`; the desired install tokens are `brew install --cask tylergannon/gimbal/gimbal` and `brew install --cask tylergannon/gimbal/gimbal-app`. App asset names include the semantic version. Existing release tags are not republished by a rerun; recovery of a partial release/tap publish remains a separate explicit procedure. Do not activate or run this workflow until a real local Developer ID signed build and Apple notary acceptance prove the same sequence.
