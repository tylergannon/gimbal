# Gimbal distribution map — independent pass 4

Date: 2026-10-12
Repository inspected: `/Users/tyler/.codex/worktrees/gimbal-distribution/gimbal` (branch `codex/gimbal-distribution`). Research only; no source or release workflow changed.

## Finding

Treat these as two independent deliverables built from the same tag:

1. `gimbal`, a CLI/server binary distributed through Homebrew Formula and GitHub release archives for Linux (at minimum `linux/amd64`; add `linux/arm64` deliberately).
2. `Gimbal.app`, the macOS 27 arm64 microphone/speech shell distributed as a signed, notarized `.dmg` (or app ZIP) with a tap Cask optional. It is a client of a separately started Gimbal server; packaging must not create a LaunchAgent, start/stop the server, or imply the app owns the server lifecycle.

The split follows source: `Justfile` `build` produces `web/build` and `bin/gimbal`; `web/server.go` embeds the web build. `native/host/main.go` explicitly says the host owns presentation transport only, never opens projects/stores, and never starts the independent workspace server. It proxies to `GIMBAL_SERVER_URL`, defaulting to `http://127.0.0.1:8080`. `native/Sources/NativeHost.swift` additionally requires the local host origin to be 127.0.0.1. So an app artifact is not a second server distribution.

## Source and tool constraints

- `go.mod` requires Go 1.27.1 and declares `github.com/tylergannon/skgo/cmd/skgo` as a `go tool`.
- `Justfile` `build` runs `go mod tidy`, frontend install, `go generate ./...`, formatting and frontend build, checks `web/build/skgo.manifest.json`, then builds `bin/gimbal`. A release job must therefore build the web artifact before GoReleaser builds the CLI; it cannot just run GoReleaser against a checkout whose `web/build` is absent.
- `go tool skgo native build --platform macos` is the distribution build. The no-preset configuration already selects the real microphone and preserves the base bundle ID `com.tylergannon.gimbal`; `--preset real` is for a distinct `.real` development bundle and should not be used for distribution. The actual pinned generator in the Go module cache (`github.com/tylergannon/skgo@v0.29.0/internal/nativebuild/build.go`) refuses non-darwin hosts, fixes `GOARCH=arm64`, makes a Go `c-archive` with `CGO_ENABLED=1` and Xcode's Apple SDK clang, runs `mise` for Zig and XcodeGen, then invokes `xcodebuild`. The app is arm64 only today; a universal binary is not available from this path. The native config sets app deployment target 27.0, and `native/Transcription/Package.swift` also has macOS 27.0. This means the released shell requires macOS 27 or newer; Xcode 26 is insufficient for the declared SDK/deployment target.
- The generator's Xcode call uses `CODE_SIGNING_ALLOWED=NO` unless `SKGO_DEVELOPMENT_TEAM` is set. The generated project spec also sets `CODE_SIGNING_ALLOWED=NO`, `ENABLE_APP_SANDBOX=NO`, and app Info.plist includes microphone and speech-recognition purpose strings and `NSAllowsLocalNetworking`. The resulting Debug app is suitable for a local run, not external distribution.
- The `gimbal` main package imports `plugin`; `Registry.LoadPlugins` uses Go's `plugin.Open` and dynamic `.so` loading. Go's own `plugin` docs say the package is supported on Linux, FreeBSD and macOS, requires host/plugins compiled with the same Go version, flags, build tags and common source, and carries runtime/initialization constraints. Go's cgo docs say cgo defaults off for cross-compiles and a target C compiler must be provided. Therefore Linux archives need `CGO_ENABLED=1` and a working target compiler; a plain macOS-to-Linux `CGO_ENABLED=0` GoReleaser cross build is not a valid supported path for this CLI. Easiest safe proof is to build each Linux architecture on a native Linux runner. If cross-building Linux arm64 from amd64, explicitly provision an aarch64 C toolchain and verify the artifact on arm64.
- There are no release workflows or GoReleaser config in this worktree yet. `goreleaser` is installed locally (reported by parent as 2.18.3); current official GoReleaser docs mark the `brews` formula integration deprecated (soft deprecated since 2.16) in favor of `homebrew_casks`. A CLI should remain a Formula; use GoReleaser's still-present formula publisher for now only if acceptable, or maintain/update the formula with a small explicit release step. A Cask is appropriate for the GUI app. The GoReleaser cask `app:` option is marked Pro-only in current docs; do not assume the free binary-cask config installs `.app` into Applications. A simple `.dmg` release asset with the app plus `/Applications` alias works without that integration. If the tap should install both, publish `gimbal` formula and a separate `gimbal-app` Cask, with the latter depending on the CLI formula only if that install flow is desired. Cross-repo tap updates need a dedicated write token; GoReleaser docs say the default Actions token cannot write a separate tap repo.

## Apple signing and local proof

Current local observations from this host: `xcodebuild -version` reports Xcode 27.0 / build 27A266a; `xcrun --find notarytool` resolves inside `/Applications/Xcode.app`; `security find-identity -v -p codesigning` prints `0 valid identities found`. The user reports the Developer Program membership is renewed through 2027, but Apple's certificate service still reports the account ineligible, so there is no Developer ID identity available to sign with yet. An unsigned build is now proven locally; signing/notarization remain blocked on a valid Developer ID certificate and notary credentials.

Once available, expected production flow:

1. Create/renew Apple Developer Program account; create a Developer ID Application certificate and export its private key as protected PKCS#12; create an App Store Connect API key for notary authentication (or use an app-specific password and Team ID). A local installable build can use the same Developer ID certificate in a temporary keychain.
2. Build `just build`, then `go tool skgo native build --platform macos --preset real`; run/inspect the actual unsigned `.app` locally and prove it reaches the existing server. Preserve the separately-owned CLI server boundary.
3. Set version/build metadata in the bundle before signing; current generated Info.plist is hard-coded to version `0.1.0` / build `1`, so a tagged distribution needs a deliberate versioning mechanism (or a post-generation plist edit before signing). Sign the final app with Developer ID Application, hardened runtime and secure timestamp. Current app has sandbox disabled and has Info.plist permission-purpose strings; no app sandbox entitlements or provisioning profile are currently configured. The app directly records microphone input through `AVAudioEngine`/`AVAudioInputNode.installTap` and uses Core Audio to select a named input, so its hardened-runtime signature includes Apple's `com.apple.security.device.audio-input` resource-access entitlement. Apple documents this entitlement for recording audio and accessing Core Audio input; the user must still grant microphone privacy permission, requested through the existing `NSMicrophoneUsageDescription`. This is narrowly scoped and does not enable the app sandbox, JIT, debugging, or library-validation exceptions.
4. Verify signature strictly, archive with `ditto -c -k --keepParent`, submit the archive with `xcrun notarytool submit ... --wait`, inspect the returned notary log including warnings, staple to `.app` with `xcrun stapler staple`, verify with `codesign --verify --deep --strict` and Gatekeeper `spctl --assess --type execute`, then produce a drag-install DMG and staple that too. A submitted ZIP cannot itself be stapled; Apple says staple the app inside and recreate the ZIP. Upload only after the downloaded release artifact can be copied into `/Applications` and launched with the independent server already running.
5. Secrets in CI: use protected GitHub Actions secrets/environment, ephemeral runner keychain, import certificate with password, set key partition list, and always delete the temporary keychain and certificate material. Use the Apple API key/key-id/issuer-id to `notarytool` or keychain profile. Avoid self-hosting secrets on a runner that executes untrusted pull-request code. Follow GitHub's documented keychain cleanup on persistent self-hosted hardware.

## Packaging implementation and proof

`scripts/release-macos.sh` now has explicit `--build-only` and `--release` modes. Build-only creates an unsigned Release app under ignored `dist/macos/Gimbal.app`. Release mode requires an explicit release version/tag, a valid Developer ID Application identity, and an existing named notarytool keychain profile before generating/building. Normal mode always runs SkGo first to refresh generated remotes and embedded host code; `--skip-generate` is an explicit optimization for an existing generated Xcode project, and `--skip-build --built-app PATH` consumes an exact previously built candidate. Release metadata is numeric and written to `CFBundleShortVersionString` / `CFBundleVersion` before signing. It signs nested Mach-O files and bundles, the app executable and outer app with hardened runtime, timestamp and only `com.apple.security.device.audio-input`; it signs no JIT, library-validation, get-task-allow or app-sandbox exception. When `GIMBAL_CI_KEYCHAIN_PATH` is set, every `notarytool history`, `submit`, and printed `log` command uses that custom keychain; local runs without it keep the default keychain behavior. It notarizes a temporary ZIP, staples and validates the app, checks `codesign` and `spctl`, emits a stapled app ZIP, then creates a DMG with an `/Applications` symlink, signs/notarizes/staples the DMG. Notary submission failures print the submission ID and `notarytool log` command when available.

Local proof on 2026-10-12: the parent completed the normal unsigned native Debug build. I then ran `bash scripts/release-macos.sh --build-only --version 0.1.1 --build-number 1`; Xcode built the Release app and the script copied it to `dist/macos/Gimbal.app`. Its Info.plist says bundle ID `com.tylergannon.gimbal`, version `0.1.1`, build `1`; `file` reports the main executable as Mach-O arm64; `codesign -dv` reports an ad-hoc/linker signature with no team. `bash -n scripts/release-macos.sh` and `plutil -lint native/release.entitlements.plist` passed. A release-mode preflight with a placeholder profile stopped before any network/build work with `no valid Developer ID Application identity found`; the current keychain still reports zero valid identities. Signed/notarized output was not produced.

Apple primary references require Developer ID Application (not Mac App Distribution or development/ad hoc), hardened runtime, secure timestamp, valid signatures on every executable, no `get-task-allow=true`, and notarization for distributed non-App-Store apps. `notarytool` is current; `altool` was shut off for notarization in 2023. Notary submission accepts ZIP/DMG; staple the app/DMG; logs should be checked even after accepted status.

The microphone entitlement decision is supported by [Apple's Audio Input entitlement documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.audio-input) and [hardened runtime capability guide](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime): audio input is the resource-access capability for recording through Core Audio, and privacy authorization remains required. The source calls `AVAudioEngine.inputNode.installTap` and `AudioUnitSetProperty` for selected input devices. Signed runtime capture has not been demonstrated locally because the machine still has no Developer ID identity; the entitlement is justified by the app's direct API use and Apple's hardened-runtime contract.

## Runner tradeoff

- **GitHub-hosted `xcode-27` arm64** is the clean default for the app build/sign job once secrets exist: current official hosted-runner table lists `xcode-27` (3 M1 cores, 7 GB, 14 GB) but explicitly labels it public preview; GitHub warns beta images are as-is and outside normal SLA/support. It runs the required macOS/Xcode 27 SDK and is ephemeral, which bounds signing-key persistence. It may be memory tight while `vp build` plus Zig and Xcode run; measure one real release-tag build. Ensure Go 1.27.1 via setup-go (published image currently lists Go through 1.26.8), bootstrap mise, and use the repo's pinned native/mise.lock for Zig/XcodeGen.
- **Self-hosted `amritanandamayi` Mac** can be a pragmatic fallback if it has macOS 27, Xcode 27, Apple Silicon, sufficient disk/RAM, available always-on network, and a Developer ID identity. It avoids preview dependence and may retain a secure signing keychain. Before choosing it, verify those facts on that host; don't assume local host observations carry over. Persistent machine registration/keychain increases cleanup and isolation responsibility; route only trusted tag releases to it, and never run PR-controlled code there with signing secrets.
- **Linux cross-build** cannot produce the app at all: SkGo's generator checks runtime.GOOS == darwin and uses macOS SDK/Xcode. Linux is suitable for the CLI, and preferred for native Linux CLI compilation because Go plugin loading requires cgo. Use Linux as its own job. Hosted `ubuntu-24.04-arm`/`ubuntu-26.04-arm` are currently listed but preview? Verify exact label state at use; x64 Ubuntu is stable. Could ship only linux/amd64 first, then add arm64 after native ARM build validation.

Recommendation: split GitHub release into a Linux CLI/archive/Formula job and a Mac app job. Start the Mac app on hosted `xcode-27` once available; if preview instability or memory makes builds unreliable, use the named self-hosted Mac after qualifying it and isolating the tag-only secret path. Linux is not a candidate for the native app job. Keep post-build macOS local signing proof as a gate before wiring credentials into automation.
