## Core teaching

Gimbal is assembled in a deliberate order. `just build` first tidies Go modules, installs the web package, runs Go generation, formats the generated web output, builds the Svelte app, and only then builds `cmd/gimbal` into `bin/gimbal` (`justfile:L4-L10`).
The order is part of the contract: generated bindings and the embedded frontend must exist before the Go binary is compiled (`justfile:L4-L10`).
The normal local checks are separate from the build: `just vet` runs `go vet`, builds the binary, and invokes the binary's `lint`; `just test` runs Go tests and web tests; `just fmt-check` checks the Vite+ formatter (`justfile:L23-L30`, L35-L39).
The end-to-end recipe installs dependencies and Chromium, then runs Playwright against `BASE_URL`; it can target either the configured origin or another URL (`justfile:L18-L21`).

Go owns the production composition, while `web/` owns the Svelte package and its generated/build artifacts. The root module explicitly treats `web/` as a Go package containing the build and excludes `web/node_modules` from `./...` traversal (`go.mod:L1-L7`).
The Go module pins skgo, polytype, and their generator tools. `go tool` runs the pinned module-cache tools, so generation does not require a writable checkout of skgo (`go.mod:L22-L25`, L48-L56).
`web/package.json` exposes `check`, unit tests, Storybook, and build scripts; the package is private and uses pnpm 12.4.2 (`web/package.json:L1-L5`, L10-L20, L50-L56).

`web/server.go` is the ownership seam. `NewHandler` lives beside the embedded build because the page's remote functions import Gimbal and Gimbal cannot import the page (`web/server.go:L1-L7`).
The command binary and tests are intended to call this same `NewHandler`, giving one production stack rather than a separately composed test server (`web/server.go:L1-L6`).
Production reads the generated manifest and serves the embedded build; development reads a dev manifest and proxies pages to `vp dev` (`web/server.go:L22-L39`, L45-L76).
The generated loads, remotes, endpoints, and transport are registered before the page handler is built (`web/server.go:L79-L115`).
The final handler wraps the same observation routes around the Kit stack, and the SSR renderer uses those routes as its fetch host; this keeps browser and SSR observations on one composition (`web/server.go:L117-L126`).

The frontend generator can rewrite generated TS/JSON files. The regeneration worklog records the chosen workflow: accept skgo 0.5.0's generated web directory as the base, then restore Gimbal-owned routes, components, remotes, and tests (`ephemeral/worklog/202609181700-skgo-050-web-regeneration.md:L1-L5`).
That worklog also records a compatibility constraint: preserve the official Svelte compiler and Svelte-aware checker split while taking scaffold, Vitest, and Storybook from the generated base (`ephemeral/worklog/202609181700-skgo-050-web-regeneration.md:L3-L5`).
Tailwind had to be added through the official `vp dlx sv add` flow, with a temporary literal plugin array workaround before restoring skgo's lazy wrapper (`ephemeral/worklog/202609181700-skgo-050-web-regeneration.md:L7-L11`).
The practical ownership rule is therefore: generated files are regenerated by the build, but Gimbal-owned application routes and behavior are restored and preserved by hand (`ephemeral/worklog/202609181700-skgo-050-web-regeneration.md:L3-L5`).
`just build` runs `vp fmt` immediately after `go generate`; otherwise seven generated files fail the formatter check that the build is intended to preserve (`ephemeral/worklog/202609181700-skgo-050-web-regeneration.md:L13-L15`).

## Checks, hooks, and proof

The pre-commit hook runs staged-content policy, Go formatters, linters, and Go tests. Goimports and modernize may stage their fixes; golangci-lint and Gimbal lint run with default configuration (`lefthook.yml:L7-L40`).
The pre-push hook runs Gimbal lint (`lefthook.yml:L42-L45`). The repository's explicit stance is to fix code rather than add linter configuration or suppressions (`lefthook.yml:L1-L5`).
The staged-content script rejects committed run products such as logs, result files, screenshots, and files under `ephemeral/attest/` (`scripts/check-staged-content.sh:L24-L38`, L49-L55).
It also rejects code under `ephemeral/`, except frozen legacy material, because repeatable checks belong beside the code they check (`scripts/check-staged-content.sh:L35-L38`, L57-L63).
Ordinary commits are bounded to 100 paths, 10,000 added lines, 5 MiB total, and 1 MiB per file unless Tyler explicitly enables `GIMBAL_ALLOW_LARGE_COMMIT=1` (`scripts/check-staged-content.sh:L4-L7`, L65-L97).
Release or build teaching must treat a green aggregate gate as supporting evidence; runtime claims still require observing the built binary or a live browser/end-to-end run.
For web behavior, `just e2e` is the named route to Playwright evidence (`justfile:L18-L21`); for server composition, use the same `NewHandler` path used by the binary and tests (`web/server.go:L1-L6`).

## What is actually shipped

The docs workflow is real CI: on `main` pushes, pull requests, or manual dispatch it installs docs dependencies, checks and builds `docs-site`, uploads the Pages artifact, and deploys only on push (`.github/workflows/docs.yml:L1-L8`, L19-L43, L45-L55).
Its Pages build is intentionally a standalone package with a repository-name base path (`.github/workflows/docs.yml:L31-L43`).
The docs worklog says to keep `docs-site/` standalone, with no root JavaScript workspace or monorepo configuration (`ephemeral/worklog/20260914-issue174-docs-site.md:L1-L2`).
It also records a strict static boundary: no SPA fallback, root prerendering, and adapter-static enforce fully static output (`ephemeral/worklog/20260914-issue174-docs-site.md:L2-L3`).

The model-price workflow is the other shipped release-like automation. It runs daily or manually, checks out `main`, runs `just prices`, and has write permission (`.github/workflows/prices.yml:L1-L9`, L15-L28).
It refuses to publish if `main` moved during generation, if the generator touched anything beyond `internal/observation/model_prices_gen.go`, or if no valid reachable `vX.Y.Z` tag exists (`.github/workflows/prices.yml:L29-L61`).
When valid, it commits the generated file, increments the patch component of the latest reachable semantic tag, creates the next tag, and atomically pushes the commit and tag (`.github/workflows/prices.yml:L63-L72`).
This is concrete automation for one generated-data patch release; it is not evidence of a general feature-release pipeline.

## Current conversation directive

Directive authority: current user instruction, not repository source and not a claim that tooling already implements it.
After features or fixes merge, build required assets and run `go install ./cmd/gimbal`; update affected plugin/skill instructions and installed copies.
The distribution requirement is tool unannounced/local-machine distribution sufficient. Do not teach a public release pipeline, package registry, or plugin marketplace publication unless a later source or directive adds one.
The future skill should label this as a required operator sequence, while distinguishing the source repository, generated/build assets, and the installed binary actually used by the local machine.

Additional current user directive: builtin workflows must be well documented through the CLI, potentially by generating help from workflow function declaration comments; authoring must require useful, complete, appropriately detailed docs, and release verification must check that installed `--help` matches the workflow. Do not implement generator changes in this research task; reader 11 owns the generation-code investigation.
This adds a release proof obligation: after `go install ./cmd/gimbal`, invoke the installed command's help and compare it with the workflow declaration/help source that the build is meant to expose. The source segment does not yet define the generator or comparison mechanism, so the future skill must mark the check as a directive-backed requirement pending reader-11's source findings.

The operator sequence should preserve the repository's dependency order: regenerate bindings, format generated web output, build the frontend, build or install the command, then run the checks appropriate to the changed surface (`justfile:L4-L10`, L23-L30).
If a change affects browser behavior, the useful proof is a browser run against the built or live server, not only `go test`; the available recipe installs Chromium and runs Playwright (`justfile:L18-L21`).
If a change affects Go workflow linting, use the installed or freshly built Gimbal command's `lint` path, since both vet and hooks invoke that executable path (`justfile:L23-L26`; `lefthook.yml:L26-L36`).
If a change affects generated model prices, preserve the workflow's narrow target and race check; do not hand-edit or broaden the generated diff (`.github/workflows/prices.yml:L34-L49`).
If a change affects docs, run the docs package's own frozen-lockfile check and build, then treat Pages deployment as a separate push-only stage (`.github/workflows/docs.yml:L19-L43`, L45-L55).
When a generated web change is expected, inspect the diff for restored Gimbal-owned routes and components after generation; the regeneration worklog explicitly makes that restoration part of the chosen base strategy (`ephemeral/worklog/202609181700-skgo-050-web-regeneration.md:L1-L5`).
Do not put a proof script or captured run output under `ephemeral/`; the staged-content policy will reject those categories and the repository directs repeatable checks into package tests (`scripts/check-staged-content.sh:L49-L63`).
Do not claim a release merely because a tag exists. The only source here that creates tags is the guarded model-price workflow, and it creates a patch tag for that generated-data update (`.github/workflows/prices.yml:L51-L72`).

The web package's `prepare` script may run Svelte synchronization, while `check` explicitly runs synchronization and Svelte-aware type checking; build/release instructions should account for this package lifecycle (`web/package.json:L10-L18`).
The package has separate unit-test and Storybook commands, but the root `just test` invokes the package's test script and the root build invokes `vp build`; a future skill should name which one is evidence for the changed claim (`web/package.json:L10-L20`; `justfile:L4-L10`, L28-L30).
The module's comments are part of the build contract: `web/` is intentionally a Go package because it embeds the build, and ignored directories prevent accidental descent into frontend dependencies (`go.mod:L5-L7`).
The server's dev mode intentionally clears baked versions and marks registries as development to avoid reload loops; production and dev are related modes of the same composition, not independent app implementations (`web/server.go:L57-L76`).
The server's production mode renders pages in-process with the adapter-produced SSR bundle, then serves static assets around it (`web/server.go:L78-L91`).
Origin failures are explained at the HTTP boundary with a reverse-proxy remedy, so a local operator can distinguish an install/build failure from a browser-visible origin configuration failure (`web/server.go:L129-L160`).

## Gaps and conflicts

There is no manifest entry here for a release workflow that builds, tags, or publishes the main Gimbal binary. The prices workflow's patch tag behavior must not be generalized to feature/fix releases (`.github/workflows/prices.yml:L29-L72`).
The build recipe writes `bin/gimbal`, but the current directive separately requires `go install ./cmd/gimbal`; the recipe does not prove the installed executable was refreshed (`justfile:L4-L10`).
The sources do not define how installed plugin/skill copies are located or synchronized. That procedure is a future skill concern under the current directive, not an inferred existing script.
The sources describe dev proxy and embedded production modes, but they do not by themselves prove a deployed binary can serve a real browser session; use E2E or live runtime evidence for that claim (`web/server.go:L22-L39`, L78-L126; `justfile:L18-L21`).
The docs workflow proves Pages publication only for `docs-site`; it does not publish the Gimbal CLI (`.github/workflows/docs.yml:L19-L55`).
