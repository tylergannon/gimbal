## What is actually implemented

Tenacious is a YAML/legacy-JSON multi-step orchestrator. Its documented vocabulary distinguishes workflow, run, step, visit, asset, and session transcript; a workflow is explicitly a graph that can branch or loop, and a visit is a repeat caused by a question or feedback ([`ui-tenacious-USER_MANUAL--01-overview.md.txt:12-45`](ui-tenacious-USER_MANUAL--01-overview.md.txt#L12)). The bundled six-step workflow visibly loops `code → code_review → code` in its declared transitions ([`ui-tenacious-workflows--6step.yaml.txt:56-80`](ui-tenacious-workflows--6step.yaml.txt#L56)).

The shipped viewer is a read-only, four-level terminal file browser: runs → run detail → step detail → transcript. It has one screen at a time, no panes, no mouse, and Enter/Right drills down while Escape/Left backs out ([`ui-tenacious-USER_MANUAL--06-viewer-tui.md.txt:12-44`](ui-tenacious-USER_MANUAL--06-viewer-tui.md.txt#L12)). This is implemented as four screen identifiers and a navigation stack; selectable targets are explicitly parallel to rows, and each drill creates the next screen context ([`ui-tenacious-tenacious--viewer--tui.py.txt:91-109`](ui-tenacious-tenacious--viewer--tui.py.txt#L91); [`ui-tenacious-tenacious--viewer--tui.py.txt:394-417`](ui-tenacious-tenacious--viewer--tui.py.txt#L394)).

The run list is an information-dense multi-line card. It shows status, start/activity times, project, TLDR, the chronological visit path with per-visit duration, total visits and wall duration, git progress, plan checkbox progress, summed cost, and provider auth mode ([`ui-tenacious-USER_MANUAL--06-viewer-tui.md.txt:119-171`](ui-tenacious-USER_MANUAL--06-viewer-tui.md.txt#L119)). The implementation builds the same enrichment object, sorts by most recent activity, wraps the path without truncating history, and renders pure strings with variable block lengths ([`ui-tenacious-tenacious--viewer--runs_enrich.py.txt:323-350`](ui-tenacious-tenacious--viewer--runs_enrich.py.txt#L323); [`ui-tenacious-tenacious--viewer--runs_enrich.py.txt:700-757`](ui-tenacious-tenacious--viewer--runs_enrich.py.txt#L700); [`ui-tenacious-tenacious--viewer--runs_enrich.py.txt:869-920`](ui-tenacious-tenacious--viewer--runs_enrich.py.txt#L869)). Only the runs list auto-refreshes every 10 seconds; deeper screens are stable until reload ([`ui-tenacious-tenacious--viewer--tui.py.txt:327-379`](ui-tenacious-tenacious--viewer--tui.py.txt#L327)).

Run detail does not draw a graph. It lists steps in BFS reachability order from `start_step`, appends declared-but-unreachable steps, displays each step's `next_steps`, and shows visit counts. If `workflow.json` is unreadable it falls back to step directories and marks order/reachability unknown ([`ui-tenacious-tenacious--viewer--model.py.txt:415-487`](ui-tenacious-tenacious--viewer--model.py.txt#L415); [`ui-tenacious-tenacious--viewer--tui.py.txt:161-210`](ui-tenacious-tenacious--viewer--tui.py.txt#L161)). This is the only graph-like surface: adjacency is text (`→ next`) and there are no drawn nodes, edges, ranks, or layout coordinates.

Step detail separates visit facts from sessions. Visits show number, question presence, outcome, and mtime; sessions are step-level artifacts, sorted by mtime, and are the only selectable rows. The manual explicitly warns that a session can combine several visits and cannot identify which visit produced each line ([`ui-tenacious-USER_MANUAL--06-viewer-tui.md.txt:210-244`](ui-tenacious-USER_MANUAL--06-viewer-tui.md.txt#L210)). The model discovers Claude/Codex transcript paths and external user-home indexes, but does not expose visit-to-session mapping ([`ui-tenacious-tenacious--viewer--model.py.txt:546-616`](ui-tenacious-tenacious--viewer--model.py.txt#L546)).

Transcript drilling is implemented and shared with the CLI dump surface. Claude and Codex JSONL records become ordered `Turn` values; malformed records or unknown blocks degrade to `raw`/`event` turns instead of aborting the viewer ([`ui-tenacious-tenacious--viewer--transcripts.py.txt:4-12`](ui-tenacious-tenacious--viewer--transcripts.py.txt#L4); [`ui-tenacious-tenacious--viewer--transcripts.py.txt:275-339`](ui-tenacious-tenacious--viewer--transcripts.py.txt#L275)). Rendering labels text, reasoning, tool calls, tool results, errors, events, and raw data with indentation and blank separators ([`ui-tenacious-tenacious--viewer--render.py.txt:4-35`](ui-tenacious-tenacious--viewer--render.py.txt#L4)). The CLI offers `--list`, `--info`, `--visits`, `--sessions`, `--session PATH --dump`, and `--selftest`; there is no graph, timeline, zoom, or selection API ([`ui-tenacious-tenacious--viewer--__main__.py.txt:28-54`](ui-tenacious-tenacious--viewer--__main__.py.txt#L28); [`ui-tenacious-tenacious--viewer--__main__.py.txt:117-123`](ui-tenacious-tenacious--viewer--__main__.py.txt#L117)).

## Runtime model and requested dimensions

| Dimension | Evidence-backed result |
| --- | --- |
| Graph / hierarchy | Declared top-level workflow adjacency and BFS reachability are shown as text. No visual graph or hierarchy renderer. |
| Timeline | The run list has an ordered visit path and durations/wall total. There is no wall-clock row timeline, interval lanes, or overlap layout. |
| Run drilling | Implemented four-level read-only drill-down, with explicit selectable rows and keyboard navigation. |
| Rendering/layout library | Viewer imports Python stdlib (`curses` lazily, `argparse`, `dataclasses`, `pathlib`, `json`); runtime dependency is only PyYAML. No graph/layout/rendering package appears in the pinned dependency or viewer imports ([`ui-tenacious-requirements.txt.txt:1-4`](ui-tenacious-requirements.txt.txt#L1); [`ui-tenacious-tenacious--viewer--tui.py.txt:11-18`](ui-tenacious-tenacious--viewer--tui.py.txt#L11)). |
| Static vs dynamic | The viewer reads a frozen `workflow.json` inside each run, then augments it with observed visit directories and metadata. It does not render a pre-run static template. The manual maps screens directly to on-disk files ([`ui-tenacious-USER_MANUAL--08-run-directory.md.txt:22-83`](ui-tenacious-USER_MANUAL--08-run-directory.md.txt#L22)). |
| Edge meanings | `next_steps` is displayed as allowed adjacency. No typed edge model for contains, fork, supervision, steer, or joins exists in the viewer. |
| Selection / zoom | Keyboard Up/Down or j/k, wrapping across multiple targets; PgUp/PgDn, Space/b, g/G, r, Enter/Right, Escape/Left, q. No mouse, zoom, pan, URL node links, or two zoom levels ([`ui-tenacious-tenacious--viewer--tui.py.txt:356-392`](ui-tenacious-tenacious--viewer--tui.py.txt#L356)). |
| Repeated iterations | Visits are numbered directories under a step; the run card renders every visit in a chronological chain and a total. Step detail counts/reports visits. Retry and resume are runtime behaviors recorded in new visit directories, not separate visual node instances ([`ui-tenacious-tenacious--viewer--model.py.txt:503-543`](ui-tenacious-tenacious--viewer--model.py.txt#L503)). |
| Parallel execution | The orchestrator implements parallel composite parents with sorted substeps, concurrent threads, a parent `meta.json` containing `parallel`, `substeps`, `duration_s`, and `failed_substep`, plus fail-fast cancellation ([`ui-tenacious-tenacious--orchestrator.py.txt:3125-3145`](ui-tenacious-tenacious--orchestrator.py.txt#L3125); [`ui-tenacious-tenacious--orchestrator.py.txt:3219-3261`](ui-tenacious-tenacious--orchestrator.py.txt#L3219)). The viewer only models top-level `workflow.json` steps and scans `profiles/<step>`; nested composite session paths are under `profiles/<parent>/<substep>`, so this implementation does not present a composite child hierarchy ([`ui-tenacious-tenacious--orchestrator.py.txt:650-668`](ui-tenacious-tenacious--orchestrator.py.txt#L650); [`ui-tenacious-tenacious--viewer--model.py.txt:570-616`](ui-tenacious-tenacious--viewer--model.py.txt#L570)). |
| Supervision commands | The pinned viewer has no supervisor, steer, interrupt, cancel, command, or approval edge model. The run directory exposes prompts, stdout/stderr, question/answer, and `meta.json` as raw files ([`ui-tenacious-USER_MANUAL--08-run-directory.md.txt:85-111`](ui-tenacious-USER_MANUAL--08-run-directory.md.txt#L85)). |

## What transfers to Gimble

1. Keep an explicit, bounded drill path for detail: run → scope/step → session/turn → transcript. Map every selectable row to a typed target, so keyboard selection cannot drift from the content it opens. This pattern is simple, testable, and useful even when the primary run view becomes a graph.

2. Separate immutable run declarations from observed instances. Tenacious's frozen `workflow.json` plus visit directories makes it possible to show declared adjacency, reachability, and runtime counts while degrading safely when an artifact is unreadable. Gimble can carry this forward with a generated static manifest joined to run events.

3. Treat the run list as a compact operational summary, not as a second graph. The path chain, durations, cost, plan state, auth mode, and activity timestamp answer “what is happening?” quickly; width-aware wrapping preserves the complete chain ([`ui-tenacious-tenacious--viewer--runs_enrich.py.txt:869-920`](ui-tenacious-tenacious--viewer--runs_enrich.py.txt#L869)).

4. Keep transcript parsing/rendering independent from navigation. Tenacious's defensive normalized `Turn` model supports Claude/Codex format drift and lets TUI and CLI share output. Gimble can apply the same separation to event normalization, graph projection, and transcript/detail panels.

5. Preserve parallel failure truth in persisted metadata. Tenacious records parent/substep identity, duration, exit, cancellation, and failed child, and explicitly scrubs a cancelled sibling's success sentinel ([`ui-tenacious-tenacious--orchestrator.py.txt:3187-3200`](ui-tenacious-tenacious--orchestrator.py.txt#L3187); [`ui-tenacious-tenacious--orchestrator.py.txt:3263-3309`](ui-tenacious-tenacious--orchestrator.py.txt#L3263)). This is a useful invariant for Gimble's future parallel regions and join display.

## Limits and non-transferable parts

The TUI is deliberately a file browser, not a visualization system: it has no node/edge renderer, hierarchy layout, timeline lanes, graph zoom, or static pre-run view. Its text adjacency should not be mistaken for typed control/supervision semantics. Its “session per step” artifact boundary also loses exact visit attribution, which matters for Gimble's turn-level runtime graph.

Tenacious's orchestration code does implement parallel composites, retry budgets, health monitoring, and resume behavior, but those are runtime/file facts rather than viewer projections. The live parallel tests are source evidence only; they are gated on an environment variable and were not executed here ([`ui-tenacious-tests--test_parallel_fail_fast.py.txt:4-14`](ui-tenacious-tests--test_parallel_fail_fast.py.txt#L4)).

Current Gimble context is materially richer: the local direction calls for typed hierarchical edges, scope ownership, a wall-clock run projection, and static manifest plus live instances ([`recommendation.md:15-30`](recommendation.md#L15); [`recommendation.md:61-77`](recommendation.md#L61)). The web design leaves graph rendering, density, URLs, and phone layout undecided; F3 is currently a flat list and F13 is later ([`../../../docs/web-app.md:57-64`](../../../docs/web-app.md#L57); [`../../../docs/web-app.md:80-100`](../../../docs/web-app.md#L80)). Tenacious therefore supplies interaction and persistence patterns, not a ready-made graph design.
