## Relevant observations

1. The service appends events to an execution's event history. The history is a
   complete durable record used both for recovery and audit/debugging.
2. Events arise from external occurrences and commands generated by workflow
   code. The UI therefore has a useful distinction between an intended command
   and the later observed event/result.
3. Activity execution has multiple lifecycle events, but while an Activity is
   running/retrying the history may contain only its scheduled event until a
   terminal event is written.

## Transferable UI pattern

Represent planned/static operations and observed runtime events separately, and
make the boundary visible during live execution. A pending row can show that an
operation was scheduled without implying that it has started or completed.
Terminal success/failure/cancellation should be attached to the event instance,
not inferred from a parent region's status.

## Limits for Gimble

Temporal's server owns durable event semantics. Gimble should not invent a
server-like lifecycle for commands the runtime cannot observe. In particular,
static command extraction cannot prove process start, duration, exit status, or
output; those need an explicit runtime observation boundary.
