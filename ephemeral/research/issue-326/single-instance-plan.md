# Gimbal single-instance game plan — draft for Fable 5.1

This supersedes `single-process-plan.md`'s **per-project process** destination. Tyler's corrections are authoritative: one instance should be able to host an arbitrary number of projects, and it should be possible to use just one instance on a machine. **This is sufficiency, not enforced uniqueness: more than one instance must always be permissible.** Its communication endpoint and instance state must be configurable so independent instances can coexist, especially in tests. This is a design plan, not an implementation or a claim that issue #326's exact HTTP 500 mechanism is known. Gimbal is a local tool for one user and has no users to migrate. Coherence, simplicity, and useful functionality outrank security hardening, migration safety, and elaborate failure guarantees; none of those is a completion gate invented by this plan.

## Desired state

One long-lived Gimbal instance has one web/control surface and can admit many project directories. Within it, each project has separate observation, runs, conversations, and durable files. The CLI submits a workflow to a selected instance; a conversation agent uses that same CLI from its worktree, rather than a private in-server launch route. A run has both an owning project, where it is observed and recorded, and an execution workdir, where its agents work; a conversation's Git worktree does not silently become another project. The selected instance executes and exposes the run; invoking the CLI never starts another Gimbal runtime for the project. The web UI selects a project explicitly, then shows that project's runs and each conversation's durably associated runs. Multiple projects and multiple runs may be live together without confusing their IDs, controls, graphs, or histories. Independent instances with different endpoints/state directories are allowed for tests and separate uses. Short-lived CLI clients, provider harnesses, and commands launched by workflows are distinct OS processes, but they are not additional Gimbal *runtime owners*. This is not a multi-user server or a security boundary between projects.

The current `web.Runtime` is both server and project state (`web/runtime.go`); `BaseContext` injects a single project directory, observation registry, live-run table, and conversation manager. The generated `gimbal run` commands each create a new `NewRuntime`; the existing control discovery is under that project's `.gimbal/control/`. Conversations also have a separate path: `internal/conversation/manager.go` asks the agent for a structured `workflow` field, and `cmd/gimbal/workflows.go` supplies callbacks that invoke the workflow directly in the web runtime. That path shares a process today, but bypasses the CLI and gives it a different launch contract. It was introduced for the conversation prototype, not stipulated as the destination. This topology explains issue #326's two-listener failure but is not a reason to keep one listener/process per project. Both `ephemeral/research/api/API.md` and `docs/web-app.md` record the old one-project design and need updating to the accepted multi-project destination.

## The transition question

**Option A — ship a per-project owner first.** This is the shortest path to eliminate the exact 43840/43841 double-runtime arrangement, but it would codify per-project control discovery, listener flags, CLI routing, and URL assumptions just before replacing them. With no users to migrate, that throwaway interim architecture is not justified merely by issue #326.

**Option B — separate instance from project state and go directly to multi-project capability.** An instance owns its listener, control endpoint, lifecycle, and a map of project identities to project-local state. It reuses the existing per-project registry/run/conversation behavior behind that map. The launch API and viewer route name a project, so no per-project listener or process is introduced. This is larger than A, but it changes the hard boundary only once. **Recommendation: B**, built in graduated slices that need not each be a releasable product.

## Implementation game plan if B survives review

These are cumulative outcomes, not a detailed implementation sequence or independent release gates. Prefer the smallest idiomatic Go design that makes each outcome real. Do not turn local single-user usage into an authentication, policy, isolation, or distributed-systems project.

1. **One instance, many project states.** The listener and control endpoint belong to the instance, while runs, conversations, observation, and files belong to a project. Admitting another project creates project state, not another server. The instance can host simultaneous runs in different projects; another instance with its own configurable endpoint/state can coexist.
2. **Project identity reaches every surface.** A CLI-supplied project directory maps to one stable project identity, including ordinary path aliases. The page can select a project; run lists, streams, controls, conversations, and links stay within that selection. The selected project's history reopens after an instance restart. Browser routes use project identity in the path, consistent with the existing no-query-parameter rule.
3. **The CLI talks to the instance.** `gimbal run` submits a named workflow and its inputs to the selected instance, where the workflow executes and becomes observable. The CLI can report the launched run and, when requested, follow its result. The chosen instance is explicit or comes from a simple configured default; there is no implicit hunt for an owner and no second runtime created by a CLI invocation. The CLI supplies run choices such as model and execution workdir; the instance's startup environment supplies inherited executables, provider configuration, and credentials. Make that distinction visible in CLI help so a client shell's environment is not mistaken for the run's.
4. **Conversations use that same CLI.** An agent in a conversation worktree invokes `gimbal run` for the conversation's owning project, with its separate workdir. The resulting run is durably linked to the conversation, so a reload shows the right run and status without parsing agent prose. Delete the conversation-only structured `workflow` response and the direct-launch callbacks; chat remains chat, not an alternate workflow API.
5. **Live observation has one owner.** The instance that starts a run serves its live state instead of rereading a half-written run from disk. Completed history remains readable. Close the same-process run-publication window as its own supported-path defect without claiming it caused the historical #326 failure. A workflow panic becomes that run's recorded failure rather than ending the host and unrelated runs; direct `gimbal.Run` can retain its existing behavior. Change the evaluator to use one instance for launch and viewing.
6. **Decide the scope of authored workflows.** Stock workflows can run in the stock instance because their Go bodies are already compiled there. For custom workflows, choose whether an instance built with them is the normal authoring model or whether separate workers are worth their added contract. Also state how `run-prompt` and direct `gimbal.Run` coexist with the hosted mode. Do not imply all Go closures can be sent through the CLI.
7. **Show the intended product running.** With a built binary, start one instance, admit projects A and B, run workflows concurrently through the CLI, observe and control each in its own page, and reopen both histories after restart. Confirm a run uses the instance's documented startup environment and its CLI-supplied run choices. Cause a workflow panic in A and show it fails while B's run and page remain usable. Launch a run from a conversation in B's worktree and verify the B-owned run and durable conversation link. Start a second configured instance and show that it remains usable without confusing client routing; attempt to attach the same project through it and verify the chosen refusal or forwarding behavior. Update the accepted design records, evaluator, and command help to match what actually works. Separately resolve issue #326's original causal diagnosis or explicitly reframe the issue; architecture alone is not proof of the exact historical 500 mechanism.

## Decisions that must be resolved, not guessed

- **Instance bootstrap:** Prefer an explicitly started persistent instance with `gimbal run` as a client, unless auto-start is itself desired. A simple default endpoint is fine; explicit selection must remain possible so multiple instances work.
- **Two instances, one project:** This is different from permitting two instances on one machine. The smallest clear contract is one active owner of a given project's live runs; a second instance can still host other projects. Decide whether the second instance refuses that project or routes to its owner. Genuine simultaneous writers to one project need a separate reason and design, not an accidental promise.
- **Arbitrary authored workflows:** Decide whether custom workflows are linked into the chosen instance binary or run as workers whose results appear in that instance. This affects whether the initial product covers all authored workflows or only the stock binary.
- **Issue #326 disposition:** Retained evidence proves two Gimbal runtimes shared one project and the initial empty page was healthy. It does not retain the raw 500 cause. Do not close the issue as diagnosed merely because the new topology works. Either obtain Tyler's approval to reframe it as a topology defect with exact file error unknown, or collect bounded forensic evidence and a focused regression for the actual 500 mechanism.

## What feedback should change this plan

Argue against B if multi-project routing or authored-workflow execution makes a transitional A genuinely valuable, and against A if its shortcuts would be discarded. Test whether each outcome belongs in the plan or adds machinery without functional value for one local user. Distinguish a proven #326 fix from a plausible architectural prevention and from a forensic diagnosis.
