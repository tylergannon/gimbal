# Gimble single-instance game plan — draft for Fable 5.1

This supersedes `single-process-plan.md`'s **per-project process** destination. Tyler's corrections are authoritative: one instance should be able to host an arbitrary number of projects, and it should be possible to use just one instance on a machine. **This is sufficiency, not enforced uniqueness: more than one instance must always be permissible.** Its communication endpoint (socket/port and relevant instance state) must be configurable so independent instances can coexist, especially in tests. This is a design plan, not an implementation or a claim that issue #326's exact HTTP 500 mechanism is known.

## Desired state

One long-lived Gimble instance has one web/control surface and can admit many project directories. Within it, each project has separate observation, runs, conversations, and durable files. The CLI submits a workflow to a selected instance; a conversation agent uses that same CLI from its worktree, rather than a private in-server launch route. The selected instance executes and exposes the run; invoking the CLI never starts another Gimble runtime for the project. The web UI selects a project explicitly, then shows that project's runs. Multiple projects and multiple runs may be live together without confusing their IDs, controls, graphs, or histories. Independent instances with different endpoints/state directories are allowed for tests and separate uses. Short-lived CLI clients, provider harnesses, and commands launched by workflows are distinct OS processes, but they are not additional Gimble *runtime owners*.

The current `web.Runtime` is both server and project state (`web/runtime.go`); `BaseContext` injects a single project directory, observation registry, live-run table, and conversation manager. The generated `gimble run` commands each create a new `NewRuntime`; the existing control discovery is under that project's `.gimble/control/`. Conversations also have a separate path: `internal/conversation/manager.go` asks the agent for a structured `workflow` field, and `cmd/gimble/workflows.go` supplies callbacks that invoke the workflow directly in the web runtime. That path shares a process today, but bypasses the CLI and gives it a different launch contract. It was introduced for the conversation prototype, not stipulated as the destination. This topology explains issue #326's two-listener failure but is not a reason to keep one listener/process per project. `ephemeral/research/api/API.md` records the old one-project server design, so it will need an explicit design amendment when a new contract is accepted.

## The transition question

**Option A — ship a per-project owner first.** This is the shortest path to eliminate the exact 43840/43841 double-runtime arrangement. A project-scoped active-writer claim plus in-owner launch can use most of today's `Runtime` shape, and the single-process initialization race can be tested. But it would codify per-project control discovery, listener flags, CLI routing, and URL assumptions just before replacing them. The extra migration and user-facing interim semantics are not justified merely by issue #326. It is defensible only if we deliberately need a small, independently released containment fix before settling multi-project identity and workflow-loading semantics. Such a release must be labeled transitional, not the destination.

**Option B — separate instance from project state and go directly to multi-project capability.** An instance owns its listener, control endpoint, lifecycle, and a map of project identities to project-local state. It reuses the existing per-project registry/run/conversation behavior behind that map. The launch API and viewer route name a project, so no per-project listener or process is introduced. This is larger than A, but it changes the hard boundary only once. **Recommendation: B**, with an internal extraction of project state as the first implementation slice, not a shipped per-project singleton architecture. If #326 needs immediate containment, change its evaluator to launch and browse one runtime, without first shipping A's new process contract.

## Implementation game plan if B survives review

1. **Separate instance and project lifetimes.** Move listener/control/discovery and instance cancellation above the project. Load project state lazily from a physically identified project directory and keep it until instance shutdown; project-local contexts own registries, run controllers, conversation managers, and `.gimble` files. Project admission must not start a second server. One project failing to load should not silently poison another project's page. Several instances may coexist with distinct configurable endpoints/state; do not install a machine-global singleton lock or block a second instance merely because one exists. Same-project attachment/writes are a separate contract below.
2. **Give requests unambiguous project identity.** Resolve an existing project directory to its real filesystem identity, not merely `filepath.Abs`: symlink and relative aliases to one directory map to one project state; a symlink retarget cannot silently switch an admitted identity. The web UI uses a stable, opaque project ID in the URL path, not a query parameter or arbitrary filesystem path supplied by a browser. Local CLI control requests identify a project path; the instance admits it and maps it to the project ID. Runs, streams, controls, conversations, and links resolve the selected project before looking up a run ID. The root page can select among admitted projects. Persist enough association to reopen history after restart; stale discovery is not active ownership.
3. **Launch built-in workflows in that instance through the CLI.** The stock Gimble binary already compiles its built-in workflow bodies. Adapt generated CLI commands so they validate flags/model choices, submit typed inputs to a specifically selected instance, and either return an observable run ID promptly or follow only their submitted run to a terminal result. The instance validates before admission, launches with its project state, and returns a run ID only after the run is observable. A stable client launch ID bound to the selected project's identity and the selected instance's **process incarnation** permits recovery from a lost response while that process remains alive. A fresh process at the same endpoint has a new incarnation ID: after an ambiguous acceptance followed by restart, the client reports unknown outcome and never retries automatically. A client never silently re-submits under a new ID or fails over to another instance. A client Ctrl-C targets its run, not the instance or another project. A following CLI's exit status reflects a known terminal result; unknown outcome is a distinct error. A named default instance profile is allowed, but scanning healthy instances and choosing by PID/reachability is not: without explicit selection or a configured default, the CLI fails with a useful instance-selection message.
4. **Make Conversations a CLI caller, not another launch authority.** A conversation agent invokes the same Gimble CLI from its conversation worktree, identifying both that project and the intended instance through the CLI's normal selection contract. It can receive a run ID without holding the chat turn open until completion; the page links that run through normal instance observation. Remove the structured conversation `workflow` request and the review/implementation callbacks that launch workflows directly from the server. Conversation messaging remains a conversation, not a second workflow-launch protocol. A normal CLI invocation and a conversation-agent invocation with equivalent inputs must resolve to the same selected instance and run semantics; neither starts another Gimble runtime. Do not make the selected instance implicit merely because the agent happens to be hosted by it.
5. **Define local control and browser trust boundaries before carrying execution authority.** Mutating CLI launch/control stays on a Unix-domain socket, not a configurable TCP control port. Configure each instance's private state directory/socket path; require the directory to be owner-only, protect socket and discovery/profile files, and verify the selected endpoint belongs to the expected local user and process incarnation before sending credentials or project paths. Same-UID local clients are the initial CLI trust principal; a multi-user service is not implied. Do not copy instance-selection secrets into workflow child environments. The loopback web port is reachable by other local users, so `Origin` alone is insufficient. Protect *reads and mutations* with a per-instance HTTP authentication challenge and high-entropy credential (initially Basic over loopback), obtained by the owner from the private instance profile and entered through the browser's challenge. HTTP authentication protection spaces include the scheme, host, and **port**, so two instances can retain separate browser credentials; ordinary cookies cannot provide that isolation. Do not use a cookie bearer credential. Preserve origin/CSRF checks for mutations as a second boundary. Do not put credentials in project files, workflow logs, or URLs; reject non-loopback plaintext web binding. The browser cannot reach the control UDS; a configurable *web* port remains independent of that private socket. Refuse insecure endpoint state rather than silently downgrading. Verify an unauthorized local client, a spoofed or mismatched profile, a cross-origin browser request, and a same-origin request without HTTP authentication cannot read privileged data, admit a project, launch work, or receive environment material. Browser proof must pair with two instances on separate ports simultaneously, then visit an adversarial third loopback port and show it receives no reusable Gimble credential and cannot replay one to either instance.
6. **Preserve execution authority across projects.** Today a workflow inherits the invoking process's environment, including credentials, `PATH`, and provider state. Moving execution to a persistent instance cannot silently substitute its startup environment. Capture the CLI caller's execution environment for that run only after selecting and verifying the UDS endpoint; keep secrets in memory only, and pass configuration explicitly to adapters and child commands. Never mutate process-global environment to switch projects or persist the captured environment in run logs or discovery. A conversation agent's CLI call follows this same rule. Refactor current `os.Getenv`/implicit `exec.Cmd.Env` consumers where necessary, or reject a requested configuration the host cannot honor. Prove simultaneous projects with different provider/executable markers do not leak or cross-use them.
7. **Contain run failure inside the shared instance.** Current `gimble.Run` records a workflow panic and then re-panics, intentionally killing a single-run process. An in-instance launch boundary must recover that panic into that run's terminal result after the existing recording path, while leaving other projects' runs and controls alive. Prove with a deliberate duplicate-scope-key panic in project A while project B continues. Arbitrary authored code can still call `os.Exit` or corrupt process-global state; admitting it in-process is a trust decision, not something panic recovery solves.
8. **Make ownership and observation coherent.** An instance never disk-replays an active run it itself started. Close the narrow directory-publication/registration gap when a page lists runs in that project; do not mask arbitrary read errors. Historical runs remain disk-readable. Remove active-foreign-run behavior as a supported live path, but retain read-only completed history. Update the issue #326 evaluator to launch and browse through one instance.
9. **Settle other execution paths before claiming broad completeness.** `run-prompt` currently creates its own headless runtime over a temporary project, and public `gimble.Run(gimble.Project(...))` can write without `web.Runtime`. They need an explicit coexistence rule; they need not be outlawed merely to make the stock instance multi-project. User-authored Go workflow bodies cannot be shipped over RPC as closures. They must be compiled into the chosen instance binary, or run in separate execution workers that do not become a second observation/control owner for the same project. The first path is simpler but trusted and restart-bound; the second permits isolation but requires a real worker/host event contract. Decide which is part of the promised product before claiming all workflows work through one instance.
10. **Version and prove the client/instance contract.** A newly installed CLI can reach an old persistent instance. A protocol version and workflow/input capability check must reject incompatibility before transmitting environment or project data, admitting a project, or starting a run, with a clear restart/upgrade instruction; never auto-kill an instance with active work. A new client must recognize a missing legacy handshake and must not fall back to old launch behavior. Replace two-listener directions in the evaluator and Gimble skills; generated command help must match actual launch/lifecycle behavior. Prove with a built binary: empty project A, start a run in A from CLI, observe and steer it in the same instance, admit project B, run B concurrently, verify pages/controls/history remain isolated, terminal CLI status and Ctrl-C affect only the intended run, then restart and read both histories. From a conversation in B, have its agent use the same CLI to launch a run in B and follow its returned ID on B's page; with two instances live, verify explicit selection does not silently route that call to the other instance. Test path/symlink aliases, a deliberate A panic while B continues, distinct run environments, both new-client/old-instance and old-client/new-instance mismatch, two independent instances with configured endpoints/default-selection ambiguity, same-project double admission, and a dropped launch response while two instances remain live. Also drop the response, kill and restart that instance at the same endpoint, and prove the old client does not execute a second run and reports unknown outcome. A deterministic test at the run-registration boundary must never produce a runs-page 500. Use cheap models for live proof and name them.

## Decisions that must be resolved, not guessed

- **Instance selection and bootstrap:** A persistent instance and a CLI that returns an exit status cannot be the same foreground process after the run ends. Prefer explicit `gimble` server start, then `gimble run` as client, unless auto-starting a detached instance is a product requirement. Multiple explicitly selected instances remain allowed. Headless one-shot commands need a clear coexistence rule, not a machine-wide ban.
- **Two instances, one project:** The historical two-runtime/same-project active reader-writer path is unsafe, but forbidding a second *instance* is not an acceptable fix. Options are (a) one active writer for that project, while the second instance remains fully available for other projects and either forwards to the owner or refuses only that project attachment, or (b) genuine multi-writer/foreign-live observation coordination. Recommend (a) as the smaller contract unless Tyler wants concurrent independent writers to the same project. This is a project attachment rule, never a machine singleton rule; neither option may yield a mysterious 500.
- **Arbitrary authored workflows:** Decide whether custom workflows are linked into the chosen instance binary or execute as workers under its ownership of observation/control. This affects whether B covers all authored workflows or initially covers only the stock binary.
- **Issue #326 disposition:** Retained evidence proves two Gimble runtimes shared one project and the initial empty page was healthy. It does not retain the raw 500 cause. Do not close the issue as diagnosed merely because the new topology works. Either obtain Tyler's approval to reframe it as a topology defect with exact file error unknown, or collect bounded forensic evidence and a focused regression for the actual 500 mechanism.

## What feedback should change this plan

Argue against B if multi-project routing or authored-workflow execution makes direct migration materially riskier than a transitional A; argue against A if its shortcuts would have to be discarded. Test whether project-scoped active-writer exclusion is necessary, or whether a weaker contract meets #326 without forbidding useful testing. Identify what is truly necessary for one multi-project instance rather than adding unrelated features. Distinguish a proven #326 fix from a plausible architectural prevention and from a forensic diagnosis.
