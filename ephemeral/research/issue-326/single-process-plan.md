# Superseded per-project Gimble plan (Fable 5.1 round 01)

This draft is preserved as the starting point of the review conversation. The current recommendation is `single-instance-plan.md`: one instance can host many projects, and multiple instances remain permissible.

## Decision and boundary

One Gimble **runtime** owns a canonical project `.gimble` directory at a time. That runtime owns the web page, control socket, observation registry, and every live workflow run in that project. `gimble run` invoked from another shell is a short-lived client process: it executes no workflow body and writes no run record there. Agent harnesses and workflow-launched commands are still subprocesses; “single process” does not mean eliminating those external tools. The supported raw library `gimble.Run` path is also a project writer and obeys the same ownership claim, though it need not host a web page.

This follows the server-first contract in `ephemeral/research/api/API.md` and Tyler's explicit correction in `issue.md`. It does not assert that the historical issue #326's exact file error is known. The empty first page worked; the later 500 occurred in an evaluation with two runtime owners. The plan removes that topology and separately proves the remaining same-process publication window. Issue #326 currently requests diagnosis of the observed 500 and a regression test once its cause is known. Therefore single-owner proof alone **does not close #326**: before closure, either Tyler explicitly accepts a revised issue disposition that identifies invalid topology as the defect while leaving the precise file error unknown, or a bounded dual-process forensic reproduction with raw server error capture identifies the mechanism and yields its focused regression check. The latter is diagnostic only; it does not make foreign active-run replay a supported product mode.

## Behavior to implement

1. **Establish exclusive project ownership for every writer.** Canonicalize the project path and acquire a project-scoped, OS-enforced claim before publishing either listener or creating a run directory. Hold it for the runtime lifetime; release on orderly shutdown and automatically on process death. A second `NewRuntime`, even with another port or `--no-web`, fails with an actionable “project already owned” error. Treat stale discovery as a hint, never ownership. A raw `gimble.Run(gimble.Project(...))` without a runtime acquires the same claim for its run lifetime. The owning runtime passes a private ownership capability through the run context so its concurrent `Runtime.Run` calls share the owner's claim rather than contending with themselves. For standalone raw runs derived from one `Project` context, share the claim until their last concurrent run ends; independent processes still contend. Ensure failed startup and failed raw-run initialization release claims. Do not mistake a web-port conflict for a project lock.
2. **Launch inside the owner.** Add a narrow launch operation to the existing local control socket. The owner binary has built-in workflow bodies compiled in; a request identifies the workflow, typed inputs, model selections, canonical work directory, and a client-generated launch ID. The owner validates before accepting work, deduplicates the launch ID for its lifetime, invokes its existing `Runtime.Run` in a goroutine, and returns the run ID only once registration is observable. A lookup of launch ID recovers acceptance and terminal result after a dropped response; a retry with the same ID never reruns the body. The client must report an ambiguous result and not resubmit under a new ID when it cannot reach the owner. No dynamic plugin host or second web listener is needed. A custom binary can host only workflows it compiled.
3. **Route CLI commands deterministically.** `gimble` without a subcommand starts the persistent owner and keeps serving after runs end. `gimble run WORKFLOW ...` requires a healthy owner for that project, submits the run, and follows *that run* to a terminal outcome. If no owner exists, it fails with a command to start `gimble`; it does not create a transient web server that disappears on command exit. Preserve an explicitly headless direct mode (`--no-web`) only when no owner exists: that command is the sole owner for its run and exits with its result. If an owner exists, explicit listener flags (`--port`, `--uds`, `--no-web`) that cannot be honored are rejected with the owner's actual endpoint rather than ignored. Preserve nonzero CLI exit for failed/cancelled runs and distinguish launch failure from workflow failure. On Ctrl-C, cancel only the submitted run, not the shared owner; an accidental client disconnect does not cancel it. A competing owner startup fails the claim and never becomes a second owner.
4. **Make the runs page owner-consistent.** While a run is active, the page and control API use the owner's in-memory store. Completed and pre-existing history remain readable. Remove the active-foreign-run behavior and its test as an endorsed contract. Serialize the small run-directory publication/observation-registration section with the owner's runs-list snapshot selection, so its page cannot scan an initializing directory and fall through to disk replay. Do not hold this lock while an agent works or while rendering the whole page. Do not convert arbitrary read errors into a silent empty state. Keep the unrelated error-page/polling recovery question separate unless same-process proof shows it is required for this work.
5. **Align product-facing workflows and examples.** The issue #326 evaluation must start one Gimble owner, then launch work through it and browse that same listener. Remove `validate-product`/installed-skill guidance that recommends a standalone viewer plus a delegated listener over one project. Update generated command help and relevant tests with the new owner/client semantics; generator source owns generated commands. Preserve `run-prompt`'s intentionally separate temporary log directory, and check examples/library users before changing their process model.

## Proof for this architecture, then issue disposition

- Focused tests: a second runtime for the same canonical project is refused across ports and `--no-web`; raw `Run` contends with a runtime or a raw `Run` in another process; two concurrent raw runs sharing one `Project` context can run under one claim; stale discovery does not block a new owner; failed startup releases ownership; simultaneous owner startups do not create two owners.
- End-to-end built binary: start `gimble` on an empty project, see the empty page, submit a cheap-model built-in workflow from another shell, verify only the original owner PID writes/hosts the run, see its live state and a successful/failing terminal outcome on the same page, and verify the client exit status. Test another submission after the first run ends, concurrent runs, Ctrl-C isolation, a dropped launch response with same-ID recovery, and restart/history reading. Check absent-owner failure and the distinct headless direct mode.
- A deterministic same-process test holds run initialization at the directory-publication/registration boundary while requesting the runs page. It must not produce a 500 or replay an uninitialized run. Browser smoke checks empty → live → ended on one listener. `just build` precedes Go/web checks because generated frontend assets are required.
- Re-run the issue #326 validation scenario with one owner/listener. This proves the revised topology and observed behavior, not which of the two unlogged foreign-reader races caused the old screenshot. Do not mark the original issue diagnosed/closed without the explicit disposition decision or forensic evidence described above.

## Scope and open decisions for review

- The launch request/response must preserve typed parameters, model overrides, validation, and terminal errors without recreating a second per-workflow parsing scheme. Prefer adapting the existing generated command path and the already-used conversation in-runtime launch pattern; keep new API surface minimal.
- An existing owner's chosen listener settings are authoritative. Decide the exact user-facing endpoint format for port versus UDS, but explicit incompatible flags must never silently appear to work.
