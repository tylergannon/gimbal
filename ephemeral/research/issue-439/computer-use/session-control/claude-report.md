## 1. Answer to the lane question

**Observation-backed conclusion:** In this build, the `codex_app` tools (`create_thread`, `send_message_to_thread`, `wait_threads`, …) are **client-executed dynamic tools owned by the desktop app**. They are only reachable from inside a turn the desktop app is already running: the Codex core emits an `item/tool/call` server request back to its client (the desktop), or the model calls the bundled `codex_app` MCP server, which forwards over a desktop-owned Unix pipe that is (a) peer-authorized by a native macOS addon, (b) only usable when the desktop itself has exported the pipe path into the environment of the core it launched, and (c) requires thread/turn metadata supplied by the executor. The bundled plugin is proprietary, RSA-signed, and switched on by the desktop only for the local host. No official doc describes a plugin-facing API to create or steer desktop sessions; third-party plugins are documented to consist of skills, MCP servers, hooks, and browser extensions, with host sandbox/approval applied.

**Inference (mine, for the parent to validate):** A user-installed Gimbal plugin cannot legitimately expose a job entrypoint *into* desktop-owned sessions. A plugin's MCP server runs as a child of the Codex core, is called by the model, and has no supported way to open the desktop's pipe (peer authorization + env not forwarded to arbitrary MCP servers) nor to reach the desktop's `item/tool/call` handler. The one direction a plugin does have is *inside-out*: once a desktop session is running, the model inside it can call `codex_app` tools (and, if a plugin MCP server is installed, that plugin's tools) subject to approval prompts. Externally-initiated control exists only through distinct, non-plugin mechanisms (section 3).

## 4. Observations vs inferences on the specific sub-questions

1. **"Are plugin tools merely client-invoked?"** Observation: `codex_app` tools reach the desktop either as `item/tool/call` server requests to the desktop client (C1, C5) or as MCP `tools/call` from the model via the bundled server, which the desktop then handles with the same `callDynamicAppTool` (C7, C10 `callTool:(e,t)=>…callDynamicAppTool(e,t)`). Both are model-initiated inside an existing turn. Inference: yes, client-invoked in both routes; the MCP route is a bridge for the model, not for external software.
2. **"Can a user plugin legitimately expose a job entrypoint into desktop-owned sessions?"** Observation: a user plugin can contribute skills, MCP servers, hooks (C15). An MCP server receives only allow-listed env (C16) and the desktop clears/sets `CODEX_APP_TOOLS_PIPE_PATH` itself (C10); the pipe rejects peers failing native authorization (C11); the bundled server also needs executor thread metadata (C8). Inference: no legitimate entrypoint. A plugin's process could at most act *within* the turn that called it. Nothing observed grants a plugin the ability to start a turn, steer, or cancel a desktop thread from outside.
3. **"Trace create_thread/send_message/read/wait."** Observation: desktop side is C5-C6 (routing) and G (`create_thread` result schema at `main@off2688400..`, excerpt G: `type:\`dynamicToolCall\`…namespace:\`codex_app\`…tool:\`create_thread\``); the actual thread creation happens in renderer code (`dynamicAppTools.dispatchToolCall`) which is not in `main-39FdJ_vp.js` and was not extracted.
