## What is established, and what is not

The fetched documentation describes app-server as an interface for deep integration inside the caller’s own product (cached `app-server.md`, lines 5–8); its connection/transport sections do not promise attachment to the installed desktop. They explicitly call WebSocket experimental and unsupported (A). The public implementation provides the generic session-control half: initialize a connection, start/resume threads, begin and steer turns, subscribe to their events, and interrupt turns. The exact public attachment mechanisms are WebSocket to an explicitly exposed server and WebSocket-over-Unix-socket to an explicitly exposed control socket. A newly spawned stdio app-server is a separate runtime.

The desktop-owned session plus native Computer Use combination is **not established by these public sources alone**. The unresolved edge is the installed desktop's hosting contract: whether it accepts an additional external client, and whether a thread initiated by that client gets the desktop's native configuration, plugin broker, attestation, and tool execution wiring. Loaded-thread rejoin has stronger source support for retaining existing runtime state than a fresh externally initiated `thread/start`, but neither is a live desktop compatibility result here.

A plugin MCP subprocess and a native desktop tool are different roles. The former exposes tools for the agent to invoke; the latter may already possess an application-owned dispatcher. The parent's separate inspection of first-party `codex-app-tools` must determine its authorization boundary. This lane does not assume its session-control tools can be invoked externally by an ordinary plugin. It also does not rule that out: a desktop-launched third-party plugin might satisfy implementation-level ancestry checks, but those checks and whether the interface is public require the desktop-lane evidence. “External” is not itself a trust classification. A pre-existing queue-polling agent was not investigated or substituted for user-requested external initiation.

Smallest unanswered question: **Does installed desktop build 20052 expose a supported entry point to an ordinary third-party plugin/external process that creates a desktop-owned thread through the same native setup path used by the app?** If yes, its authorization, event delivery, steer, and interrupt contracts need confirmation. If it exposes only a raw app-server socket, the next exact question is what desktop setup an external `thread/start` must receive for native Computer Use. Public transport support alone does not answer either.
