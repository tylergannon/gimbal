# Mixed operating systems and remote computer use

[Back to TL;DR](../proposal.md)

**Keep placement in the backend and native session creation inside the provider's desktop.** One authored workflow can build on Linux, submit a macOS computer-use task, and check its result back on Linux. The server tracks one run throughout. The local Codex desktop worker now demonstrates the provider submission path; connecting it to a mixed-platform backend is the next integration boundary.

## Recommended arrangement

A macOS worker runs in the intended user's desktop environment. Codex launches the Gimbal MCP adapter; an external Gimbal client submits work to that adapter, which asks Codex to create and manage its own task. The owner task stays loaded but its agent need not poll or spend turns dispatching work. Linux execution uses the backend's ordinary execution units.

```text
Gimbal server → backend run
                  ├─ Linux task → ordinary process/container/job
                  └─ macOS task → Gimbal desktop adapter → Codex native session
```

[PR #440](https://github.com/tylergannon/gimbal/pull/440) supplies the local adapter with start/read/message/cancel, a request ledger, and saved-app-permission preflight. Two fresh `gpt-5.6-luna` sessions natively captured and operated the actual Chrome app without observed per-run approval. A separate active task received a message and was interrupted by archive-and-stop; its observed foreground process stopped. This is evidence for those paths, not arbitrary descendant containment or every active-turn steering state. [Implementation evidence](../computer-use/session-control/implemented-worker.md) and [worker contract](../../../../plugins/codex-desktop/README.md).

The demonstrated deployment registers the shipped executable as ordinary MCP in a trusted project. The package includes plugin metadata, but marketplace install/reload has not been exercised. It uses a private version-dependent bridge, local Unix ingress, and a loaded owner; it is not yet a `HarnessAdapter`. Keep these details inside the provider integration. The central server should never import or understand Codex's private IPC.

## Provision once; fail explicitly during unattended work

Explicit worker setup grants macOS access, persists native permission for the actual target apps, and provisions the specific MCP binding tool. These are separate permissions. Saved app approval is a prerequisite, not a guarantee of screen access, provider policy, or permission for every future action. Do not write the native consent store or approve dialogs automatically.

Declare the task's required apps before submission. The current adapter rejects a missing saved approval before creating a task. If a task nevertheless requests approval, its next `read` attempts archive-and-stop and reports `approval_required` with whether cancellation was confirmed. **The integrating backend must keep reading active tasks**; the adapter has no autonomous approval watcher. An unanswered sensitive-action request or a permission change must fail visibly and retain unresolved cleanup, rather than leave an unattended run waiting indefinitely. This is ordinary provider observation, separate from the server's event subscription.

One live acceptance scenario per advertised worker capability is sufficient: create a fresh task through the actual ingress, capture/input on its provisioned target, observe completion, and cancel a still-active owned task. The demonstrated app is Chrome, which the desktop marks with a Chrome-specific native surface. Before a workflow depends on a non-Chrome app, repeat the fresh-session check with that actual app and its saved permission. Recheck the applicable small scenario after desktop changes; no general permission framework is proposed. The earlier [authorization investigation](../computer-use/findings.md) explains why spawning a CLI via SSH or a sibling LaunchAgent was insufficient. Launchd may supervise future worker availability, but cannot substitute for desktop-launched bridge ancestry or proven provider access.

## Bind native identity before the first work starts

A full backend must **allocate the native task without starting workflow work, durably bind its native ID to the run/task/attempt, then dispatch under the run's stop-intent gate**. Provider-enforced allocation-before-turn is required; an equivalently recoverable provider-idempotent creation can satisfy the same no-orphan claim. A prompt telling the agent to wait is not that gate.

The current worker does not have this capability. It saves a local request record, calls `create_thread` with the actual prompt, then saves the returned native ID. If creation starts work but the reply is lost, the local ledger retains an unknown outcome without an addressable native task. Its request ID is not a provider idempotency key. The worker's fixed 30-second call timeout can trigger this gap even when creation eventually succeeds; tuning that timeout narrows one trigger but cannot repair lost-reply ownership. Ordinary MCP `create_thread` does not expose the desktop's internal allocation-without-first-turn hooks, and no usable route to those semantics has been demonstrated. Sources: [current local start path](../../../../plugins/codex-desktop/lib.mjs) and [saved desktop creation trace](/Users/tyler/Documents/Codex/2026-10-09/gimbal-session-control-research/validation/desktop-create-thread-trace.md).

This is the next provider integration gate before advertising a fully owned unattended backend. The backend/caller must preserve an uncertain current start and its desktop reservation; the current worker itself does not enforce that reservation. Do not retry it, declare it cancelled, or release its reservation without resolving native identity and cessation. The merged worker remains experimental while that dependency is unresolved. Completed-response native tests establish permission and control behavior, not recovery from this lost-creation-reply window.

## Named environments place work; roles choose the agent

The active runtime-backend work already supplies the authoring seam: `ExecutionBackend.Resolve` resolves a named environment; `InEnvironment` selects it for sessions, commands, and services; `ExecutionEnvironment.Harness(role)` selects the role's adapter inside that environment, and `Start` dispatches its process work. The workflow can use a Linux context for build/check commands and a macOS context for a native session. Roles remain cognitive/model bindings, not aliases for machines. Reuse existing roles rather than invent OS/provider names.

This source is **unmerged work** on `codex/temporal-container-backend`, distinct from the mainline compiled Temporal example. The three cited files are committed at `013559e85701cb424696b41fd396391a05a223ec`: [execution API](https://github.com/tylergannon/gimbal/blob/013559e85701cb424696b41fd396391a05a223ec/execution.go), [runtime session binding](https://github.com/tylergannon/gimbal/blob/013559e85701cb424696b41fd396391a05a223ec/session.go), and [Temporal backend](https://github.com/tylergannon/gimbal/blob/013559e85701cb424696b41fd396391a05a223ec/internal/execution/temporal.go). A [local checkout link](/Users/tyler/.codex/worktrees/gimbal-temporal-backend/gimbal/execution.go) is provided for editing convenience. The coordinating task owns the [parallel concrete API draft](/Users/tyler/.codex/worktrees/project-workflow-exploration/gimbal-view/ephemeral/temporal-docker-interface-design-2026-10-09.md). It is unratified and not an accepted requirement or already reviewed by this proposal's Fable session. This document adopts the existing implementation's separation rather than duplicating that draft's interface design. The [pinned historical worklog](https://github.com/tylergannon/gimbal/blob/013559e85701cb424696b41fd396391a05a223ec/ephemeral/worklog/20260927-browser-evaluator.md) reports real no-model Linux command/readiness/cancellation checks, including an independently tightened process-alive check. Authenticated remote turns remained blocked on worker credentials at that revision; they are not proven by those command checks or freshly rerun here. Its `New` constructor calls `roleBindings` and rejects the entire run's binding set if any role is not Codex, so mixed local/non-Codex roles are currently rejected before construction. A usable macOS native environment remains a separate integration obligation.

Ordinary Go workflow control and typed result validation stay in the lean runner. The Temporal backend dispatches standalone activities to generic workers; those workers need neither a workflow plugin nor the workflow's generic response types. This does not resume the ordinary Go body after its runner dies; [recovered backend control](ownership.md#recover-remote-environments-without-the-runner) must identify and stop remaining owned work rather than replay that body. It is different from compiling workflow control flow into a Temporal controller. A compiled consumer may still lower authored sites to queues, but compilation is not a requirement for using a backend.

For ordinary mainline sessions without an execution environment, role-to-`ModelBinding.Adapter` wiring in project Go remains a narrower placement route. It must not define the universal backend model or silently move commands alongside a model role. In either route, backend deployment configuration is the placement authority: match the selected environment/role to the actual worker's OS, provider, required app permissions, and capabilities before admission. The integration must narrow today's run-wide validation to supported roles declared for the selected environment, leaving unrelated local role bindings unrestricted. Reject an unsupported declared configured environment/role binding before that role can cause effects; do not wait for first dispatch to discover a known capability mismatch. This does not require enumerating every unused catalog role or predicting a dynamic Go body. Reject an unresolved or incompatible desktop environment rather than falling back to a headless host. A compiled consumer checks its queue mapping against that same deployment configuration if it chooses compilation.

Durably associate each run/task/attempt with its environment, worker owner, request ID, and native thread before work proceeds, using the native admission rule above. The current desktop worker records request-to-thread identity; backend integration supplies run association, reservation, and placement observations. A request for Claude computer use requires its own demonstrated provider integration. Fable reviewing this design is not evidence for that integration.

## One controlling task per desktop

Reserve one desktop for one controlling task unless the backend supplies genuinely separate surfaces. The local adapter does not yet enforce this reservation; its request serialization is not execution exclusivity. Keep related turns on the same session while they depend on desktop state. On lost connectivity, reconnect to the recorded task/attempt/session or report uncertainty. Do not blindly replay clicks or submit a second controller.

The provider application and owner task are shared worker infrastructure. Cancelling a run cancels its owned tasks; it must not kill Codex or an unrelated user's application. Release a desktop reservation only when the controlling activity is known to have ceased. The current archive-and-stop result does not establish arbitrary distributed process cleanup; the backend still owes [whole-run termination](backend-contract.md#own-everything-the-run-starts).

A dedicated environment is also a cleanup boundary: the current Temporal backend can remove its whole container after an individual operation's unconfirmed stop, affecting sibling turns, commands, and browsers. Record that environment removal as the cause of their termination and reject later work in the removed environment. The intended fallback applies to uncertain cessation of **started owned work**; a queued dispatch or schedule-to-start timeout alone must not cause destructive environment cleanup. The pinned `Start`/`awaitStarted`/`Stop` path treats every Temporal `TimeoutError` as unconfirmed; the correction must inspect its timeout type and distinguish `ScheduleToStart` failure from uncertainty about started work. This is an integration correction, not current behavior. Never apply whole-environment removal to an externally shared provider.

## Cross-machine handoff and recovery

Pass typed values and referenced artifacts, materialized on the selected worker; a Linux path has no implied meaning on macOS. Where project code is actually deployed, associate its OS/architecture executable variants with one workflow build identity. Generic backend workers do not need a workflow executable variant merely to run remote commands or native agent turns. Reuse an existing backend's transport and resource registry to reach the macOS adapter instead of exposing its private local socket unauthenticated. The required remote admission, ownership, and observation behavior does not require a shared filesystem.

## Recover the desktop owner without losing its tasks

First resume/rebind the same owner task. An archived task or a restarted desktop does not, by itself, erase native task identity. A durable adapter ledger prevents blind replay of an uncertain start; it does not guarantee that its owner remains available.

If the old owner cannot be resumed, an explicitly provisioned replacement may adopt that same private ledger. A small Go launch bootstrap acquires the worker/ledger directory's nonblocking exclusive OS lock, then exec-replaces itself with the existing signed Node executable, retaining the locked descriptor for the Node worker's lifetime. It does not remain an extra parent in the provider bridge's ancestry chain. Do not forward the held descriptor to any child. This fences concurrent workers; only the lock holder may remove a stale socket and bind its replacement.

A held lock reports unavailable immediately. Resume the old worker or explicitly stop it after verifying its recorded process identity before replacement, even if its owner thread is archived; do not hang waiting, steal the lock, or unlink its live socket. File presence alone is not the lock. Verify recorded native task identities and current state through the provider, preserve unresolved or missing entries, and durably record the owner handover in the ledger and run observations. Inherit desktop reservations and outstanding stop intents before admitting new tasks. The lock is local to the macOS worker; it is separate from the central server's state-directory lock. The same server instance still owns the runs: replacing a provider owner is not adoption by a foreign server.

A verified task may be reattached or cancelled by its existing identity. A missing reply or missing session remains unresolved unless provider evidence establishes its outcome and cessation; never drop or relaunch it merely to finish adoption. Losing the shared owner means control is unavailable, not that its created tasks stopped. The server retains those runs and retries their stop intents after recovery.

This is a required backend recovery change, **not current worker behavior**: `Worker.load` presently rejects a different owner ID, and PR #440 provides neither the lock bootstrap, replacement-owner adoption, nor automatic restart. Current `server.mjs` uses socket binding/path existence for exclusivity; `scripts/launch` only selects and execs Node.

The worker lock bootstrap protects its ledger, whereas the local runner bootstrap gates child admission. Reuse small internal Go launcher code: the local gate can be a project-runner mode, and the desktop lock mode can run from the installed Gimbal executable before execing Node. Future worker provisioning records the installed Gimbal executable's absolute path in worker configuration; launch reads that path, not `PATH` or the marketplace cache directory. Having Gimbal installed on the Mac is a prerequisite of that future lock mode, not a requirement of today's Node-only worker. Keep those deployment duties distinct; the desktop worker must not depend on a project runner binary or an extra installed bootstrap program.

Re-run ordinary-MCP binding and the native acceptance scenario after the bootstrap change: preserved bridge authorization and lock lifetime must be demonstrated, not inferred from this design. The implementation must change that equality rule only through the fenced handover above. No separate supervision service is required.

## What remains to demonstrate

The local provider path is demonstrated. The full required backend must additionally run one authored workflow across Linux and macOS with real artifact handoff, remote submission, exclusive desktop access, reconnect to the same session, and run-wide cancellation that leaves unrelated work alive. Demonstrate Claude separately before advertising both providers. Validate the complete `HarnessAdapter` behavior actually used by the workflow, including typed generation and correct steering outcomes; the worker's current `message` success is not that contract.

Runtime backend checks must establish that the selected named environment and role reach the configured worker and reject incompatible placement. If a consumer compiles workflow sites, its compiler must preserve that mapping. Recovery tests must fence a former owner, adopt the ledger, and cancel the same native task without creating another. Integration tests and a real run establish desktop access, session continuity, and cessation. Use backend-native primitives and those focused assertions; do not create a second scheduler, distributed log, or worker supervision framework in Gimbal.
