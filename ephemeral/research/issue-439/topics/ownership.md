# Ownership and restart

[Back to TL;DR](../proposal.md)

**The server durably owns every run it launches. A restart must not make it forget a run or require anyone to search the process list.** Independent execution lets a runner survive the server; it does not release the server's responsibility to find and stop it.

## One directory, one active server

A server instance is identified by its canonical state/run directory. Default to one stable per-user location, independent of the current working directory. An explicit different directory creates a different instance. Acquire a nonblocking exclusive OS lock on `server.lock` before reading or changing instance state; refuse startup if it is held. Keep the descriptor open for the server lifetime, close-on-exec, and never pass it to runners.

Leave the lock file in place. The kernel releases the lock when the server exits or crashes; file existence is not evidence of a live owner. Do not unlink the file to recover: a replacement inode could allow a second lock holder. A replacement server takes the released lock and reads the same `instance-id` and ownership records. This is one active server per directory, not one server per machine. The directory uses a filesystem with the required lock semantics; placing compute remotely does not require sharing this directory among machines or adding distributed server failover.

## Record ownership before launch

Add an `instance-id` file under `--instance-dir`, created atomically once and reused on every restart. This is the durable owner identity. Today's random per-process control ID remains endpoint metadata; it does not determine ownership. Use a small durable record per run at `projects/<project>/runs/<run>/owner.json` under that directory. Also keep the existing exclusive project admission lock so two active servers cannot control the same project independently.

Before creating the runner process, durably save the assigned run ID, project, workflow/build identity, run-directory path (`<project>/.gimbal/runs/<run>/`), launch identity, and `launching` state. Persist endpoint/process identity as it becomes known. The record also retains last-known execution state, cleanup state, cancellation intent, and the backend execution identity. Recover the observation cursor from the durable journal prefix rather than duplicating it in this record. These are distinct facts: a workflow can have returned while its agent cleanup remains pending.

If reservation storage fails, do not spawn. If the server crashes between spawn and acknowledgment, the record still exists. Reconcile that launch; never blindly start another copy because acknowledgment was lost. The runner publishes `runner.json` in its assigned directory before executing the workflow, identifying its owner instance, run, launch, build, and endpoint. A returned spawn error records `failed-to-start`. The crash window before a startup acknowledgment is handled below.

A PID is useful metadata, not identity or the source of the run list. Descriptor files help reconnect to already-owned runs; their presence alone does not establish ownership or liveness.

### Resolve an interrupted launch

For local launch, acquire an exclusive `process.lock` in the reserved run directory before spawning and pass that locked file descriptor to the child. The launcher closes its copy after spawn; the runner immediately marks the inherited descriptor close-on-exec and retains its copy until exit. Do not explicitly unlock the shared descriptor, or pass it to agent subprocesses. This small OS-held lifetime marker covers the crash window before a PID or endpoint can be saved. It uses the same local-filesystem locking assumption as project admission.

After recovering exclusive project admission, reconcile a descriptor-less launch by attempting that lock: if it is available, neither launcher nor runner remains, so record `failed-to-start`; if held, keep the launch visible as starting/unresponsive and preserve stop intent. A timeout alone does not prove death. Publishing `runner.json` durably must precede all workflow/agent work. A descriptor with no remaining lock means the runner exited; replay its journal and retain unresolved agent cleanup separately. This rule resolves a launch that never executed without pretending a crashed runner cleaned up its agents.

## Reconnect after restart

The replacement server opens the same registry and enumerates every owned run whose cessation is not established, including unresolved launches and cleanup-pending runs. It contacts each recorded endpoint and checks the persistent owner ID together with run and launch identity before attaching observations or sending controls. The identity/status reply carries all three; a new server process reads the same owner ID from disk.

An unavailable endpoint changes connection status to `unreachable`; it does not delete the row or invent a terminal result. A stale endpoint that answers for another identity is rejected. Resume observations from the recovered journal position and reconcile the runner's current execution and cleanup state. Completed records remain history.

Local runners use a run-owned OS execution boundary, with stdout and stderr in their reserved run directory. Distributed backends own the equivalent boundary at every execution site, as specified in the [backend contract](backend-contract.md). A process group is a local implementation, not the definition of a distributed run. Server shutdown leaves them running. The durable registry remains responsible for reconnecting and controlling them. There is no automatic timeout that kills a healthy runner solely because the server is offline.

## Local force-stop has a concrete execution boundary

Keep separate command/turn process groups, but register every run-owned execution unit durably before it can do work. The runner is the sole local child-admission authority. For each agent command, service, or `RunCommand`, a small bootstrap (a mode of the runner executable is sufficient) starts the intended group, publishes its unit nonce, PID, PGID, and immutable process-birth identity, then waits before executing the workload. Under the run's OS-held admission/stop lock, persist its registration and then grant execution. No grant or a closed gate means no workload. Gate and admission-lock descriptors are close-on-exec and never retained by workload descendants, so terminating the runner closes its sole grant writer. Use an identity that survives bootstrap-to-workload exec; command-line text changes at exec and is not that identity. These execution-unit records are backend control state, not another event history.

Persist stop intent before force-stop. If the runner is unresponsive, verify and terminate that runner first, then acquire its released admission lock and stop new admissions. Waiting children see a closed gate; already granted units have durable records. Verify and signal those recorded groups without needing the runner to answer or scanning processes to discover ownership. Reconcile cleanup into the run history. If runner identity, storage, or a group's identity after leader exit/reuse cannot be verified, retain that named unit as cleanup-pending; never signal a possibly unrelated group or declare it stopped.

Every hosted run-owned root spawn uses this managed path. Its workload may fork/exec ordinary grandchildren within the registered group. This boundary supports only actual harness/workload profiles verified to keep all tool descendants in recorded units; third-party binaries cannot be made compliant by declaring detachment prohibited. Profiles that escape the recorded groups require independently enforceable backend-native containment (such as an existing container, cgroup, or scheduler job), or verified separately addressable native resources. Otherwise reject that hosted placement before dispatch. Unknown escaped execution is not an accepted residual, and no claim is made that all current CLI adapters already qualify. Existing per-command groups remain useful; the implementation must migrate every owned spawn, including `RunCommand`, rather than assume the runner's group already contains them. Shared provider services are the distinct boundary described below; do not kill their shared process.

The decisive check runs each real adapter binary on an actual long-running tool command, wedges its admission runner and also exercises an unresponsive harness, then force-stops its owned execution while unrelated shared services survive. Include tool descendants that start their own groups: the chosen containment must reach them, or the placement must be rejected. A cooperative fixture is insufficient. Cooperative cancellation may precede force-stop but cannot supply containment when the harness is wedged. Also crash between registration and the startup grant: an ungranted child must perform no workload, and a granted child must remain discoverable by its unit record. This supplements the inherited `process.lock` launch check; neither an ancestry assertion nor a successful kill of the runner alone is sufficient.

## Recover remote environments without the runner

Instance deployment configuration records the installed backend plugin path/identity, backend configuration, and secret references. The server writes that reference and its assigned `(RunID, LaunchID)` to `owner.json` before launch; only the server writes this outer ownership record. Pass the selected configuration and that same key to the backend before the first `Resolve`. The backend uses it for durable resource records, rather than minting an unrelated incarnation that must be published back. Derive native names from a canonical hash of the full run/launch key and environment name, retaining the exact ownership key in resource labels/records; do not slice raw IDs into Docker names. Each resolved environment is a registered execution unit whose native identities are retained before workload dispatch. For Temporal/Docker this includes the scoped bootstrap owner/name, queue, container, retained state volume, and Docker-host locator. Those are backend-specific records, not universal Docker fields added to Gimbal's core API.

Use one compatible installed server/recovery-plugin deployment. The project runner links its backend client from the project module graph; it never loads the server's Go plugin. Its build metadata declares the backend recovery-contract ID. Before hosted launch or effects, the server supplies that ID in the backend-specific `recovery_contract` configuration field when constructing its typed recovery controller. The plugin validates exact support before returning the controller; admission proceeds only after success, and the server saves the ID with ownership. This uses the existing configuration input, not an implicit capability-query method. Backend resource records carry the same ID, and recovery checks it again before acting. Support one format/version initially; do not add a compatibility matrix or migrations. Keep that installed bundle, paths, and configuration in place while any owned run or cleanup remains pending; stop/drain and resolve cleanup before upgrading it. This is an installation rule, not a per-run artifact cache or version manager. Restarting that same deployment is supported; mixed-version upgrades are not promised. A missing or incompatible backend or contract ID refuses new admission but preserves the registry. An incompatible persisted record remains a named visible control failure; it is never reinterpreted or discarded.

A replacement server loads the configured installed **backend plugin**'s explicit typed recovery entry to construct a backend-specific controller from the recorded configuration and run/launch key, independently of the dead runner. It does not execute project `main` or load a workflow plugin. This recovery entry is a proposed addition to the coordinated plugin contract, not implemented by the pinned backend. Persist the stop fence, verify the recorded container/native resource against its ownership identity, prevent further dispatch/retries, and stop it; append established cleanup outcomes to the run history. Do not create a fresh backend identity or call `Resolve` to recreate an uncertain environment. The pinned backend's fresh UUID and in-memory cleanup list do not supply this recovery path: implementing it is required, aligned with the [parallel API draft](/Users/tyler/.codex/worktrees/project-workflow-exploration/gimbal-view/ephemeral/temporal-docker-interface-design-2026-10-09.md), whose interface remains owned by that task. We adopt its execution/recovery seam and record contract, not its workflow-plugin loader or runner-side `plugin.Open`; this proposal builds project runner executables. Failure to reach or verify a resource leaves its named cleanup pending.

## Shared providers retain named ownership when control is unavailable

Providers shared outside a run are provisioned **outside any run**, through the backend's explicit setup/lifecycle command or existing service manager. Backend/instance configuration records the known shared attachment endpoint and identity; it does not acquire exclusive ownership of a daemon that may serve other instances or the native desktop. Hosted adapters attach only: an absent provider is an explicit admission failure, never a lazy daemon spawn inside the runner. Hosted Codex must change its turn path to use the existing internal `startDaemon=false` / `errDaemonNotRunning` variant; today that path still allows startup. Hosted OpenCode also needs attach-only behavior. Neither server shutdown nor run cancellation may terminate this shared infrastructure. This uses existing service setup and configuration, not a second supervisor or registry. A provider dedicated to a run-owned container is different: that environment may bootstrap it and terminate the entire container on cancellation.

Service lifecycle authority is separate from an attached run's authority. Gimbal's OpenCode lifecycle utility owns the recorded per-user daemon process, while Codex uses its external daemon lifecycle. An explicit `gimbal opencode stop` is a deliberate service-wide action affecting every attachment, not a single-run cancellation. Preserve that stop's evidence against the recorded provider generation/identity during run reconciliation. Verified daemon/group cessation establishes only what was actually stopped; confirm native session/tool cessation only where containment or provider evidence supports it, otherwise retain named cleanup-pending ownership. One instance's registry neither represents all users of the service nor grants exclusive termination rights.

A provider-hosted session is admitted only after actual interrupt-and-observe tests establish that stopping the session also stops its tool descendants. Persist the provider, daemon/host, and native session identity before its work starts. Cancel through the provider, then verify cessation. Current [Codex](../../../../codex/codex.go) and [OpenCode](../../../../opencode/adapter.go) cancellation/close returns do not establish descendant cessation; the backend integration must retain its persisted native identity independently of adapter memory and obtain authoritative stop evidence before releasing ownership. Never kill the shared Codex or OpenCode daemon, desktop owner, or another run's sessions to force one run to stop.

If the shared provider is wedged or unreachable, retain that **named owned resource** as cleanup-pending, keep its reservation, and retry its stop after recovery. Do not advertise an independent force-stop that the provider does not supply. This is the same unavailable-control condition as an unreachable execution machine; it is different from an unregistered escaped process whose identity was never captured. The local managed-process boundary must stop its owned units despite a wedged harness; a shared service cannot inherit that physical force guarantee. The desktop's lost-creation-reply gap is also different: it lacks a known native session ID, so its allocation-before-work gate remains required.

## Cancel one or all

A single-run cancellation selects its registry entry by run ID. Persist the cancellation intent before acknowledging acceptance, then address the verified runner endpoint. The runner performs whole-run cancellation and owns stopping its agent sessions and completing cleanup.

Expose cancel-all as an instance-level request on the central control endpoint. The CLI resolves that endpoint through discovery under the selected `--instance-dir`, rather than choosing a project-scoped handler.

**Cancel all means every run owned by this server instance at acceptance, across its projects, whose cessation is not established.** Include `launching`, running, unreachable, and cleanup-pending entries. Serialize this selection with launch admission so a concurrent launch reservation cannot be missed; save the selected runs' cancellation intents before acknowledging the request. New launches admitted afterward are outside that request.

A crash partway through saving a cancel-all request can leave some intents saved, but cannot produce a successful acknowledgment. Retrying cancel-all safely selects all remaining runs again. Saved intents survive restarts; deliver them as endpoints become available, including runners that were still starting. Repeated cancellation uses the existing cancellation/cleanup retry behavior.

Report per-run progress: requested, cancellation accepted, cleanup pending, cessation confirmed, or unreachable/pending. Acceptance is never reported as “everything is dead.” Unreachable entries remain owned and actionable. Operators use the server's run list and controls, including after restart; PID hunting and manual SIGTERM are not the normal control path. Force-stop addresses independently controllable recorded execution units, not just their coordinator process. The backend must stop further scheduling/retries, verify identities, and report every unit whose cessation cannot be confirmed. Local managed units have the independent force boundary above; shared provider sessions use their named provider stop path and remain cleanup-pending while that provider cannot answer. See the [backend contract](backend-contract.md); no unreachable machine is declared stopped merely because a request was accepted.

## Which runs belong here

All supported hosted launches, including CLI launches, go through the central launcher. Direct library `Run` calls remain owned by their calling process; importing their journals for history does not claim the server launched or controls them. At project admission and explicit history refresh, scan `<project>/.gimbal/runs/`, skip IDs already in the ownership registry, and inspect descriptors before importing direct-run journals. A hosted descriptor naming another owner is foreign-owned, never a direct run; report its owner and leave its files untouched. Direct-run history import does not create ownership records. The server's cancel-all targets its durable ownership records.
