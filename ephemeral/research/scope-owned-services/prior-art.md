# Issue 276: required foreground services owned by a scope

Recommend **fail-fast scope ownership with bounded process-group shutdown**. A required service exists for the declaring scope's lifetime; losing it before intentional shutdown fails that scope, even with exit zero. Successful launch permits workflow work to continue but says nothing about readiness. Readiness remains an ordinary workflow check.

This report answers [issue 276](issue-276.md) using downloaded primary sources reached through the [semantic index](corpus/INDEX.md). The three comparisons below supply precedents; the final contract is a recommendation, not behavior already guaranteed by Gimbal or any single precedent.

**What launch and exit actually establish.** Go's `Cmd.Start` synchronously reports preparation and process-creation errors. After successful start, `Wait` must observe the process once, release resources, and finish configured I/O copying. Nonzero exit produces `*exec.ExitError`; cancellation or I/O failures can also make `Wait` fail. `CommandContext` defaults to killing the tracked process, without group cleanup or a graceful interval. `WaitDelay` can bound a stuck child or inherited pipe, but cannot establish descendant termination. The Go tests explicitly cover a zero-exit child leaving a grandchild writing to its pipes, and a signal-handling child exiting zero while `Wait` reports cancellation. Preserve process status separately from cancellation and output errors. ([Go implementation](corpus/topic-001/sources/go-os-exec-exec.go.txt), [Go lifecycle tests](corpus/topic-001/sources/go-os-exec-exec_test.go.txt))

With `zsh -c`, the launched program interprets shell code. Failure to launch zsh is synchronous; a missing utility *inside* the string is a later shell result, normally 127, even if it happens immediately. Ordinary foreground execution waits for a command; `exec` can replace the shell. Pipeline status can hide an earlier command's failure, while asynchronous syntax can return zero before background work finishes. Gimbal observes the launched process's result, not an aggregate result for every subprocess. Neither shell success nor interactive job-control/HUP rules establish noninteractive SIGTERM propagation to descendants. Require the supplied command to remain foreground and represent the required workload's lifetime. ([zsh invocation](corpus/topic-002/sources/zsh-invocation.html), [builtins](corpus/topic-002/sources/zsh-builtins.html), [jobs/signals](corpus/topic-002/sources/zsh-jobs-signals.html), [POSIX shell language](corpus/topic-002/sources/posix-shell-command-language.html))

**Three relevant approaches.** The two test tools own a local command for bounded work, making them useful lifetime precedents without persistent ownership.

| Approach | Relevant behavior | Transfer and limit |
| --- | --- | --- |
| Fail-fast structured scope: Go `errgroup` and Python `TaskGroup` | First child error cancels sibling work; Python excludes ordinary cancellation. Completion waits for children. Go returns the first error; Python groups failures. | Adopt failure propagation and cleanup-before-result. These systems ordinarily accept successful child completion and wait on normal scope exit; treating zero exit as failure and stopping a long-lived service at normal close are explicit Gimbal choices. [Go source](corpus/topic-005/sources/topic005-go-errgroup.go.txt), [Python documentation source](corpus/topic-005/sources/topic005-python-asyncio-task.rst). |
| Playwright Test `webServer` | Starts a shell command, races optional URL/output readiness against exit/timeout, retains it through tests, routes output, and tears down after work or setup failure. Configured graceful shutdown signals the group and documents timed SIGKILL escalation. | Borrow bounded ownership and group shutdown. Defaults use SIGKILL; zero graceful timeout disables escalation. The downloaded plugin races exit during setup, not throughout test execution, and its graceful completion observes the direct child's `close`. Neither proves continuous fail-fast monitoring or complete descendant cleanup. [Docs](corpus/topic-007/sources/playwright-webserver.html), [plugin](corpus/topic-007/sources/playwright-webServerPlugin.ts). |
| `start-server-and-test` | Starts through a shell with inherited output, waits for a URL, runs tests, and invokes cleanup in `finally`. | Borrow unconditional cleanup and visible output. Its unexpected-close listener is removed after readiness; cleanup uses `tree-kill` with SIGINT and shows no bounded escalation in this layer. [README](corpus/topic-007/sources/start-server-and-test-README.md), [source](corpus/topic-007/sources/start-server-and-test-index.js). |

Thus startup failure detection alone is insufficient for a *required* service. Transfer continuous scope ownership, failure observation, output, and cleanup; leave the tools' readiness/reuse/multiple-server machinery behind.

**The Unix boundary.** Use a dedicated process group, established as a launch precondition and separate from Gimbal's group. Ordinary descendants inherit membership; group signaling reaches them even when the shell does not forward signals. Group formation has prerequisites: changing a child's group after its exec can fail, and a process-group leader cannot simply call `setsid`. A session can contain several groups; it is not one universal signal target. ([Linux setpgid](corpus/topic-003/sources/linux-setpgid.2.html), [Linux setsid](corpus/topic-003/sources/linux-setsid.2.html), [macOS SDK setsid](corpus/topic-003/sources/macos-sdk-setsid.2), [POSIX definitions](corpus/topic-004/sources/posix-base-definitions.html))

Signal delivery, direct-child reaping, and group termination are distinct observations. Linux group-signaling success means at least one signal was delivered; the downloaded macOS `killpg` manual documents failure without delivery for permission mismatch. SIGKILL cannot be caught or ignored, but does not supply a synchronous completion acknowledgment. Waiting for the direct child reaps it and yields its status, not every descendant's status. An absent group (`ESRCH`) can be a benign shutdown race: it establishes absence of that group at observation, not absence of escaped descendants. Permission failure is not equivalent to absence. ([Linux kill](corpus/topic-003/sources/linux-kill.2.html), [macOS SDK killpg](corpus/topic-004/sources/macos-sdk-killpg.2), [Linux signal](corpus/topic-003/sources/linux-signal.7.html), [Linux wait](corpus/topic-003/sources/linux-wait.2.html))

**Recommended initial contract.** These outcomes combine the Go/Unix evidence with structured-scope failure propagation; they deliberately strengthen the test tools' startup-only observation.

| Event | Owning scope's observable outcome |
| --- | --- |
| Synchronous startup failure | Launch or ownership-boundary setup failure is returned before declaration succeeds; the required dependency fails the scope. Successful spawn is neither readiness nor assurance that the command remains alive. |
| Unexpected exit | Any observed exit before intentional shutdown, including zero, fails the owning scope and requests cancellation of its remaining work. Retain the exit/signal result and output; clean up surviving group members even though the direct child exited. |
| Normal work completion | Begin intentional service shutdown, then complete the scope successfully only after owned cleanup succeeds. An enclosing declaration spans inner loop iterations; an iteration-local declaration ends with that iteration. The global scope follows the same rule. |
| Explicit cancellation | Initiate the same cleanup while owned work unwinds. Retain cancellation as the cause when it wins the ordering below; a shutdown-induced exit adds no unexpected-exit failure. |
| SIGTERM and escalation | Send SIGTERM to the owned group, allow a finite nonzero grace period, then SIGKILL remaining group members. Continue cleanup after shell exit; it must not disable escalation. Bound final termination observation and output draining as well. |
| Cleanup result | Reap the direct child and establish termination within the owned boundary before claiming successful cleanup. Permission errors, surviving members, or an expired final observation deadline produce explicit incomplete cleanup. Preserve the original scope failure/cancellation alongside cleanup failure; never claim termination merely because a signal was sent. If bounded observation expires, report final process status as unknown where necessary. |
| Output and status | Expose stdout/stderr while running and retain the observed final exit code or signal, cancellation cause, escalation, and cleanup result. Shell-encoded status is not a separately observed descendant signal. Report interrupted/truncated output; pipe closure alone is not process cleanup. |

For races, **the first recorded lifecycle event wins**: an observed exit before scope shutdown is recorded remains a service failure; intentional close/cancellation recorded first classifies the subsequent exit as shutdown-associated. Keep the raw exit result either way. This defines observable ordering, not unknowable physical causality between concurrent events. Do not relabel an already-observed failure as successful teardown. Scope shutdown initiation is intermediate; a final result follows completed cleanup observation or its explicit bounded failure. This precedence is a recommended policy, not dictated by `errgroup` or `TaskGroup`.

**Four actionable constraints.**

1. Separate launch acceptance, lifetime observation, and readiness. Every successful start requires one final process observation; ordinary workflow code determines usability.
2. Make disappearance of a required service scope-fatal for the entire owning lifetime, with the recorded-event ordering above. Preserve the first cause through sibling cancellation and cleanup.
3. Own a dedicated group and require bounded SIGTERM-to-SIGKILL cleanup of its remaining members. Direct-child exit and closed output pipes cannot substitute for group cleanup; incomplete cleanup is visible.
4. Require foreground, non-escaping workloads and observable output/status. Ownership ends with the declaring scope. No restarts, dependency graphs, readiness framework, persistent daemon, launchd integration, or management of a delegated tool's external resources belongs in this contract.

**One unresolved macOS/Linux portability point.** There is no demonstrated common mechanism in these sources to retain and verify ownership of *every descendant after group/session escape*. POSIX permits departure through `setpgid`/`setsid`; Linux documents subreaper adoption and cgroup tree-kill facilities, while the reviewed macOS SDK material establishes group signaling without a corresponding portable containment guarantee. This is an evidence limit, not proof that macOS has no stronger facility. The manuals' differing permission semantics also need platform-specific interpretation. ([POSIX](corpus/topic-004/sources/posix-base-definitions.html), [Linux subreaper](corpus/topic-004/sources/linux-child-subreaper.2const.html), [Linux cgroups](corpus/topic-004/sources/linux-cgroup-v2.html), [macOS killpg](corpus/topic-004/sources/macos-sdk-killpg.2), [SDK provenance](corpus/topic-004/sources/macos-sdk-provenance.md))

The initial promise must therefore be conditional on descendants remaining in the owned group. Detected escape or unverifiable cleanup is reported, but universal escape detection is not promised. Arbitrary daemonizing commands are outside that guarantee. A finite cleanup deadline bounds Gimbal's wait and reporting obligation; it cannot promise that an unkillable process has vanished. This settles the bounded foreground-service contract without importing platform containment machinery.
