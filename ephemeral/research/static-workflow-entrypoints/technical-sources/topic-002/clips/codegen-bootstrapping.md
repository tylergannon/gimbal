## 1. Changes to Generator Pipeline (`command.go` and `source.go`)

### Current Behavior
In [`internal/generate/command.go:96-220`](../sources/internal-generate-command.go.txt), `commandTemplate` emits a single file (`workflow_gen.go`) directly inside the workflow's package clause (`package {{.Package}}`). This file bundles:
1. `Graph` literal and `init() { gimbal.RegisterGraph(Graph) }`
2. `Hosted() web.WorkflowEntry` (decoding raw JSON and returning a closure for `web.WithWorkflows`)
3. `Command(...) *cobra.Command` (defining CLI flags, calling `web.Submit` with untyped JSON payload and `web.Follow`)

Because `workflow_gen.go` is in the workflow package, the workflow package imports `github.com/tylergannon/gimbal/web`. When route handlers beside web routes need to call the workflow, this produces the cycle: `web -> internal/skgo -> web/src/routes -> internal/workflows/... -> web`.

### Required Modifications
1. **Workflow Package Generation**:
   - `gimbalgen` will only emit the `Graph` variable and `RegisterGraph(Graph)` inside the workflow package (plus Mermaid/Svelte diagram when requested).
   - Delete `Hosted()` and `Command()` generation from the workflow package.
   - Result: Workflow packages have zero dependencies on `web`, `cobra`, or `skgo`.
2. **Typed SKGO Form Route Handlers Generation**:
   - For each built-in workflow, emit a typed SKGO Form route file (e.g. in `web/src/routes/start_<name>.remote.go` or `web/src/routes/start/<name>.remote.go`).
   - Declares the typed request struct containing:
     - `Project string` (owning repository directory)
     - `WorkDir string` (execution directory)
     - `Conversation string` (optional conversation ID)
     - Concrete workflow parameters (e.g. `Goal string`, `OutcomesFile string`, etc.)
     - Role model override fields (e.g. `CodeReviewModel string`)
   - Emits a function marked as `skgo.Form`:
     ```go
     // StartReview starts the review workflow.
     //
     //skgo:form
     func StartReview(ctx context.Context, req ReviewStartRequest) (StartResult, error)
     ```
   - Handler body calls `inst := host.FromContext(ctx)`, `p, err := inst.AdmitProject(req.Project)`, validates arguments, and executes `p.StartRun(ctx, "review", models, func(runCtx context.Context) error { return review.Review(runCtx, env, params) })`.
3. **Client Cobra Commands Generation**:
   - Emit Cobra commands in `cmd/gimbal/` or `internal/commands/` outside workflow packages.
   - The command flags bind parameters and role models.
   - Instead of calling `web.Submit`, `cmd.RunE` calls the typed SKGO Go client generated by SKGO (e.g., `client.StartReview(ctx, req)`).

## 2. Static Definition of the Five Stock Built-ins

Currently, the five built-in workflows are duplicated in:
- `cmd/gimbal/workflows.go:36-51` (`newRunCommand` and `builtInWorkflows`)
- `//go:generate` directives scattered in five workflow packages
- `cmd/gimbal/defaults.json`

To enable generators to consume the list consistently without drift:
- Define an authoritative static slice in an internal package (e.g. `internal/builtin/workflows.go`):
  ```go
  package builtin

  type WorkflowDef struct {
      Name      string // "review", "implement", "research-document", "pyramid-summary", "validate-product"
      Package   string // "github.com/tylergannon/gimbal/internal/workflows/review"
      Entry     string // "Review"
      Params    string // "ReviewParams"
      Dir       string // "internal/workflows/review"
  }

  var Builtins = []WorkflowDef{ ... }
  ```
- Both the route generator and the CLI generator iterate over `builtin.Builtins`.
- `cmd/gimbal/workflows.go` imports generated client commands without manual map registration.

## 3. Acyclic Generation on Clean Checkout

### The Stale / Deleted File Risk
When `go generate ./...` runs on a clean checkout:
If `web/src/routes/...` contains route handlers that import `internal/workflows/...`, and route handlers are scanned by `skgo generate` (`internal/skgo/config.go`):
1. If workflow packages depended on `web` or generated code that wasn't compiled yet, `packages.Load` would fail during scanning.
2. In the new decoupled architecture, workflow packages depend ONLY on `gimbal` and `workflow`. They have no dependencies on `web`, `skgo`, or generated route code.
3. Therefore, workflow packages can always be generated and compiled first.

### Generation Sequence
Structure generation in explicit stages (in `Justfile` or via an explicit generator tool `go run ./internal/generate/all`):
1. **Stage 1 (Workflows)**: Run `gimbalgen` over each workflow in `internal/workflows/`. Generates `workflow_gen.go` (graphs only). These compile cleanly with no external dependencies.
2. **Stage 2 (Route Handlers)**: Generate typed SKGO Form route handlers (`web/src/routes/start_*.remote.go`) referencing the workflows and `internal/host`.
3. **Stage 3 (SKGO Generation)**: Run `go tool skgo generate --web ../../web` to scan routes and produce `internal/skgo` (transports, route registries, and typed Go clients).
4. **Stage 4 (CLI Commands)**: Generate or compile Cobra commands in `cmd/gimbal/` referencing the typed Go clients.

This guarantees that a clean checkout (`git clean -xfd`) can build without circular dependencies or missing-symbol errors.

## 4. Decoupling Standalone Example Workflows

Currently, `cmd/examples/interview/main.go` and `cmd/examples/implement-interview/main.go` call `interviewworkflow.Command(...)` and `implementinterview.Command(...)`.
As noted in `ephemeral/research/static-workflow-entrypoints/assessment.md:114-121`:
> neither workflow is registered by the stock server. Against that server, their submissions reach the unknown-workflow refusal.

### Decoupling Strategy
1. The two examples in `examples/` (`interview` and `implement-interview`) are explicitly NOT stock built-in workflows.
2. They do not get registered in `builtin.Builtins` and do not generate stock web start forms.
3. In their packages (`internal/workflows/interview`, `internal/workflows/implementinterview`), `gimbalgen` generates only `Graph` for diagramming / registration.
4. In `cmd/examples/interview/main.go` and `cmd/examples/implement-interview/main.go`, rewrite their `main()` to invoke `gimbal.Run` directly (standalone execution mode):
   ```go
   ctx := gimbal.Project(context.Background(), projectDir)
   err := gimbal.Run(ctx, "interview", models, func(ctx context.Context) error {
       return interview.Interview(ctx, gimbal.Env{WorkDir: projectDir}, params)
   })
   ```
   Or if live UI observation is desired, invoke `host.NewRuntime(...)` locally.
5. This eliminates the expectation that the stock Gimbal server must host these custom examples, while preserving their role as runnable standalone examples.
