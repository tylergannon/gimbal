# SvelteKit Enhanced Form Protocol and Wire Format

## Scope

This topic establishes the precise wire protocol used by SvelteKit's client-side `enhance` action and remote form handlers, including binary envelope encoding, response serialization, field validation issues, error envelopes, and validation-only requests, based on pinned SvelteKit reference code and SKGO test fixtures.

## Synthesis

### 1. Request Format, Headers, and Binary Encoding

When a user submits an enhanced form in SvelteKit, the client does not send standard `multipart/form-data` or `application/x-www-form-urlencoded`. Instead, `form.svelte.js` transforms the `FormData` into a plain object (coercing types with `n:` and `b:` prefixes and unflattening dotted field paths) and serializes it using `serialize_binary_form`.
([sveltekit-client-form-protocol.txt](sources/sveltekit-client-form-protocol.txt), [sveltekit-form-utils.txt](sources/sveltekit-form-utils.txt))

- **HTTP Method**: `POST`
- **Target URL**: `${base}/${app_dir}/remote/${action_id_without_key}` (e.g. `/_app/remote/<hash>/<name>`)
- **Headers**:
  - `Content-Type`: `application/x-sveltekit-formdata` (`BINARY_FORM_CONTENT_TYPE`)
  - `x-sveltekit-pathname`: Current page pathname (e.g., `location.pathname`)
  - `x-sveltekit-search`: Current page search query (e.g., `location.search`)
- **Binary Envelope Layout**:
  - `1 byte`: Format version (uint8, currently `0`)
  - `4 bytes`: Header length (uint32, little-endian)
  - `2 bytes`: File offset table length (uint16, little-endian)
  - `$N$ bytes`: Header payload serialized with `devalue.stringify([data, meta])`
    - `data`: Form input fields (with uploaded files replaced by metadata tuples `["File", [name, mime, size, lastModified, index]]`)
    - `meta`: Metadata object containing optional `remote_refreshes: string[]` and `validate_only: bool`
  - `$M$ bytes`: File offset table containing JSON array of offsets (e.g. `[0, 1024]` or empty if no files) relative to the end of the table
  - Raw concatenated file bytes (sorted smallest first).
- **Golden Fixtures**: Verified by SKGO tests using real envelopes generated by Kit's own serializer: `formGoldenSubmission` (text fields + refresh), `formGoldenWithFile` (file payload), and `formGoldenValidateOnly` (validation-only payload). ([skgo-remote-form.txt](sources/skgo-remote-form.txt), [skgo-formdata.txt](sources/skgo-formdata.txt), [wire-envelopes.md](clips/wire-envelopes.md))

### 2. Response Serialization under devalue/JSON Wire Protocol

All runtime remote responses are returned with `Content-Type: application/json`, `Cache-Control: private, no-store`, and HTTP status **200 OK**. SvelteKit and SKGO differentiate outcomes via top-level JSON fields rather than HTTP status codes. ([sveltekit-server-remote-functions.txt](sources/sveltekit-server-remote-functions.txt), [sveltekit-client-form-protocol.txt](sources/sveltekit-client-form-protocol.txt), [skgo-remote-form.txt](sources/skgo-remote-form.txt))

- **Successful Execution**:
  - JSON Envelope: `{"type": "result", "data": "<devalue_string>"}`
  - Unflattened `data` contains:
    - `_`: `{"submission": true, "result": <typed_value>}`
    - Optional single-flight update fields: `q` (queries), `l` (live queries), `i` (ignored), and `r: true` (which instructs `form.svelte.js` to suppress blanket `refreshAll()`).
- **Field Validation Issues (`*skgo.Invalid`)**:
  - HTTP Status: `200 OK`.
  - JSON Envelope: `{"type": "result", "data": "<devalue_string>"}`
  - Unflattened `data` contains:
    - `_`: `{"submission": true, "issues": [{"name": "<field>", "path": [...], "message": "<msg>", "server": true}]}`
    - Refreshes (`q`, `l`, `r`) are **omitted**. This suppresses page refreshes and preserves the user's typed input. The input itself is not echoed back.
- **Server Failure Envelopes**:
  - HTTP Status: `200 OK` (at runtime; non-200 is used only during prerendering or for protocol-level errors like 405 Method Not Allowed, 413 Payload Too Large, 415 Unsupported Media Type).
  - JSON Envelope: `{"type": "error", "error": {"status": <status_code>, "message": "<error_message>"}}`
  - The client checks `result.type === 'error'` and raises an error; it must never assume HTTP 200 signifies success. ([wire-envelopes.md](clips/wire-envelopes.md))

### 3. Validation-Only Requests and Prevention of Workflow Execution

As the user types into form controls, SvelteKit's client calls `form.validate()`, which issues an asynchronous check to the server. ([sveltekit-client-form-protocol.txt](sources/sveltekit-client-form-protocol.txt))

- **Wire Representation**: The request carries the standard `application/x-sveltekit-formdata` binary envelope, but the `meta` object in the devalue header contains `{"validate_only": true}` (as captured in fixture `formGoldenValidateOnly`).
- **Server-Side Detection**: In SKGO, `formdata.ParseWith` parses the header and extracts `meta.ValidateOnly`.
- **Handling Invariant**: In `remote_form.go:176-179`, the server explicitly detects `if meta.ValidateOnly` before invoking the handler:
  ```go
  if meta.ValidateOnly {
      rs.writeResult(w, rs.newEvent(r, false), map[string]any{"_": []any{}})
      return
  }
  ```
- **Rationale**: SKGO remote functions are declared `'unchecked'` because validation is executed by the Go handler code. Running the Go handler on `validate_only` requests would execute workflow start side effects on every keystroke. Thus, the server immediately returns an empty issue list `{"type": "result", "data": devalue({"_": []})}` with HTTP 200 without invoking the workflow.

## Actionable Constraints for Implementation

1. **Client Envelope Framing**: Any Go client calling a remote Form must construct the 7-byte prologue (version 0, LE u32 header length, LE u16 offset length), devalue header `[data, meta]`, and optional file table matching SvelteKit's exact envelope.
2. **Never Treat HTTP 200 as Success**: Both the Go client and tests must parse the response JSON and verify `type == "result"` and inspect `_` for `issues` vs `result`. A response with `type == "error"` or `issues` must be mapped to distinct Go error types (`*skgo.HTTPError` and `*skgo.Invalid`).
3. **Respect Validation-Only Requests**: All generated workflow start handlers rely on `remote_form.go`'s guard to ensure typing in the browser UI does not trigger workflow runs.

## Questions Addressed

- **Precise request format**: Documented headers (`application/x-sveltekit-formdata`, `x-sveltekit-pathname`, `x-sveltekit-search`), 7-byte binary prologue, devalue header, and file offset table from primary sources.
- **Serialization of success, field issues, and errors**: Documented JSON/devalue schemas for HTTP 200 responses, distinguishing result payloads, issue nodes, and error envelopes.
- **Validation-only request detection**: Identified `meta.ValidateOnly` wire flag, `formGoldenValidateOnly` fixture, and `remote_form.go` early-return mechanism.

## Distinctions: Supported Facts vs Inference

- **Supported Fact**: SvelteKit runtime remote calls return HTTP 200 for application errors, encoding failure details in `{"type": "error", "error": {...}}`.
- **Supported Fact**: Field issues return HTTP 200 with `{"type": "result", "data": "..."}` where unflattened `_` holds `issues`, omitting `q`, `l`, and `r`.
- **Supported Fact**: SKGO `remote_form.go` returns `{"_": []}` for `validate_only` requests without running the handler.
- **Inference**: A Go CLI client does not need to send `validate_only` requests since CLI argument validation occurs locally before dispatch.

## Contradictions and Unresolved Questions

- None. SvelteKit reference implementation and SKGO's existing golden tests agree on wire formats and envelopes.
