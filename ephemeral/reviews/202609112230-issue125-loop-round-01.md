## Findings

### 1. issue — sprint goal still tells the planner to create command "steps" for the removed sweep

`internal/workflows/sprint/sprints.go:227` (`done`) ends with "Give the two
checks steps of their own, with those commands." That sentence existed for
the old backlog schema, where each `step:` could carry a `command:` that
Loop swept before each planning turn. LOOP-WORK.md's third item replaces
that sweep: the workflow now runs `checks` (`go vet`, `go test`) itself
after every task at `sprints.go:171-181`, and the backlog schema has no
steps or per-task command sweep.

Impact: the sprint planner is instructed to dispatch two assignments whose
whole content is "run go vet" and "run go test". Each costs a coder fork,
a supervisor session, and a validator turn (`runTask`), and produces
nothing the workflow has not already recorded. LOOP.md explicitly warns
against "tiny bookkeeping assignments". This is the one consumer LOOP-WORK
asks to adapt, and the adaptation left its goal text contradicting the new
contract. Fix is a one-sentence deletion.

### 2. issue — the live proof does not establish the adaptive behaviors LOOP-WORK names

LOOP-WORK's validation standard for the live run requires (a) a planner
"receiving a failed check ... selecting useful follow-up work", (b)
"adaptation of a plan, including advancing past a nonblocking defect", and
(c) assignments that are "coherent, appropriately sized". The retained
evidence falls short on each:

- (a) is scaffolded rather than observed. After task 1 the workflow writes
  `authoritative promise status: UNMET ... no later workflow-recorded probe
  result exists yet` (`ephemeral/attest/issue125/main.go:96-99`, present in
  `run.jsonl`). The worklog records this was added because Luna twice ended
  dispatch on the bare exit 7. The planner therefore chose follow-up after
  being told in prose that the promise was unmet, not from the failed check
  plus the parent context alone.
- The follow-up it chose, `establish-probe-stability`, is a validation-only
  task: rerun `./probe.sh`. The harness anticipates exactly this and skips
  the worker when `task.Validation.Command == "./probe.sh"`
  (`main.go:66-68`). That hard-codes the expected second task into the
  proof, and the task itself is the bookkeeping-sized assignment LOOP.md
  says to avoid. The Haiku validator passed sizing anyway.
- (b) is not demonstrated. The with-plan probe (`main.go:128-146`) hands the
  planner `priority: A usable export is the primary promise` and a plan that
  already states Phase 2 "has no dependency on the typo", then records the
  first selection and breaks. Nothing in the observed state diverged from
  the plan, so no adaptation occurred; the planner picked the item it was
  told was primary. LOOP-WORK's Evidence paragraph admits "task selection
  only", but its validation standard was not amended to match.
- LOOP.md's evidence list also asks to "Exercise early break and
  cancellation to verify scope lifetime". `TestLoopEndsTaskScopeOnBreak`
  covers break; no Loop test cancels the context mid-task.

Impact: the definition-of-done's validation side requires evidence that
"actually demonstrates" the behavior. The retained run demonstrates the
mechanical contract well (structured task in decision, scope, and stored
value; feedback projected; exit 7 preserved), but the adaptive-planning
claims rest on hints the harness supplied. Either the fixture needs a real
divergence and no promise-status prose, or LOOP-WORK's "How we'll know"
paragraph must be narrowed to what was shown.

### 3. issue — `boundarySource` in the Codex projector is provenance beyond LOOP-WORK

`codex/events.go:39,370,389-390,410` add a `boundarySource` field that is
written into the `session.step.ended` NativeRef accounting map, with a
dedicated test. The worklog says the resumed-turn error blocked the second
planner turn on a real Loop, so some fix was required. The required fix is
the deletion of the `errors.New("codex: turn completed before
rawResponse/completed")` branch. Recording where the boundary came from is
new attribution metadata that LOOP-WORK does not ask for and that the
worklog itself assigns to issue #135. The user's stated constraint excludes
provenance and tracking machinery beyond LOOP-WORK.

Impact: small, but it is exactly the class of addition the user barred, and
it widens a contract (`NativeRef` accounting keys) that #135 is meant to
settle.

### 4. nitpick — SPRINTS.md still describes the removed contract

`ephemeral/research/api/SPRINTS.md:60-63` documents `Laps`, steps with
`command:`, the per-lap command sweep, and (line 104) the loop command
event. AGENTS.md lists SPRINTS.md as read-first for "what is being built".
Godoc, API.md, and LOOP.md now agree with the code; SPRINTS.md contradicts
all three and will mislead the next sprint's researcher, whose prompt sends
it there.

### 5. nitpick — exact-match backlog check is terminal for a formatting mismatch

`loop.go:120` requires `slices.Contains(backlog.Tasks, p.Next.Value)`, an
exact struct equality. A YAML `|` block scalar decodes with a trailing
newline (verified), while the structured `next` result carries the same
text without it. A real planner that writes multi-line descriptions as
block scalars, which is the natural YAML for prose, will produce a task the
loop refuses with a terminal `did not preserve that assignment` error,
while a YAML parse error at `loop.go:107-110` gets a repair turn. LOOP.md
does say an inconsistent assignment is an error, so this is by design, but
the asymmetry regresses the #115 resilience the worklog worked to keep.
Trimming both sides before comparison, or offering the same repair turn,
would remove the trap.
