Evidence:

- `implementation-plan.md` L133–137: "The recursive encoding must be settled before writing the exact production declarations in `github.com/tylergannon/gimble/workflow`."

This codification does not authorize a polytype implementation change or settle the final Graph field layout. Finalize that choice ... before handing Sol an exact production struct to implement."

The only Go declarations in either document are the two supervision structs (`graph-model.md` L148–160) and the `Workflow[T]` interface (plan L176–182). There is no `Graph`, `Operation`, `Subgraph`, `AgentCall`, `Command`, `Set`, `SetJSON`, `Exit`, `Sequence`, `Condition`, `Loop`, `Scope`, `Group`, session-declaration, or `Expression` declaration anywhere in the handoff, and the plan explicitly deleted the earlier one.

Impact: the deliverable's named core artifact is absent. Sol cannot implement from this handoff without first making a design decision with two materially different outcomes (extend polytype v1.0.0 to accept recursive types, or flatten to ID references in the Go model), and `graph-model.md` L273–274 withholds authorization for one of those two paths while the plan's step 1 tells Sol to settle it. The acceptance rows that depend on the layout (plan L446, "comparing nested bodies or their encoded child references"; graph-model L293–294 codec/TypeScript proof) cannot be checked against anything concrete. Either the encoding decision must be made and the full declarations written into the handoff, or the handoff should state that the L5 requirement is unmet and why, rather than presenting itself as complete.

### 2. Issue — over-engineering / unrequested exported surface: the plan introduces an unnamed root-package "start bridge" and a second generator binary that no authoritative source asked for

Governing rules: `AGENTS.md` "As simple as possible. Add a name only when a workflow that exists needs it." and its "No wrappers" rule (a new exported name only when Tyler asks for it by name). `review-user-decisions.md` L7: "Tyler proposed gimble generate-bindings with -workflow-type, optional -out, and optional -pkg."

Evidence:

- `implementation-plan.md` L324–329: "Provide the shared typed start bridge through the root package, available to caller modules, with the owning runtime reached through its request context. The runtime supplies that bridge's execution machinery." This directs Sol to add a new exported API to package `gimble` with no name, signature, or contract, and to thread a runtime through request context so route packages can reach it. Neither the issue, the comment, nor the decisions mention a root-package bridge; the comment's assembly (L100–110) and the plan's own example (L281–283) go through `web.Runtime.Run` directly. Under the no-wrappers rule Sol has no authority to invent this name, and the handoff gives Sol nothing to implement for it.
- `implementation-plan.md` L198 and L202: a separate `cmd/gimblegraph` binary invoked as `go run github.com/tylergannon/gimble/cmd/gimblegraph -name sprint -entry Sprint -output workflow_gen.go`, while L296–300 and L425 put bindings generation under the `gimble generate-bindings` subcommand Tyler proposed. Two generator entrypoints with different invocation styles for one feature is unrequested infrastructure; the decisions describe one `gimble` subcommand pattern.
- Lesser, same category: `implementation-plan.md` L185–186 and L309 require an exported zero-state type `SprintWorkflow` where comment L93 asked only for "an exported value such as `sprint.Workflow`". A named type is defensible because `-workflow-type` selects by type name (L299), but the plan should say that is the reason rather than adding the export silently.

Impact: Sol is handed at least one unspecified exported API to design in the root package and two CLI surfaces to build, contrary to "build what was asked" and the one-subcommand direction. A concrete fix is to name and specify the bridge in the handoff only if Tyler approves it, or drop it by having generated route bindings call the runtime through a mechanism the plan already specifies, and to fold graph generation into the `gimble` CLI as a sibling subcommand of `generate-bindings`.
