## Findings

### 1. Nitpick: say how the runner keeps `process.lock` out of agent subprocesses

`ownership.md:19` says "Do not ... pass it to agent subprocesses." The
descriptor arrives in the runner as an inherited fd without close-on-exec, and
Go does not add that flag to inherited descriptors. Every agent and service
subprocess in the tree is spawned with `os/exec` and `Setpgid`
(`service_process_unix.go:12`, `agy/process_unix.go:12`,
`opencode/process_unix.go:44`), so a leaked descriptor would keep the lock
held by a detached grandchild after the runner dies, and `ownership.md:21`
would then report a dead runner as "starting/unresponsive" indefinitely. One
clause closes it: the runner marks the inherited descriptor close-on-exec
before any other work.

### 2. Nitpick: `process.lock` is missing from the file-ownership table

`storage-and-remote.md:12` lists the runner's run-directory files as
`events.jsonl`, the existing logs, `runner.json`, and stdout/stderr. The
launcher now creates `process.lock` in that same directory before spawn
(`ownership.md:19`). Add it to the table and say the launcher creates it so
"mutable run files remain exclusively owned" (`storage-and-remote.md:17`)
stays true with one named exception.

### 3. Nitpick: "makes them durable before exposing their positions" should say what durable means

`interchange.md:29` was strengthened to make each record durable before its
position is visible to subscribers. The current writers never call sync
(`event_persistence.go:29-50`). If this means a write to the file so that a
later file read sees it, say so; if it means fsync per record, say so and
accept the cost. The two readings produce different implementations and
different failure behavior for the "replay its journal" step at
`ownership.md:21`.
