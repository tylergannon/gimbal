# Run identity and storage seam

## Recommendation

Make each run own a backend-neutral record store. The launcher assigns its run ID; the engine assigns and persists identities for everything inside it. Keep readable workflow addresses as labels, separate from durable ULIDs. Commit action identity, request and dispatch binding before calling an executor; commit results before reporting success. Supply a filesystem implementation rooted in the selected workflow host's existing run directory.

This is the recording foundation. Reopening the store works; resuming execution does not ship in this slice. An existing run cannot accidentally be started a second time. Workflow function signatures and their Group, Session, Generate, Check and RunCommand calls remain unchanged.

## Start boundary and ownership

Proposed engine entry: `gimbal.Run(ctx, runID, name, models, body) error`. RunID is a validated ULID, with no workflow-name suffix. Required means no engine fallback: empty/invalid IDs fail before directory creation or workflow code. CLI/web/runner/conversation launch boundaries allocate a ULID once when creating a new invocation. Routed admission forwards that ID unchanged through backend.Workflow and invocation.Request. A direct library caller supplies the same argument. Existing workflow definitions `(context.Context, gimbal.Env) error` are untouched; their host/launcher changes. Delete effects.WithRunID/RunID and its context key; the explicit argument is the sole engine input, populated from invocation.Request.RunID. There is no precedence rule between two carriers.

A configured Store factory plus RunID locates the records. A run ID is not a global storage URL. Store selection belongs to the project on its workflow host, outside workflow definitions. Every application entry process (host, run-process child, remote workflow owner and cleanup owner) calls the same project-store resolver; in this slice its production implementation is DirectoryStore(project/runs). No context value or Go factory is assumed to cross Spawn's JSON stdin. The proposed `gimbal.WithRunStore(ctx, store)` supports direct in-process library calls and tests; it does not configure spawned application runners. Reject an application project configuration that attempts a non-default context-only override while admitting routed runs, rather than let the runner and sweeper choose different stores. A later SQL implementation is wired into that project resolver in each process; a serialized selection/configuration reference can be added then if needed, without changing workflow definitions or this Store interface. This slice adds no storage-plugin configuration framework. Run resolves the factory once and passes its run handle internally; methods never look up a global store. No filesystem or SQL types enter the contract. The runtime configuration owns the factory's lifetime; the run/controller owns its writer handle through pending cleanup, as described below.

The selected workflow host owns the writer. Remote task hosts continue owning executors. The central catalog retains the original run ID and placement route; it does not open another machine's directory. This slice propagates identities through existing local, HTTP and messaging routes; it does not introduce a store service, shared disk, owner failover or scheduler recovery.

`Create` is exclusive. A duplicate start returns an existing-run error without invoking the body, opening observation destructively, or dispatching anything. `Open` always acquires an exclusive writer handle, even when the caller only intends to inspect records. Offline tools/tests use it after the previous owner has closed; a second process inspecting an actively owned run receives busy. Read methods on the existing owner handle are available concurrently in process. No separate live read-only open is promised in this slice; the running application observes through its existing projection/subscription path. Run does not turn Open into implicit resumption. No migrations or compatibility shims for old run formats. Existing historical UI reads must continue to work through their existing read path; new-run records use the new contract.

## Identity without workflow boilerplate

The engine uses typed ULID-backed RunID, NodeID and RecordID values. Node kind distinguishes scope, session, action, service and question. Actions include command invocations and individual native turns. The root scope has a real NodeID and no parent. A session belongs to its scope; a turn belongs to its session; an action also records its executing scope when that differs from its owning session's scope. Services/questions belong to scopes. A question's persisted NodeID replaces registerInterviewQuestion's independent ULID allocation and remains the existing answer-control ID; use its parent scope, interview name and occurrence as the slot, without a second mapping table. Forked sessions have their own identity plus a source-session relation. Graph node names and user context keys are not new identities.

Every node has a stored slot `(parentID, kind, name, ordinal)` and an immutable spec, alongside its ULID. Reserve the ordinal under scope.mu, then release that mutex before EnsureNode performs I/O; recheck cancellation/ended state before publishing the handle or dispatching. Independent slots may commit out of order. The existing scope ordinal allocation supplies the ordinal; the existing hierarchical path remains DisplayKey. `EnsureNode` returns the recorded node for the same slot/spec or creates one with a fresh ULID. A conflicting spec fails. A ULID is allocated only on first insertion, not on every lookup. The parent must already exist in this run. The root uses one distinguished root slot.

The slot is an address for locating an ID, not a second externally meaningful ID. Preserve current readable addresses in graph/context text and existing control routes; attach durable IDs to event records and map display-address controls to nodes at the runtime boundary. Native provider IDs remain opaque bindings, never replace Gimbal identity. Retain executor prefixes such as command_/turn_/session_; their suffix can be the logical node ULID. Native provider IDs cannot be synthesized this way.

Groups allocate each child node before launching its goroutine, as today's child allocation already does. Independent branches use their own parent IDs and ordinal counters; completion order must not allocate identities. Concurrent use of the same parent/name retains today's scheduling-dependent call order; this slice does not certify it for replay. No source reflection, stack inspection, workflow-side ID arguments or user-authored checkpoint calls.

EnsureNode permits stable lookup for a future interpreter, but does not itself make Go deterministic or authorize a second activation. This slice does not reuse saved action results to skip execution.

## The storage seam

Put the public contract and portable record types in `runstore`, the first implementation in `runstore/directory`. These packages do not import gimbal or SQL drivers. Engine codecs translate existing lifecycle/agent payloads to versioned JSON. sqlc could later generate the queries inside a SQL implementation; it is not the interface.

Proposed interface, with names subject to normal Go implementation refinement:

```go
type Store interface {
    Create(context.Context, Header) (Run, error)
    Open(context.Context, RunID) (Run, error)
}
type Run interface {
    Header(context.Context) (Header, error)
    EnsureNode(context.Context, NodeSpec) (Node, error)
    Node(context.Context, Slot) (Node, error)
    Append(context.Context, []Fact, Durability) ([]Record, error)
    Flush(context.Context) error
    Read(context.Context, uint64, int) ([]Record, error)
    PutBlob(context.Context, io.Reader) (BlobRef, error)
    OpenBlob(context.Context, BlobRef) (io.ReadCloser, error)
    Close() error
}
```

Header contains only format version, RunID, workflow name, root NodeID and creation time: values available at this start boundary. Full invocation/input/code identity capture is later recovery work, not an implicit new launch-metadata API in this slice. Action intents still record their actual resolved inputs and routes. Runtime objects, credentials and resolved secret values are excluded; reacquisition references remain configuration.

NodeSpec contains Slot, DisplayKey and immutable JSON metadata. EnsureNode appends a Buffered node-created fact under the same ordering as Append. Its first referencing Committed lifecycle/intent fact flushes the identity before activation/dispatch; Close or explicit Flush persists unused nodes for offline readback. Header and root scope are committed together by Create. Header exposes the root NodeID. Node returns not-found distinctly. Engine helpers propagate store errors before allowing work to start; scope/session constructors that cannot return errors today may latch a run recording failure and prohibit dispatch, then return that error from Run. No panic-only persistence contract.

Fact is a versioned tagged record with RecordID, node/scope/session references, kind and JSON payload. Engine facts include action intent, executor binding, action outcome, lifecycle and agent events. Record adds the store-assigned gap-free sequence. IDs identify records; sequence expresses order. ULID timestamps never determine event order. The store validates node references. JSON must be valid and serialization version known to the engine; arbitrary Go errors are stored as explicit category/message/cancellation fields, not gob or serialized pointers.

Append adds one bounded batch atomically to the logical record stream, with no partially framed batch visible. Durability is `Buffered` for live agent events and `Committed` for node creation, intents, bindings, lifecycle boundaries and terminal results. Buffered success acknowledges a complete write to the OS, not power-loss durability; Committed waits for Flush through that batch's sequence. Flush also covers all preceding buffered events. Create commits header/root. EnsureNode buffers the new identity; all productive dispatch and scope activation remain behind a Committed referring fact, which flushes it first. Close flushes and returns any error. A store-owned coarse flush timer (250 ms target) limits ordinary buffered-event exposure; this is not a guaranteed power-loss window under slow storage.

Repeated identical RecordID returns its original record; a conflicting fact is an error. Compare the original encoded fact bytes, not semantic JSON equality. Existing duplicate records retain their sequence; new records get contiguous sequences in input order. Callers retain RecordIDs across a retry. `(nodeID, fact kind)` is additionally unique for intent, preassigned binding, native binding and terminal-outcome facts: a different RecordID conflicts, even if its payload looks equivalent. Validate all conflicts before writing, including conflicts inside a batch. No canonical JSON/equivalence framework and no automatic execution retries.

Read returns records through the latest successfully synced sequence after a supplied cursor, bounded by count; large data is referenced through blobs. PutBlob streams into immutable content-addressed storage, syncs before returning, and returns relative logical key, size and digest. It never returns an owner-machine path as portable identity. OpenBlob verifies the reference belongs to this run. Missing/corrupt records or blobs return errors rather than manufacturing empty results. Blob persistence precedes any referencing outcome record; unused blobs after interruption are acceptable in this slice. No collector/export subsystem is needed.

There is one writer handle per run, with thread-safe operations inside it. A second writer is rejected. DirectoryStore enforces this using BSD flock semantics on a separately opened descriptor on the selected workflow host. Two handles conflict even within one process; a per-process fcntl lock is not sufficient. This exclusion is a semantic requirement for every implementation: a future SQL adapter must enforce it with a cross-process database ownership primitive (for example a connection-scoped advisory lock keyed by RunID), not merely an in-process mutex. The current session implements no SQL adapter, distributed failover or lease renewal system; an adapter unable to honor exclusive ownership cannot claim this contract. Exclusive Create/mkdir implements create-once semantics; the registry reservation protects its live-object map; the store lock protects later writer Open. These serve different boundaries, not three interchangeable OS locks. Preserve the existing runner.lock: runner Connect and task cleanup use it to detect/control a detached runner (internal/runner/runner.go:227 and task_cleanup.go:34). Replacing that liveness protocol is outside this store slice, and a SQL store would not supply a local runner-liveness file. No cross-run transaction or SQL-shaped query API. Every implementation must pass the same small contract tests.

## Directory implementation and existing observations

Use `<project>/runs/<RunID>/state/` for authoritative records and blobs. Header/root is the first committed batch. Store batches in numbered append-only segments rolled at 16 MiB (a single batch is bounded to 1 MiB). Each batch is one length-delimited JSON frame with a checksum; sequence numbers belong to facts, not filenames. Serialize byte writes briefly, but do not hold the append/observation path behind a disk sync. A flush barrier records a sequence boundary, syncs the segments that contain it and advances the durable watermark only after success. Concurrent Committed callers can share a flush through their sequence. Sync the parent directory when creating a segment before acknowledging any committed batch in it. Sync newly created directory ancestors before Create reports success. Hold the flock descriptor for the writer handle. This is a small framed append log, not a query engine, compactor or database implementation.

On Open, scan segment frames, validate format/checksum/sequences/references, and rebuild compact slot/ID-to-offset indexes; do not load complete transcripts/results into those indexes. The recovery check in this slice models process death with an intact OS page cache. Only an incomplete final frame in the last segment can be discarded, and a writer truncates it before appending. A checksum failure or malformed fully framed committed record is an error, including at the tail. A failed write/sync poisons that handle for mutation until close/reopen: a failed acknowledgment may still have persisted a valid frame. Reopen resolves that uncertainty using the original RecordIDs. Reopening never clears complete records. Successful Committed appends retain the filesystem fsync guarantee; this slice does not implement automatic repair of an arbitrarily corrupted unsynced region after power loss. Such corruption is an explicit Open error, not silently discarded data.

Preserve observation's registry-first invariant. Register the live observation object, then invoke Store.Create inside observation.Open's existing initialization callback, before any body or reducer activity; remove that registration on failure. Adapt its callback/initialization contract rather than creating the directory first. Inside that same initialization callback, after successful Store.Create, the engine idempotently ensures its consumer-local projection/artifact directory (MkdirAll/accept existing directory) before starting observation writes. Exclusive creation belongs to Store.Create, not this materialization step. DirectoryStore has already created that directory; an injected non-filesystem store need not touch it. Projection materialization is engine responsibility and never part of the generic Store contract. A registered initializing object must not be mistaken for an external read-only run. Run listings use registered live runs, remote route records and recognized existing observation/projection files. They do not call Store.Open/Run.Header for a live run or directly parse authoritative segments; new-format projections only appear after Create commits the header. Listings also recognize legacy observation/log files; they skip bare/incompletely initialized directories. Direct access to such a directory reports incomplete initialization, without caching an external store. A new-format marker/format detection selects this behavior; no migration of old logs. Duplicate concurrent registration must not replace the winning live object: admission reserves RunID in the registry atomically, then exclusive Store.Create decides persistence ownership. A rejected duplicate leaves the winner's registration intact.

Create makes the final run directory exclusively, creates/opens its writer-lock file and acquires flock, then commits header/root and syncs their directory entries. Only after those steps does it atomically publish a small immutable `state/ready` marker and sync its directory. That marker means initialization committed while the writer lock was held; it contains no duplicate authoritative metadata. Store.Open and new-format sweepers must see ready before touching the writer-lock file, and Open opens that file without O_CREATE. Missing ready/lock means incomplete initialization and causes no flock attempt. Thus no observer can steal the store lock in Create's own create-before-flock window. Busy on a directory Create just made is an initialization error, not evidence of a duplicate accepted run. The completed marker remains after writer Close; normal reopens still require exclusive flock.

If initialization fails, the run is not accepted and no body runs; an abandoned directory is reserved/incomplete, never silently reused. Output/temp-file permissions follow current private executor/state conventions.

The current run.jsonl, session transcripts and observation tables become projections for newly created runs: record through Run store first, then feed existing reducers and live streams. Do not maintain two authoritative event writers. A projection failure is reported as an observation error without erasing the committed fact or marking a successful action failed. Readers of historical runs keep their existing reader. Keep existing UI projection output formats and observation stream sequence separate from store sequence. This slice adds no persistent projection cursor or live reconstruction path. Authoritative readback uses Run.Read; a test can feed the saved facts once into a fresh existing reducer. Repairing stale UI projections after a host crash belongs to the later recovery slice.

Lifecycle/intent/outcome boundaries use Committed append. Normalized agent events use Buffered append and feed observation/subscribers immediately after the complete frame is written, without waiting for a disk flush; a live event is a projection, not a durability acknowledgment. No 20-ms fsync-before-display queue. Keep pending append/flush bookkeeping bounded and never buffer complete transcripts in memory. At capacity, Buffered append applies context-cancelable backpressure until capacity is available; it never drops events or fails solely because a bound was reached. Under prolonged storage stalls this may stall native observation; it is not an unbounded-memory or zero-latency promise. The timer, lifecycle boundary, outcome and Close flush preceding event frames. A flush failure latches a recording error, prevents later dispatch/success, and leaves the live projection explicitly ahead of durable state until the error is resolved. After a crash, fully framed valid records discovered on Open are synced before exposing them as committed; incomplete tail rules below apply. Test streaming under a deliberately blocked flush: deltas below the bounded capacity must reach subscribers before that flush is released, while a terminal result must wait. This tests independence from sync latency rather than asserting unmeasured hardware timing. Capture complete command/turn results, errors, usage and output references at the current native-outcome boundary. Keep large output file-first using PutBlob's streaming ingestion; engine code may materialize consumer-local paths through the existing artifact layer. Never place a foreign host path in a durable result as its sole artifact identity.

## Dispatch integration: enough to make the IDs useful

An action intent contains its node ID, resolved request, stable executor operation/session IDs and owner route before external work. Preassigned executor IDs are part of the intent; any provider-native identity learned later uses a distinct native-binding fact, not an overwrite of the preassigned binding. Save prompts/schema and command args/workdir as payloads or blobs as appropriate; do not persist temporary secret callback URLs or secret values as durable request input. Record the durable secret/config references instead. Bindings may record native IDs learned after admission separately; this slice promises traceability, not lossless recovery of an unacknowledged native creation.

Local command executor currently creates a fresh ID inside runCapturedCommand; agentexecutor.Adapter does likewise inside CreateSession/RunTurn. Replace those workflow-owned allocations with engine-supplied execution identity in the existing effect context. Standalone run-prompt/executor uses still allocate ULIDs when no workflow identity exists. Choose an explicit backend-contract change: add `ExecutionIdentity` to backend.Process, Session, Turn and Target (the existing close request type), and to messaging envelopes for the operations they already support, including close. Messaging fork stays unsupported and fails before dispatch; this slice does not add it. It carries logical scope/session/action ULIDs and the preassigned executor session/operation IDs appropriate to the operation. Keep Owner.Scope/Task as the existing hierarchical execution/control addresses: changing them to flat ULIDs would break prefix-based cleanup. HTTP JSON and messaging envelopes carry ExecutionIdentity unchanged; add `effects.WithExecutionIdentity` and `effects.ExecutionIdentityFromContext` as a separate context key beside Owner. taskdaemon re-injects the received identity into the contexts it constructs for native adapter calls, including its background/timeout contexts. Context values do not cross the network on their own. The command task-host bridge must use the supplied command ID instead of executor.NewCommandID. Replies still report provider-native bindings; they cannot replace supplied executor IDs.

For workflow-owned session creation, reserve the session ID before lazy CreateSession. Reserve a separate action node/operation ID for fork and close dispatches; close is not allowed to reuse the last turn's ID. Thread these IDs through the adapter/effect-context plumbing into agentexecutor's CreateSession, Fork, Close and RunTurn. scope.end and retryCleanup must construct a fresh cleanup effect context containing Owner plus ExecutionIdentity before adapter.Close; their current bare Background/timeout contexts cannot carry it. HTTP/messaging close preserves Target.ExecutionIdentity; taskdaemon.close passes it on to agentexecutor.Close instead of minting an unrelated ID at agent.go:626. For adapters without the separate executor (e.g. OpenCode), retain their native IDs as explicit post-admission bindings; do not claim a preassigned provider ID or independent result-retention capability. Their Gimbal action identity is still recorded before the call.

Missing ExecutionIdentity is allowed only for genuine standalone callers that have no workflow store; those mint ULIDs at their entry boundary. A workflow-owned request must not silently regenerate an ID. Update all in-tree backend/plugin implementations and their conformance tests in the same change. Third-party backend authors must implement the new semantic contract before supporting these workflow-owned requests; there is no fallback that silently drops identity, no mixed-version protocol compatibility promise or migration layer. State this backend-contract change in the implementation issue/PR. Add `ExecutionIdentity bool`, default false, to both gimbal.BackendDefinition (registry.go:290) and MessagingDefinition (messaging_registration.go:17). Set it on conforming in-tree registrations; Registry.Connect checks it in both its execution-backend and messaging branches before any workflow-owned dispatch. Backends that do not declare support are rejected before productive work. This declares plugin support; it is not evidence of the remote daemon version. To fail safely on an old daemon that ignores unknown JSON fields, use new required-identity wire operation names for productive requests: `identified-session`, `identified-turn`, `identified-process`, and `identified-close` on HTTP task endpoints and messaging Kind. New handlers validate the supplied identity then call the existing implementation; old handlers return 404/unsupported-kind before any native execution. Fork follows identified-session where already supported. All new shipped producers (including standalone producers, which allocate IDs themselves) use these names; remove replaced productive wire handlers and never retry on an old operation name. Read/status/control paths remain as currently shaped, with fresh control request IDs. On identified HTTP operations, a 404/405 is a typed definitive contract rejection surfaced by both effects.Call and backend.HTTP.call. Centralize the classification in effects.ConfirmStarted by passing the original admission error to it: a typed rejection returns immediately without polling, while genuinely uncertain errors retain the current reconciliation. Update every caller (taskdaemon/client.go:81, remote_execution.go:66 and environments/operations.go:212) to propagate that classification unchanged, without an outer DeliveryUncertain wrapper or old-name fallback. The environment helper uses its existing upgrade-Gimbal message for this rejection. Its mutation receipt is still written as Attempted before sending (required for uncertain outcomes); after a definitive rejection it durably settles the receipt as not admitted/Attempted=false before returning, so an explicit retry after upgrade is not condemned to polling a nonexistent task. The mutation finalizer at operations.go:159–172 needs an explicit definitive-rejection branch: leave Result and Error empty, set Attempted=false before invoking the existing cleanup closure (which itself writes receipts), release the acquired binding through that cleanup path, and persist the settled receipt before returning the typed upgrade error unwrapped. Do not route this through helperFailed, which caches Error, or the uncertainty branch. CleanupPending reflects only the actual binding-release result: false after release, true if release failed. Join a real release failure with the rejection rather than misclassifying native admission as uncertain; before an explicit retry reuses such a receipt, finish its pending binding cleanup before new admission, even though Result and Error are empty. Preserve the original operation/request identity. Failure to persist that settlement returns a recording error and leaves the receipt conservative; it never authorizes an automatic resubmit. This does not erase a receipt for an accepted or uncertain request. Record a rejected outcome for that action; do not create an unresolved-admission cleanup obligation for work that was never accepted. Existing unrelated owned sessions/resources still retain their real cleanup obligations: rejection must not clear them. Other genuinely ambiguous transport failures keep their existing reconciliation behavior. This is one explicit breaking wire-contract change, not a negotiation/migration framework or parallel execution path. Test against the old decoder/dispatcher shape, not merely an in-process false capability flag. An obsolete or nonconforming third-party transport must fail its conformance checks; a declared flag is not proof that arbitrary plugin code honors the contract.

ExecutionIdentity also carries RequestID, a bare ULID chosen before the intent is committed: use the action NodeID, or the session NodeID for its one create request. The executor ID remains the appropriate prefixed ID. Change effects.Request to take an explicit request ID; Harness.call, messageTurn and startMessageProcess obtain that ID from the supplied ExecutionIdentity instead of minting one below the adapter boundary. Standalone/control producers allocate their own request ID at their operation boundary. Fork and close use their distinct action IDs, never the session-create request ID. Do not blindly inherit a productive request ID into an interrupt/poll/control subrequest. Bulk cleanup fan-out remains host-owned housekeeping and can mint its own child delivery IDs; its caller records the cleanup episode, not an audit entry for every transport delivery. Tests inspect actual accepted executor requests and demonstrate that a missing/unsupported identity fails before native work, not merely that new metadata columns exist.

An action outcome records raw return/error/usage and durable owned output, below Generate's validation/correction loop. Each correction turn receives a new action node; Generate itself need not introduce another executor identity. Check continues building scope context normally. A command nonzero exit is a result; a transport or recording error is not invented as a successful result. If outcome commit fails after native completion, return a recording error and retain the executor result. No resubmit. Seven-day executor retention is not the permanent store: successful outcome commit owns its output independently.

Question/service/session lifecycle facts receive identities and flow through the store; Set and ordinary Go calculations do not become artificial actions. Existing cancellation/shutdown behavior remains this slice's behavior. Durable control acceptance, resource reconciliation, fork/close retry semantics and automatic recovery are later work; record their existing events and relationships without claiming those operations are restartable.

## Terminal cleanup is part of recording, not a second writer

Run's body returning and the run controller releasing ownership are distinct existing events. Keep the run-store handle open through final body facts and initial cleanup. If cleanup is complete, flush/close it on the normal finish path. If CleanupPending remains true, transfer its lifetime to the retained controller; retryCleanup uses the same handle, and the last successful cleanup flushes/closes it. Flush before Run returns even when the handle remains retained. Later store/close errors are reported to the cleanup caller rather than swallowed. Do not keep a process alive for the store: the existing retained-cleanup lifecycle determines lifetime. A process death releases the OS writer lock.

Normal workflow-owned direct close calls and explicit operator retryCleanup invocations get recorded action intents before dispatch and outcomes after those invocations return. Each explicit retryCleanup invocation is a new cleanup action occurrence, not an overwrite of the prior result. Existing executor close/serialization behavior remains responsible for native cessation; this adds no automatic retry policy. Scope cleanup is a bulk operation: its child adapter calls inside the task host are owned implementation work, not extra workflow-method actions. Record the bulk cleanup request identity and outcome; do not pretend to know the executor IDs of child closes before the remote host selects them. Direct session-close requests do carry the preassigned close executor ID as specified above.

Route RecordCleanup and RecordTerminated through the run-store writer for new-format runs, then update their existing observation projections. They must not independently truncate/append authoritative run facts. When the retained controller is alive, pass its existing handle. For new-format CleanupExited/orphan mutations, acquire Store.Open's exclusive writer handle first, then open the already-existing runner.lock and try its lock non-blocking. Busy at either step releases any acquired handle and returns without dispatch. This is the same order as runner startup (Store.Create, then runner.lock) and avoids stealing a just-created runner.lock before its owner flocks it. Only after both checks may cleanup dispatch or terminal/cleanup recording proceed. Resolve the same project Store in each application process and pass that factory to cleanup/terminalization; observation does not choose it. In-process injected-store tests pass their same instance to their retained controller/cleanup code; they do not attempt to send a Go object through a spawned runner. Close that handle after the cleanup request. A live store-writer conflict returns busy; it does not start cleanup in parallel or bypass the store. No automatic workflow-body invocation is added.

Run terminal outcome remains immutable; subsequent cleanup attempts/results append distinct facts after it. Allocate post-terminal cleanup action slots from the stored occurrences, so a new process cannot reset their ordinal counter. This is recording an existing control operation, not replaying workflow code. Persistence errors prohibit productive dispatch. Existing safety-stop/teardown paths must still be able to stop a known owned target after a recording failure: propagate the recording failure and actual stop result separately, never claim that unrecorded cleanup was durably accepted. This exception does not authorize replacement execution, automatic workflow retries, owner takeover or orphan cleanup without cessation checks. Legacy-run terminalizers retain their existing reader/writer path; new-format dispatch is explicit. Store selection/identity and termination facts are the only changes to these cleanup paths; native resource reconstruction and durable queued controls remain later work.

The existing periodic CleanupExited sweepers (internal/host/host.go:407–425 and internal/runner/daemon.go:112–120) are housekeeping, not new workflow-method actions every second. Preserve their retry cadence and existing unchanged-outcome suppression. Create/commit one cleanup-episode node and intent for the target scope on its first dispatch; append a repeatable `cleanup-state` fact only when cleanup status/error changes, and append the one terminal-outcome fact on eventual completion, comparing the existing status/error fields rather than canonical JSON. Repeated identical failed polls append nothing and request no sync. They may resend housekeeping requests with transient delivery IDs; the store does not promise an attempt-by-attempt audit for these internal deliveries. Reopen loads the last cleanup state before comparing. The initial implementation may pay a full segment scan per reopen, comparable to today's stopped-run reread; do not add a new summary cache/compactor in this slice. Measure it with the existing check and optimize only if it becomes a demonstrated issue. The episode remains uncompleted while cleanup is unconfirmed; do not store each failure as an immutable terminal action outcome. Explicit operator retryCleanup is distinct and remains recorded as described above. This preserves an existing retry policy; no new one is introduced.

For new-format runs, observation/follow.go must not call RecordTerminated from Registry.Snapshot/refresh. New-format follow.go readers must not flock runner.lock at all. Reads retain the last projected lifecycle state and may show existing connectivity-unavailable hints, without inferring death, appending a lifecycle fact, opening a writer or replacing authoritative state. The existing host cleanup/terminalization owner writes the actual fact under the store handle; historical runs keep their reader behavior. For runs with no remote task route, confirmed runner death still commits the terminal fact once. Preserve an unconfirmed-cleanup indication if owned native work may remain; absence of a remote route is not evidence of release. This slice adds no new local orphan-resource reconciliation. After that one terminalization, this sweeper has no further native cleanup to perform for that route and returns settled, without claiming resources were released. After acquiring the store writer first, the sweeper can establish that condition only by acquiring an already-existing runner.lock non-blocking; it must never create that file or treat its absence as death. It skips directories without it, including initializing runs, in-process runs and route-only entries; do not preserve CleanupExited's early return in a way that leaves new-format runner-hosted runs forever running. An in-process run whose host dies has no runner.lock; this slice retains its last projected state and does not infer death or restart it. That host-recovery behavior belongs to the next slice.

Unify the orphan stop entry in runner.go:250–263 with the same locked cleanup owner. It must not call orphanCall to dispatch and then CleanupExited to dispatch again. Preserve requested root/scope target semantics; acquire the store writer and then the runner-liveness check once in that order, perform one requested cleanup dispatch, record through that handle, then update projections. A busy live owner routes through the existing live controller or reports busy. Observation readers never become an alternate cleanup owner. ResourceReady's direct write in remote_execution.go:20–33 also moves to the ordinary store-then-project event path, including replacing its old r.writer nil guard.

Connect's discovery-only runner-lock probe is allowed after its existing published-controller-file check, but it must release that probe before any store-open or mutation. For new-format orphans, CleanupPending is read-only: use existing projected cleanup state or a read-only backend Pending query where available; on a messaging route without that query, return pending/unknown rather than dispatching cleanup to find out. task_cleanup.go's current messaging orphanCall("cleanup") dispatch is not retained as a status probe. effects.Cleanup also takes the explicit cleanup RequestID from its caller (including its in-package effects.Request call); steer uses a fresh control request ID, never a productive turn ID. Actual cleanup stays in the one mutating helper with the store-first lock order. This prevents Connect from holding runner.lock and recursively trying to acquire it again through the unified cleanup path.

Before exclusive Open, sweepers use a cheap, positive settled-run gate from the existing run projection: terminal lifecycle plus confirmed resource release means return settled without opening/scanning the store. In Run.finish, after root cleanup and aggregation of session/service/scope cleanup results, always commit a root `cleanup-state` fact before RunEnded/Complete, regardless of cancellation or task route. Its status reflects actual cleanup, not the body verdict: a failed body with confirmed released resources records released; unconfirmed cleanup records pending. Feed the optional `cleanup_status` (`pending`/`released`; absent means unknown) in the existing small run projection from that committed fact. This explicitly replaces the current conditional emission at scope.go:214 for new-format state: normal successful local and in-process runs must produce it too. Retained/orphan cleanup emits subsequent changed root cleanup-state facts through the same path. Publish released only when owned session/service/scope cleanup is confirmed; do not infer it merely from a missing Cancellation value or from a body error. On completion of retained/orphan cleanup, update that same field after the committed fact. This is one field in the existing projection, not a new index/cache subsystem. Missing/stale/invalid projection leaves the run eligible for the normal locked check. After ready validation and successful exclusive Open, if runner.lock is absent, close the handle and return settled to the sweeper for that non-runner entry; no runner-death inference or terminal mutation occurs. This applies only after writer acquisition, so an initializing or active in-process owner instead returns incomplete/busy and remains eligible on a later tick. Never mark an entry settled merely because ready or runner.lock is absent before the ownership check. Raw run-row reads for this gate must not invoke Snapshot.refresh or replay transcripts. Historical runs keep their existing handling; tests cover a host restart over settled new-format successful and failed-body runs with zero Store.Open calls, plus an unknown/pending run that still receives the check.
